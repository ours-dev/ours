# ioservice

The server side of ours.io for trees held in memory (component-framework design, "ioservice"): the root serves /boot and each component's /svc with it, and every provider serves its outgoing directory with it. It is the counterpart of Fuchsia's Rust vfs (`src/storage/lib/vfs/rust`), cut to what ours uses.

ours.io (`//system/lib/ours.io`) only says what the messages look like. This library is what answers them: the connection table, the rights and path checks of Open, Clone, Close, Read, ReadDirents and GetBackingMemory, and the walk down a tree. It is not a mounting layer: there is no mount table, and a client puts a server's tree at a path in its own namespace (`//system/lib/fsio`). A disk filesystem is a separate server and may not use this library at all.

- `ioservice::Tree` (`<ioservice/tree.hpp>`) holds the five node kinds: pseudo-directories, read-only VMO files, services, Subtree nodes and Handler nodes (and the remote entries the root mounts). The program adds the nodes; a client never does. Nodes live in storage the program provides, since user programs have no heap. A Subtree node is a place the program serves with a tree of its own, and a Handler node a place whose content a `NodeHandler` answers: `Tree::resolve(directory, path)` is `lookup()` for an Open, and stops at the first Subtree node, Handler node or remote entry it meets, answering the node and the rest of the path after it (`.` when the path ends on the node itself, empty when the walk met none of them); `lookup()` itself reaches such a node but not through it. `printable_path()` makes a client's path fit a log line.
- `ioservice::Server` (`<ioservice/server.hpp>`) holds the connection table and handles ours.io: Open with the Rust vfs's checks in its order, ReadDirents, Read, GetBackingMemory, Clone and Close. An Open that walks to a Subtree node runs the checks that come before the walk on the connection it came on, the walk included, and then answers `Action::Subtree` with the node's value, the rest of the path, the Open's flags unchanged and its channel; it makes no connection. A Subtree node is listed as a directory.
  - A **Handler node** (`Tree::add_handler(parent, name, value)`) is the other way a program serves a place of its own: the core keeps the protocol and asks a `NodeHandler` only for content, which may take time. An Open that walks to the node runs the same checks 1 to 7 on the connection it came on and the walk (8), and then asks the handler to `open` the rest of the path; the handler answers the kind of object it opened and a **cookie**, a `u64` of its own that the core keeps in the new connection, hands back on every later call and never reads (check 9 is made on the kind the handler reports: a file for a request that accepts only directories is NotDir, the reverse NotFile). A Read, ReadDirents, GetBackingMemory or Open on that connection runs the protocol's checks first (a Read without READ_BYTES is refused before the handler is asked), then calls `read`, `read_dirents`, `get_backing_memory` or `open` with the cookie. What stays in the core is the seek offset (the handler is given the connection's, and it moves by the bytes of a Read that is **completed**), the dirent phase (the `.` entry comes first and is the core's, the handler lists what follows and names the cursor to go on from), and the encoding of every reply. `clone` asks for the new connection's cookie, and `release(cookie)` is called once for every end of a connection: Close, the peer going away, the program releasing it, a connection dropped, with a request pending or not. `NodeHandler` is the abstract class the program's filesystem derives from, with a protected non-virtual destructor like `Handler`; every call is told the node's `value`, so one handler can serve several nodes.
  - **Answering later.** `open`, `read`, `read_dirents` and `get_backing_memory` are given a `Ticket` and answer `Done(result)` or `Pending(ticket)` (`Answer<R>`, a variant): a result is a `ustl::Result` of the operation's payload and a status, and a handler with no reason to wait always answers `Done`. A `Pending` request is ended by `Server::complete(ticket, result, out)`, which builds the reply in the shared `ReplyBuffer` and returns an `Outcome` for the program to write, and touches no channel. It never releases a connection and never answers `Drop`, because a connection is released only from its own callback and `complete()` runs in the handler's own Waiter: a result the wire cannot carry (an error status `ours::Status` does not name) is the handler's bug, answered InternalError as too many bytes is, and the connection stays. A ticket is the `ConnectionId` and a **serial** the connection bumps for every request it asks the handler about; a connection has one request outstanding, and `dispatch()` on a connection that has one answers `Action::Pending` for the request that begins it and `Drop` for any message that comes while it waits (the program does not read such a connection: a Loop slot answers `Suspend`). `complete()` refuses a ticket whose connection was released or reused, that has no request pending (spent, or never pending), or whose serial a later request moved on (NotFound), and a result of another operation than the request's (InvArgs), changing nothing, writing nothing and taking nothing from the result: a VMO handle in a refused result is still the caller's, and an `Opened` cookie is still the handler's to release. A pending Open holds the request's server end until it is answered; `Drop` and `release()` hand it back.
  - The bytes a Read or ReadDirents returns are the handler's, valid until the core call that received them returns: the core copies them once into the reply, as it copies a file of the tree. The handler is never asked about a request whose reply would not fit, and a handler that returns more than it was asked for is answered InternalError.
- `ioservice::LoopServer` (`<ioservice/loop_server.hpp>`, in the target `//system/lib/ioservice:loop_server`) serves a `Server` on a `loop::Loop`: one slot per connection, which waits on the connection's `LoopServer::Binding`, a `loop::Waiter` whose `on_signals()` reads a message from the channel, hands it to the `Server` and does what the `Outcome` says, and whose `on_rearm_failed()` releases the connection when the Loop could not arm its wait again. The program says what an Open of a service node comes to by implementing `ioservice::LoopServer::Delegate`, an abstract class its own server class derives from; the same class can be told, by two functions that do nothing unless overridden, that a reply could not be written (`write_failed()`) and that an Open was refused, with the directory, the path and the status (`open_refused()`). An Open that walked to a Subtree node goes to the delegate's `subtree(value, rest, flags, channel)`, called inside the connection's callback as `connect()` is, which owns the channel from then on; the `rest` views the request buffer and is valid for the call only, so a handler that parks the Open copies it, and a delegate that does not override the function closes the channel, as a missing delegate does. It is the glue the root's /boot and /svc and a provider's outgoing directory all need; it is a target of its own so that the core below makes no system call.
  - **Pending requests.** `LoopServer`'s last constructor argument is the `NodeHandler` its `Server` asks about Handler nodes. A request the handler answers `Pending` makes the `Binding` answer `loop::Action::Suspend`: the connection's slot stays in use with no wait armed, so the client's next messages wait in its channel, in order, and a client that goes away is not seen. The handler ends the request later, from a Loop callback of its own, with `LoopServer::complete(ticket, result)` (one overload for each operation's result, as the `Server`'s): it calls `Server::complete()`, carries out the `Outcome` (a reply is written on the connection's channel; the connection of a granted pending Open is made on the server end the `Server` held and gets a slot; a refused one is answered with an epitaph on that end, which is closed), and then `Loop::resume`s the connection's slot, in that order, so the next request is never started before the last is answered. The `Binding` keeps the key `Loop::add()` answered for its slot, 32 bytes where it was 24, for that. `complete()` answers Ok when the `Server` took the result, whatever became of the reply; NotFound or InvArgs, as the `Server` refuses, with nothing written and nothing taken from the result; and BadState or NotFound from the resume when the slot was not suspended, which is a bug of the program. It never releases the connection: a reply that cannot be written (the client went away while it waited) is told to `write_failed()` and the slot is resumed all the same; the connection's own callback then sees the closed peer, releases the connection, calls `release(cookie)` on the handler once and answers `Close`, so the index is not reused while the old slot is in use. A resume the kernel refuses frees the slot and has the `Binding` release the connection from inside `complete()`, after the reply. A completed refusal has no path, so `open_refused()` is not called for it. `complete()` cannot run inside the callback of the connection it completes, which is where `resume()` would answer BadState and `Suspend` would strand the connection: the `Server` accepts a ticket only after the handler's call has returned `Pending`, and nothing runs between that and the `Binding`'s return.
- `ioservice::Outgoing` (`<ioservice/outgoing.hpp>`, in the target `//system/lib/ioservice:outgoing`) is the provider side of a component, the counterpart of Fuchsia's `component::OutgoingDirectory` (`sdk/lib/component/outgoing/cpp`) cut to unmanaged protocols and static directories: its outgoing directory, an `ioservice::Tree` served by a `LoopServer`, with one entry under `svc/` per protocol and the tree of each directory capability at the path its declaration names. `add_protocol(name, handler)` adds `svc/<name>`, where `handler` is an `ioservice::Handler`, the abstract class a protocol's server derives from, with one function, `connect(channel)`; `serve(directory_request)` serves the directory on the DirectoryRequest startup handle and waits on it. When the root forwards a client's Open of `svc/<name>`, the handler gets the client's channel, usually to add it to the same Loop.
  - `add_directory(path)` takes the absolute path as the manifest declares it (`/export/data`), makes the directory at its end and every missing one on the way (`export/` once, shared by `/export/a` and `/export/b`), and returns the last node. The program fills the tree below that node with `add_directory(parent, name)` and `add_file(parent, name, file)`, which are `Tree`'s adders and nothing else. The tree itself is not reachable: the `Outgoing` keeps the service nodes under `svc/` pointing at the handlers it holds and the declared paths it has checked, and a program that could add a node anywhere could break either. A path that is not absolute, is `/`, has an empty, `.` or `..` segment, or is `/svc` or under it is InvArgs; one equal to, above or below a declared path is AlreadyExists, compared by segments (`/svcx` and `/export/data2` are fine); one whose directories do not fit is NoResource. A refused call changes nothing. The manifest compiler refuses the same paths; the `Outgoing` holds them again because a program can be wrong without a manifest.
  - `add_service(parent, name, handler)` puts a service node in the tree of a directory capability, under `parent`, a node `add_directory(path)` returned or one made below it (the tree is not reachable, so the node comes from there, as `add_directory(parent, name)` and `add_file(parent, name, file)` do). An Open of the node with `PROTOCOL_SERVICE`, through a connection that holds CONNECT (a use of `r*` does), hands the channel to `handler.connect()` exactly as an Open of `svc/<name>` hands it to a protocol's handler; as a directory it answers NotDir, as a file NotFile, and without CONNECT AccessDenied. `handler` goes in the table `add_protocol()` fills, so `MAX_PROTOCOLS` limits the two together, and the Subtree nodes of `add_subtree()` and the Handler nodes of `add_handler()` with them: eight protocols leave no room for a service node and the reverse. It is refused with InvArgs for a `parent` that is not at or below a declared directory (the outgoing root, `svc/`, the directories on the way to a declared path and an id of no node: the protocols' nodes stay `add_protocol()`'s), with NoResource when the table is full, judged before the node is added so that a refusal leaves nothing behind, and otherwise as `Tree::add_service()` refuses (InvArgs for a bad name, NotDir, AlreadyExists, NoResource for the nodes). `//examples/files` uses it for `export/docs/stop`, whose handler exits the program, which is how routing_checks stops a provider after its entry has worked.
  - `add_subtree(path, handler)` serves a declared path with the program's own code: it makes a Subtree node at the end of `path`, and every missing directory on the way, under the rules of `add_directory(path)` (InvArgs for a path that is not valid or is `/svc` or under it, AlreadyExists for one equal to, above or below a declared path of either kind, NoResource when the nodes do not fit, and nothing made by a refusal), and returns the node. `handler` is an `ioservice::SubtreeHandler`, an abstract class like `Handler` with one function, `open(rest, flags, channel)`: an Open that walks to the node reaches it after the outgoing directory has held the Open to the checks it makes on the connection the Open came on (a valid path, TRAVERSE, rights within the connection's, no creation flag, the walk to the node), with the rest of the path (`.` for the node itself; valid for the call only), the flags exactly as the consumer asked, and the channel, which the handler owns: it serves it, forwards it, answers it with an epitaph or closes it. No connection of the outgoing directory is made, and nothing can be added below the node. The handler goes in the table `add_protocol()` and `add_service()` fill, so `MAX_PROTOCOLS` limits protocols, service nodes, Subtree nodes and (with `add_handler()`) Handler nodes together, in any order. A Subtree node sits at a declared path only, not below a directory `add_directory(path)` returned: the manifest declares the path, and the program serves the place the declaration names. `//examples/files` serves `export/docs` this way, from a second `Tree` and `LoopServer` of its own.
  - `add_handler(path, handler, value = 0)` serves a declared path through a `NodeHandler`: it makes a Handler node at the end of `path`, and every missing directory on the way, under the rules of `add_directory(path)` and `add_subtree()` (InvArgs for a path that is not valid or is `/svc` or under it, AlreadyExists for one equal to, above or below a declared path of any of the three kinds, NoResource when the nodes do not fit or the table is full, judged whole before anything is made), and returns the node. An Open that walks to it runs the checks the outgoing directory makes on the connection it came on, and then the server asks `handler` to open what is left of the path; the connection it makes holds exactly the rights the Open asked for, and the server keeps the protocol on it. `value` is what `handler` is told on every call about this node, so that one handler can serve several; the table index the node is registered under is the `Outgoing`'s own, which it translates (`Outgoing` is the `LoopServer`'s `NodeHandler` and passes each call on). A request the handler answers `Pending` is ended with `Outgoing::complete(ticket, result)`, which forwards to `LoopServer::complete()`. The handler goes in the table `add_protocol()`, `add_service()` and `add_subtree()` fill, so **`MAX_PROTOCOLS` (8) limits protocols, service nodes, Subtree nodes and Handler nodes together**, in any order. `//examples/files` serves `export/slow` this way: one file whose Read it answers a few turns of its Loop later.
  - When the root routes a directory use to the provider it writes one Open on the outgoing directory, `export/data/<subdir>` with the use's rights and `ProtocolDirectory`, and the server answers it like any other: a directory node at the end makes a connection on the use's channel with exactly the rights asked, a file or a service answers NotDir, a missing segment NotFound. Every later Open through that connection is held to its rights, so rights only shrink from the entry on. No code of the `Outgoing` is in that path.
  - `Outgoing::Storage` holds `MAX_NODES` (32) nodes and `MAX_CONNECTIONS` (32) connections beside `MAX_PROTOCOLS` (8) handlers (for the protocols, the service nodes, the Subtree nodes and the Handler nodes together; an entry of the table is a pointer for each of the three handler classes, one of them set, and the value a Handler node's handler is told), 14,984 bytes in a user program (14,600 before the glue for pending requests, which grew a `Binding` from 24 to 32 bytes, 256 bytes for 32 of them, and an entry of the table from 16 to 32, 128 for 8; 13,320 before the handler node, which grew a `Connection` from 40 to 80 bytes, 1,280 bytes for 32 of them; the 13,064 this paragraph gave before does not match the tree it described, whose `Node` is 80 bytes; 9,496 with 10 nodes and 4 connections before directory capabilities). A connection is spent by the root's own, by each consumer's entry, by every directory or file a consumer opens below it, and by each clone made of an entry. The nodes are one pool: the root, `svc/` and a node per protocol take `2 + MAX_PROTOCOLS` of them once every protocol is added, and the rest go to the declared paths (a node per segment, a shared segment once) and the trees under them, so a program that wants all its protocols adds them before a large tree. A program's Loop table follows `MAX_CONNECTIONS`, since each connection has a slot: echo's is `MAX_CONNECTIONS + MAX_CLIENTS`.
  - An Open the outgoing directory refuses, such as one of a name it does not serve, is said on the debug console in one line, through the vDSO's `debug_write`, which needs nothing set up by the program. It is said for the Opens that arrive at the outgoing root and at `svc/`, which are the root's, where a manifest and a program that spell a protocol or a path differently show; an Open refused through a connection below a declared path is a consumer's, who reads its own epitaph, and is not said. `//examples/echo` is its first user, and dev's routing_checks reaches echo through it and prints `routing_checks: passed`.

The core touches no channel. `Server::dispatch()` takes one message and returns an `Outcome`: what to write and where, which new channel to wait on, which channel a service was asked for, that the request waits on a handler (`Action::Pending`, ended later by `Server::complete()`), or that the connection is to be dropped. The program does the writing and the waiting. Its one system call, the duplicate GetBackingMemory hands out, goes through a function the program gives it, so the whole server runs on the host, where its tests are.

## Layout

```text
include/ioservice/   public headers, reached as <ioservice/...>
src/                 sources
test/                host-side tests, built with googletest
```

## Building and testing

The library is `//system/lib/ioservice`; its headers alone are `//system/lib/ioservice:headers`. The gtest executable is `//system/lib/ioservice/test:ioservice`, built on the host by the default build. `LoopServer` is tested by `//system/lib/ioservice/test:loop_server`, on a real Loop against the fake kernel of `//system/lib/ioservice/test:fake_kernel`, which defines the vDSO's channel and port calls, and `debug_write`, on the host; `Outgoing` is tested by `//system/lib/ioservice/test:outgoing`, on the same fake kernel.
