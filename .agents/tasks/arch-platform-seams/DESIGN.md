# arch-platform-seams: rules for the arch, platform and driver seams, and the refactor items that follow from them

**Date**: 2026-10-30
**Status**: Proposed

## Problem
The user, 2026-10-30: "把架构接口和平台接口整理一下，我们一起来重构一波" (tidy up the architecture and platform interfaces, and refactor them together).

Why now: riscv-kernel step 1b (`.agents/tasks/riscv-kernel/PLAN.md`) writes riscv's side of every seam generic code uses. Today those seams follow no stated rule: declarations live in six homes, platform calls are spelled five ways, board chips sit in `kernel/arch/x86`, and generic behaviour lives inside x86's bodies. Without rules, riscv copies x86's placement and names, accidents included.

A survey ran first: three reports (ours's arch seams, ours's platform seams, Zircon's model), a synthesis, and an independent critique that found 12 wrong claims, 10 missing items and 9 framing problems in the synthesis. This document is the corrected second draft: every critique correction is applied, and every ours `file:line` kept was re-verified at HEAD `681b3a4d` (Zircon at `51f05104c13`, paths under `zircon/kernel`).

Nothing here is decided. Every principle below is the user's to decide, one at a time; every "Recommendation" is a recommendation only, every principle's "Decided" field reads "open", and the Decided column of the Decisions table stays empty until the user decides.

## Goals and non-goals
Goals:
- A map of the seams ours has today and of the ones Zircon has, one line per seam kind.
- The inconsistencies, each with its evidence, what it costs riscv, and the outstanding repair it overlaps, if any.
- The principles as questions for the user: the objects involved first, then the options, a marked recommendation, Zircon's choice, and a Decided field.
- Refactor items tied to the principles, each one commit (or a stated few), with its size and when it is done.

Non-goals:
- No code change and no commit comes from this document. Each item is introduced to the user on its own before it starts.
- Recorded decisions are not reopened: `kernel/irq` follows genirq (`ours-kernel-design` `references/task.md:72-91`), the time device layers follow Linux (`task.md:165-167`), page aging is decided and not built (`references/mm.md:54`), the stub rule and the named placeholders (`.agents/tasks/riscv-kernel/PLAN.md`, decisions table). Where an option would change one of them, the option says so.
- `kernel/kernel/task/sched/fair.*` is hands-off; no item touches it.
- No performance work.
- arm: no verify path builds it (`.agents/skills/ours-verify/scripts/boot_check.py:44-48`, `:579`). Items keep it compiling only where that costs nothing.

### Inconsistencies
Each item: what is inconsistent, the evidence, what it costs riscv, and the outstanding repair it overlaps.

- **I1 (naming). Platform seam calls are spelled five ways, and the rate call carries `arch_` in a platform header.** Evidence: the platform seam line of the current map. `platform::remap_isa_irq` is a controller-class call (Zircon's `remap_interrupt`, which every controller implements) named for the ISA bus. riscv cost: a name does not tell a porter which layer defines it; `arch_tick_hz` sends a porter to `kernel/arch/riscv`, though its body belongs to `kernel/platform/riscv`. Repair: None.
- **I2 (naming). `arch_` marks both cross-arch seams and x86-private functions, and x86 or PC functions sit in `ours::` with no `x86_`.** Evidence: x86-private yet named `arch_`: `arch_handle_exception` (`faults.cpp:435`, called only by `exception.S:54`), `time::arch_time_init` (`time/time.cpp:90`, declared in no header), `irq::arch_init_irq` (x86 `irq/init.cpp:4`, no declaration, no caller). Unprefixed x86 or PC names: `apic_*`, `hpet_init` (`ours/arch/hpet.hpp:19`), `time::set_global_clock_event` (`time.cpp:72`), `setup_pit` (`time.cpp:76`). riscv cost: a grep for `arch_` to list riscv's work returns x86-private names, and riscv has no rule for naming its own private functions. Repair: None.
- **I3 (naming). A namespace `ours::arch` exists, and the one translation unit that sees it must write `::arch::`.** Evidence: `kernel/arch/x86/kernel/include/ours/arch/hpet_regs.hpp:23` opens `ours::arch`; that header is included only by x86 `time/hpet.cpp:3` and is the only public header of `//kernel/arch/x86/kernel:headers` (`BUILD.gn:54`). In `hpet.cpp`'s own code only `:70` and `:263` are forced to write `::arch::`. In that same translation unit, the headers it parses after `hpet_regs.hpp` also depend on their `::arch::` inside namespace `ours` (`clang -H` of `hpet.cpp`: `ours/irq/mod.hpp:242`, `:247`, `ours/sync/spin_lock.hpp:98-179`, `ours/mm/types.hpp:22-28`, `ours/mm/page_table_deposits.hpp:44`, `ours/mm/vmas_flags.hpp:13-14`). Every other translation unit never sees `ours::arch`, so the rest of the tree's `::arch::` qualifiers are defensive or style, and their count says nothing about the cause. The conclusion holds: an `ours::arch` declared in a widely included header would capture every unqualified `arch::` inside namespace `ours`, so that naming option is ruled out. riscv cost: none directly; it limits P-name. Repair: None.
- **I4 (naming). The `arch_` file prefix means opposite things.** Evidence: generic declarations in `kernel/include/ours/arch_mp.hpp`, `arch_user_copy.hpp`, `ours/task/concept/arch_thread.hpp`; per-arch files of the same name in each arch in `kernel/arch/x86/mm/include/ours/mm/arch_vm_aspace.hpp`, `kernel/arch/{x86,riscv}/phys/include/ours/phys/arch_{bootmem,handoff,paging}.hpp`, `kernel/arch/{x86,riscv}/lib/arch/include/arch/paging/arch_mmu_flags.hpp`. ### Principles
The first draft's P-driver is folded into P-layer as a sub-question, so a single-board chip gets one answer, and its P-rate is split into three decisions. Each principle: the question, the objects involved, why it matters, the options, a recommendation (not a decision), Zircon's choice, and its Decided field.

#### P-layer: what is arch, what is platform, what is a driver, and where a driver lives
- Question: what decides whether code is arch, platform or a device driver; where does a driver live, who links it and who starts it?
- Objects:
  - The CPU: its instructions, registers, traps, MMU, context switch, per-CPU register, user copy, idle instruction, and the per-CPU devices every implementation of the ISA has (x86's local APIC; on riscv the hart timer, IPI and hart start and stop, reached through SBI firmware calls).
  - The board: which chips sit beside the CPU and how firmware describes them. A PC has ACPI, PIT, HPET, 8259, IO-APIC, COM1 and CF9 reset; QEMU virt has a device tree, a PLIC (or an APLIC with AIA), an ns16550 and SBI reset.
  - A driver: the code for one chip, which may sit on several boards (a 16550 on a PC and on virt).
  - The device-class registries a driver hands its device to: `ClockSource::enroll`, `ClockEventDevice::enroll`, `irq::init_lines(chip)`.
  - `kernel/driver` today: the i8253 only, linked by x86's arch target; `//kernel/driver:init`, an empty group nothing uses.
  - x86 libarch's board-chip register layouts: `ioapic.hpp`, `pic.hpp`, `NUM_ISA_IRQS`.
  - CPU enumeration: the CpuNum-to-APIC-ID map kept by x86 arch (`local_apic.cpp:59-82`) and filled from pc's MADT walk.
  - phys, which has arch seams and no platform layer (I30).
- Why it matters: every riscv file in steps 1b to 10 lands in one of these places; with no rule the porter copies x86, which puts board chips in arch. Whoever links a driver decides which image carries it: the i8253 left riscv's build only when step 1a moved its dependency into x86's arch target.
- Sub-questions: (1) the layer rule, and where the interrupt controller goes; (2) drivers: directory, linker, starter; (3) may libarch hold board-chip register layouts; (4) who owns CPU enumeration and the CpuNum-to-hardware-ID map, and who publishes Possible and Present; (5) does phys get the same split.
- Options for (1) and (2), one package each:
  - (a) Zircon's working rule. Arch is the CPU plus the per-CPU devices every implementation of the ISA has, with the x86 IO-APIC as a named exception (kept where Zircon and Linux keep it; the rule alone would make it a driver). Platform is discovering the board's devices from firmware and the policy over them: which device serves which job, building the line table. Measuring a CPU device's rate belongs to the layer that owns the device, so x86's TSC calibration against the local APIC stays arch. A chip only one board has lives in that platform (`platform/pc` gets the HPET, the PIT line, the 8259 and the i8253); a chip several boards share lives in `kernel/driver/<class>/<chip>`, one `source_set` per chip, linked and started from an init hook by each platform that has it, and enrolled in the existing registries. On riscv: the SBI timer, IPI and HSM in `kernel/arch/riscv`; the PLIC or APLIC and the ns16550 in `kernel/driver`; the device-tree walk in `kernel/platform/riscv`.
  - (a') As (a), with a clause in place of the named exception: arch also holds "the interrupt controller every board of the ISA has". x86's IO-APIC qualifies. On riscv none does (virt offers a PLIC by default and an APLIC with AIA, and boards differ), so the PLIC and APLIC are drivers; AIA's per-hart IMSIC, which the hart reaches through its own CSRs, would be arch.
  - (b) Every chip is a driver in `kernel/driver/<class>/<chip>`, single-board chips included (the i8253 stays; the HPET device half and the 8259 move there); the platform only discovers and wires; the IO-APIC stays arch by named exception.
  - (c) Strict: arch is the CPU only; the local APIC and IO-APIC become drivers too.
  - (d) Linux x86's: arch holds the CPU family and its usual board chips (APIC, HPET, PIT and TSC are all in `arch/x86/kernel`), and platform is a thin ops table.
  - An add-on to any of them: a match table, where each driver declares the firmware identifiers it handles and a generic loop starts whatever the firmware lists (Linux `TIMER_OF_DECLARE`; Zircon's driver configs). It pays off only with several boards per CPU, and ours links one platform per CPU (`kernel_executable.gni:10-14`).
- Options for (3): (i) libarch holds only CPU-architectural registers, and chip layouts move with their chip (`ioapic.hpp` to `kernel/arch/x86/apic`, `pic.hpp` to `platform/pc`, `NUM_ISA_IRQS` beside `ISA_IRQ_*`); (ii) libarch keeps chip layouts, as header-only register definitions phys and host tests can use.
- Options for (4): (i) the platform owns the map, because it reads the firmware that lists CPUs (the MADT, the device tree's `/cpus`), and publishes Possible and Present; arch only asks it for an APIC ID or a hart ID; (ii) arch owns the map and the platform feeds it (x86 today); (iii) phys builds the map into `ArchHandOff` (see P-fw).
- Options for (5): (i) phys stays out of scope: its seams work on both arches and stay as they are; (ii) phys is in scope, with the same rules (board consoles move to a phys platform split).
- Recommendation (not decided): (1) and (2): (a), because it moves exactly what Zircon keeps elsewhere, gives single-board and shared chips one rule each, and leaves the APIC where Zircon and Linux both keep it; the named exception over (a'), because "every board of the ISA has" is a judgement no one can check from the code. (3): (i), as Zircon's lib/arch. (4): (i), because the platform reads the firmware that lists the CPUs. This departs from Zircon, where the platform enumerates (walking the topology phys builds) but arch keeps the CpuNum-to-hardware-ID map: (ii), fed from phys's topology. (5): (i) for now.
- Zircon: (a), applied loosely. LAPIC and IO-APIC in arch (`arch/x86/src/lapic.rs`, `ioapic.rs`); HPET, PIT and 8259 in `platform/pc` (`hpet.rs`, `timer.cc`, `pic.rs`); shared chips in `dev/<class>/<chip>`, started by `platform/<p>/dev-init.cc` from phys's driver configs (`dev/init.cc:13-26`); pc starts its own chips from `LK_INIT_HOOK` (`platform/pc/timer.cc:754`). Exceptions: `arch/x86/BUILD.gn:257` links `platform/pc`, and the riscv64 SBI timer is arch while arm64's generic timer is a `dev/` driver. lib/arch holds no IO-APIC or PIC. Enumeration is the platform's, over the topology phys builds: riscv64's platform walks it and starts each hart by hart ID (`platform/generic-riscv64/platform.cc:174`), and pc's collects the APIC IDs (`platform/pc/platform.cc:203`). The CpuNum-to-hardware-ID map is arch's on both (`CPU_TO_HART_MAP`, `arch/riscv64/src/mp.rs:50`, written at `:214`; `x86_apic_id_to_cpu_num`, `arch/x86/mp.cc:339`).
- Decided: open.

#### P-name: how a seam's name says which layer defines it
- Question: how is a seam named, so that the name tells a porter which layer must define it?
- Objects:
  - Arch seams generic code calls: `arch_mp_*`, `arch_copy_*`, `init_arch_early`.
  - Platform seams: `platform_handle_irq`, `platform_reboot`, `platform::debug_console_write`, `platform::kernel_ioports`, `platform::remap_isa_irq` (a controller-class call named for the ISA bus), `init_platform_early`, `arch_tick_hz`.
  - Arch-private names: `x86_*`, `apic_*`, `hpet_init`, `time::arch_time_init`, `arch_handle_exception`.
  - A query whose implementer varies by board: `time::global_clock_event`.
  - libarch's namespace `::arch`, written about 630 times in the tree, and the existing `ours::arch` (`hpet_regs.hpp:23`), which forces `hpet.cpp:70` and `:263` to write `::arch::`, because inside namespace `ours` the name `arch::` finds `ours::arch` first and stops there.
  - phys's `arch_*` seams in `ours::phys`.
  - Precedent: `references/layering.md` records `ours::syscall::<name>` over a `sys_` prefix, because the namespace already says it (the user's call, 2026-09-28).
- Why it matters: riscv's to-do list is "every name generic code calls that riscv lacks", and five spellings plus `arch_` on x86-private names keep a grep from producing it.
- Options:
  - (a) Prefixes, Zircon's: `arch_*` and `platform_*` free functions in `ours::`, and `x86_*` or `riscv_*` for arch-private names. Cost: the four `platform::` functions and their callers are renamed, and the x86-private `arch_` names.
  - (b) Namespaces everywhere: platform seams in `ours::platform::`, arch-private names in `ours::x86::` or `ours::riscv::`, and arch seams in a namespace that cannot be `ours::arch` (it would capture every unqualified `arch::` inside `ours`). Concrete candidate: `ours::cpu_arch::` (`cpu_arch::send_ipi()`, `cpu_arch::copy_from_user()`, `cpu_arch::init_early()`). A variant frees `ours::arch` by renaming libarch's namespace instead, which touches every `arch::` in the tree. Cost: every arch seam (12 functions in `ours/arch_*.hpp`, plus `start.hpp`, `exception.hpp`, `lockup_detector.hpp`) and every caller renamed.
  - (c) Chosen by collision. Platform seams go in `ours::platform::` (four already do; the syscall precedent). Arch seams keep the `arch_` prefix in `ours::`, because `ours::arch` is off limits. Arch-private names use `ours::x86::` (or `x86_`), never `arch_` or `platform`. A query or state whose implementer differs per board is named by its subsystem (`time::global_clock_event`), and its contract says who defines it. `hpet_regs.hpp`'s `ours::arch` is renamed, and `remap_isa_irq` is named for its class. Real costs: sibling layers follow two conventions (a prefix for arch, a namespace for platform), which a porter learns as a rule rather than reads from one pattern; and the subsystem-named exception gives up the principle's own goal for those names, since `time::global_clock_event` does not say which layer defines it, only its comment does.
- Sub-question: does the rule cover phys's `arch_*` seams, which already work on both arches? Recommendation: no (P-layer (5)).
- Recommendation (not decided): (c): the fewest renames, the recorded namespace-over-prefix precedent wherever it can apply, and its two costs are named above for the user to weigh. If they outweigh it, (a) is the consistent alternative, being Zircon's.
- Zircon: (a). `arch_*` and `platform_*` in the global namespace; `x86_`, `apic_`, `riscv64_` for arch-private names; device-class APIs named by class (`timer_*`, `register_int_handler`, `remap_interrupt`, `power_*`); generic state named by subsystem (`ticks_per_second`).
- Decided: open.

- Decided: open.

- Decided: open.

#### P-complete: how an unported seam fails, and which macro names the architecture
- Question: how does an architecture that has not ported a seam fail, how clear must that failure be, and which macro says which architecture this is?
- Objects:
  - libarch's dispatchers (`arch/<x>.hpp`, ending in `#if ARCH_X86 / #elif ...`) and their failure modes (I16): `#error`; a missing branch, an error at the first user that does not name the seam; an include of a missing file; fallback declarations, which only a build without `ARCH_*` reaches, and no build does today; one late case, `clean_cache_range` at link, whose absence is documented under the stub rule.

  - (c) Either one, plus a conformance source per arch (for example `kernel/arch/<cpu>/kernel/seam_check.cpp`) that `static_assert`s every per-arch type's concept and odr-uses every function declared in `ours/arch_*.hpp` and `ours/platform/*.hpp`, so that the arch's link names every missing body, even one no caller references yet (the C++ form of Zircon's `assert_arch_signatures!`). The user would have to rule that this counts as "the link refers to it", or (c) waits until riscv's arch layer is complete, or it covers only seams generic code already calls.

- Recommendation (not decided): (a), for clearer errors: a one-line change per dispatcher. (c) only after the user rules on its interaction with the stub rule. (b) is cleaner but renames every per-arch libarch file for no more safety than (a). Detection: split by question, with (i) for kernel and phys, which departs from Zircon's usual practice (closer to (ii); see Zircon below).
- Zircon: (b) for lib/arch (`lib/arch/BUILD.gn:15-30`, per-CPU directories with the same file names and a host stub), with `#if` only in `sysreg.h` and `nop.h`, keyed on compiler macros; fixed file names for the kernel's arch headers (`include/arch/ops.h:56`); `assert_arch_signatures!` (`arch/src/api.rs:51`) for the Rust `arch_*` functions, which is (c). Outside lib/arch, Zircon's kernel mostly asks the compiler: 36 non-test sources outside `lib/arch` and `phys` test `__x86_64__` (`vm/pmm.cc:44`), and 7 non-test files test GN's `ARCH_X86` (`arch/x86/BUILD.gn:159`): `lib/syscalls/driver.cc:153`, the process dispatcher's hardware-trace ID and the hypervisor. That is close to detection option (ii).
- Decided: open.

#### P-irq: the call from arch's trap entry to the interrupt controller, and who ends an unclaimed interrupt
- Question: what shape does the call from arch's trap entry to the board's interrupt controller take, and who ends an interrupt nobody claimed?
- Objects:
  - x86's `arch_handle_exception` (`faults.cpp:435-489`): it calls `platform_start_handling_irq` for every vector (`:449`); for a platform vector `platform_handle_irq(gsi)` (`:261`) and, if that answers false, the local APIC EOI itself (`:262`); then `platform_finish_handling_irq` (`:451`).
  - The three pc functions, which only forward, and the vector-valued `HIrqNum` passed to start and finish, which neither reads (I14).
  - The `PlatformIrqMin` + GSI rule, programmed by pc and undone by arch (I14).
  - The recorded genirq rule (`references/task.md:87-91`, the user's call of 2026-10-05): the flow sends the one EOI per vector through the chip after the actions, and arch sends it only for a vector with no line. `kernel/irq` is a deliberate Linux exception modelled on genirq (`task.md:72-80`).
  - riscv: the trap cause says only "supervisor external interrupt"; the hart learns the source by claiming it from the PLIC (a register read) and ends it with a completion write, which under genirq is the chip's EOI. riscv's libarch has no `IrqFrame` yet.
  - Recorded repairs on this path: `docs/repairs/261003/x86-apic.md` #2, `docs/repairs/260926/kernel-task.md` #3.
- Why it matters: step 5 writes riscv's external-interrupt path, and this seam decides whether the claim lives in riscv's trap code or in its platform code. Decide it before step 2 writes riscv's trap vector.
- Options:
  - (a) One platform entry with no number, `platform::handle_irq(frame)`, like Zircon's `platform_irq(frame)`. The platform finds the number itself (x86: the vector from the frame, less its own base; riscv: a PLIC claim). Arch calls `irq::handle_irq_preamble` and `postamble` directly around it. For a claimed line the end stays the chip's under the flow (a PLIC completion is the chip's EOI), which fits genirq. For a vector with no line, the EOI moves from arch to platform: that changes the recorded genirq detail of `task.md:89-91`, and the user must approve it as such.
  - (b) Keep `platform_handle_irq(number, frame)` for controllers that number by vector, and add a claim-style entry for those that number on claim; drop the dead vector parameter of start and finish.
  - (c) genirq's root-handler shape: the root controller's driver installs the function arch calls on an external interrupt (Linux `set_handle_irq`, with the PLIC as the root on riscv), and the platform header has no IRQ function. Weighed by consistency: `kernel/irq` already follows genirq by the user's decision, so (c) carries that exception up to the entry, where (a) follows Zircon at the entry and genirq below it.
- Recommendation (not decided): (a), on the condition that the user approves moving the no-line EOI: one entry fits both controllers, the `PlatformIrqMin` + GSI rule gets a single owner (pc), the forwarders disappear (P-thin), and `HIrqNum` keeps only its GSI meaning. If the user weighs genirq consistency higher, (c).
- Zircon: (a). x86 `exceptions_c.cc:541` calls `platform_irq(frame)`; riscv64 `src/exceptions.rs:628` sends the external interrupt to pdev's `platform_irq` (`dev/pdev/interrupt/interrupt.rs:526`); in both, arch calls `int_handler_start` and `int_handler_finish` itself.
- Decided: open.

#### P-fw: how firmware descriptions reach the code that needs their facts
- Question: how do firmware descriptions (ACPI on a PC, the device tree on virt) reach the code that needs their facts?
- Objects:

### Suggested order
A suggestion, not a decision. Decide P-rate-shape, P-rate-name, P-name and P-decl first: step 1b cannot write riscv's side without them. Then P-type, P-complete, P-only and P-thin. P-irq, P-layer and P-fw can wait until just before steps 2, 3 and 5. The first item to land would be R3: its decision is already pending, it is small, and without it step 1b would define an `arch_tick_hz()` for riscv that a later rename undoes. R1 is not an item here; step 1b only has to avoid copying the kernel-task repair's defect. Then R8 and R9, so `ours/arch/` and the generic declaration headers list exactly what step 1b writes, then R14. Each is introduced to the user one at a time, not as this roadmap.

## Alternatives considered
The options inside each principle are not rejected: they stay open until the user decides. These are the approaches to the work as a whole that this design does not take:

- Leave the seams as they are and let riscv copy x86. Not taken: I10, I13 and I24 show copying spreads defects, and step 1a's review already found a naming departure from Zircon that had not been put to the user.
- Adopt Zircon's layout wholesale in one pass. Not taken: it reverses step 1a's recorded choices and ignores the recorded Linux exceptions (genirq, the time device layers), and one large change breaks the one-change-one-commit rule.
- Let riscv's link errors be the only contract (no principles, fix what the linker reports). Not taken as the approach: it lists only what is already referenced, and fails late; it survives as P-decl (c).
- Fix the overlapping outstanding repairs inside the refactor commits. Not taken: each repair stays its own commit with its own record, so a refactor commit stays behaviour-preserving and checkable by a symbol comparison.
