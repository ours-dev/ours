# directory-capability-step8: a Handler node asks a NodeHandler for content, now or later, and Server::complete ends a request that waited

**Date**: 2026-11-04

## Delivered
Branch `dc-step8`, worktree `.worktrees/dc-step8`, one commit on `5e44458d` (rebased from `4004c35e`, when the baseline moved the protocols to `prot::io`): `feat(ioservice): a handler node answers now or later, and Server::complete ends a pending request`. It is step 8 of the Staging table of `.agents/tasks/directory-capability/DESIGN.md` (decision 7, option C′, the core's half). Host only: the images behave as before, and nothing in `Outgoing`, `LoopServer` or the examples uses it yet.

- **`NodeKind::Handler`** (`system/lib/ioservice`): `Tree::add_handler(parent, name, value)`, `Tree::handler(node)`. `Tree::resolve()` stops at it as at a Subtree node or a remote entry, with the rest of the path (`.` for the node itself); `lookup()` reaches it and not through it; it is listed as a directory and `bind()` refuses it (NotDir).
- **`NodeHandler`**: an abstract class with a protected non-virtual destructor and the design's six operations. `open`, `read`, `read_dirents` and `get_backing_memory` are given a `Ticket` and answer `Answer<R>`, a `std::variant<Done<R>, Pending>` (`Done<R>{R result}`, `Pending{Ticket}`); `R` is a `ustl::Result` of the payload and a `Status` (`OpenResult` with `Opened{ObjectKind, cookie}`, `ReadResult` a span of the handler's bytes, `EntriesResult` with `Entries{dirents, next}`, `VmoResult` a handle). `clone` answers `Result<u64, Status>` and `release` nothing; neither waits. Every call is told the node's `value` first, and `open` also `directory`, the cookie of the directory the Open came on (none for an Open that walked to the node).
- **`Server`**: an optional fourth constructor argument `NodeHandler *`; `Action::Pending`; `Server::complete(Ticket, result, ReplyBuffer &) -> Result<Outcome, Status>` in four overloads, one per operation; `Server::release()` now answers the server end of a pending Open (`Uandle`, Invalid otherwise). The core keeps the protocol: checks 1 to 7 on the connection the Open came on before `open` is called, check 8 the walk to the node, check 9 on the kind the handler reports (shared with the tree's nodes as `judge_directory()` and `judge_file()`), the rights of a Read, ReadDirents and GetBackingMemory before the handler is asked, the seek offset (moves by the bytes of a completed Read only), the dirent phase and cursor (the `.` entry is the core's), and every reply. `release(cookie)` is called once for every cookie the handler made, whichever way the connection ends, pending or not, and for a cookie that never became a connection (check 9 refused it, or the table was full).
- **Tickets**: `Ticket{ConnectionId, serial}`, the serial bumped for every request the handler is asked about. `complete()` refuses with NotFound a ticket whose connection was released or reused, that has nothing pending, or whose serial a later request moved on, and with InvArgs a result of another operation than the request's, changing and writing nothing and taking nothing: a VMO handle in a refused result is the caller's, an `Opened` cookie the handler's. A ticket is good only after the call that got it returned `Pending`. A message for a pending connection is `Drop` (with the held server end in `Outcome::handle`) and releases it.
- **Glue**: one `case Action::Pending` in `LoopServer::handle()`, because the switch must name every action; it releases the connection, closes the held end and answers `Close`, and cannot be reached until step 9 (a `LoopServer` gives its `Server` no handler).
- Tests, README, `docs/changes/261103/ioservice.md` (new), `docs/repairs/261103/ioservice.md` (new, two items).

## Deviations from the design
Where the design is silent or its numbers are off. None changes what the maintainer decided; each is for step 9 or the design text to take up.

- **Every `NodeHandler` call is told the node's value**, not only `open`. The design's table lists the cookie and not the value for `read` and the rest, and says the value tells "the handler which of its trees this is". A `Server` has one handler, so the call must say which node; `Outgoing` (step 9) can be that handler and look its per-node handler up by value, as it looks a service up in `Delegate::connect()`.
- **`open` is also told the cookie of the directory the Open came on.** The table gives it "the rest of the path, the flags". An Open on a directory the handler opened has a path relative to that directory, which only its cookie names, so without the argument a handler's directory could not be opened below. The design says the core passes the cookie "on every call"; this reads it so.
- **The pending state keeps more than "a flag, the serial and the server end".** It also keeps the request's txid, its argument (flags / count / byte limit) and the Handler node an Open walked to: the handler's answer carries none of them and `complete()` needs them. Together with the cookie and the role, that is why a `Connection` is 80 bytes, not the 40 plus four fields the design guessed (repair item 1).
- **`Server::release()` answers a `Uandle`**, and a `Drop` carries one in `Outcome::handle`: the Open's server end the core held, which nobody else could close once its connection is gone. The design speaks of the Drop and the release and not of this handle.
- **A refused `complete()` leaves a cookie to the handler as well as a VMO handle to the caller.** The brief asks for the handle; the same holds for the object an `Opened` names.
- **A ticket is good only after the call that got it has returned `Pending`.** A handler that completes inside its own call gets NotFound and answers `Done` instead. This closes the case step 7 flagged for the glue (a `resume()` inside the callback of the slot being resumed is BadState): the core never lets a completion happen inside the callback that took the request.
- **`Pending` is checked against the ticket the operation was given**; a handler that promises another is answered InternalError and nothing waits.
- **The design's sizes are stale**: a `Node` is 80 bytes (the design says 72), and `Outgoing::Storage` with 32 connections and 32 nodes was 13,320 bytes before this step, where the design says about 12.9 KB and the README said 13,064.
- **`NodeKind::Handler`** shares its spelling with the class `ioservice::Handler` of `outgoing.hpp`. The enumerator is scoped, so nothing clashes, but a reader meets two things called Handler; the design called both names placeholders, and the choice is the maintainer's to change.

## Found along the way
- **`std::visit` and `std::get` cannot be used in this build.** They may throw `bad_variant_access`, and with no exceptions and no RTTI the test binary does not even link (the `typeinfo` of the exception is missing). The core and the tests read an `Answer` with `std::get_if`. This holds for any `ustl::Variant` here.
- **A test that expects a refusal and reads it with `unwrap_err()` traps the whole binary when the call succeeds** (step 3 and step 6 found this too). The new tests read through helpers; the older tests of `tree_test.cpp` and `server_test.cpp` still use `unwrap_err()` and would trap under a mutation that turns their refusal into a success. Not changed.
- Two items for `docs/repairs/261103/ioservice.md`: the size of a `Connection` (item 1) and the second copy a Read makes for a handler that builds its bytes (item 2). No existing repair item was closed or changed: `docs/repairs/261031/ioservice.md` item 1 (the Subtree handler forwarding through a connection of its own) is not helped by a Handler node, which the design says does not need the shared check function.

## For step 9
- **`LoopServer::handle()`**: replace the defensive `case Action::Pending` with `loop::Action::Suspend`, and add the `Server`'s handler: `LoopServer` builds its `Server` with three arguments; it needs a `NodeHandler *` (the constructor, `Memory`, or a setter like `set_delegate()`). `Outgoing` is the natural handler (a private base like `Delegate`) with its per-node table indexed by the node's value, which is why every call carries the value; `HandlerEntry` gains a third pointer and `MAX_PROTOCOLS` limits it with the rest.
- **`LoopServer::watch()` must keep the key `Loop::add()` returns** in the `Binding`; `resume()` needs it.
- **`LoopServer::complete(ticket, result)`**: call `m_server.complete(ticket, result, *reply)`. On NotFound or InvArgs nothing was taken from `result`: the handler still owns a VMO handle or an `Opened` cookie and must close or release it (the glue should say so, or return the status). On an accepted Outcome, write it on the channel of `ticket.connection` (`Server::channel()`), then `resume(key)` that connection's slot, in that order. The Outcomes it can return: `Reply` (write; a failed write is `write_failed()` and no release, the connection is released by its own callback after the `resume`), `Bind` (a pending Open or Clone: `watch(outcome.handle, outcome.connection)`, which already releases the connection and leaves the channel to the caller on failure; then answer the epitaph and close the end as `handle()` does), `Refuse` (write the epitaph on `outcome.handle` and close it; **there is no path, so `open_refused()` cannot be called for a completed refusal**), and `Drop` (only if even a status reply could not be built; the connection is already released by the core, so it must be `resume`d for its own callback to see a stale id and answer `Close`).
- **`Drop` now carries a handle.** `handle()`'s `Drop` case closes the message's handles; it must close `outcome.handle` too when valid (a pending Open's server end, from a message that came for a pending connection).
- **The case step 7 warned of cannot arise from the core**: a completion inside the call that got the ticket is refused (NotFound), so `complete()` never runs inside the Binding callback of the connection it completes. A completion from another Binding's callback (a sibling slot) or from a Waiter of the handler's own is the normal case. `resume()` answering BadState is still worth treating as "the Binding is running" and answering `Rearm`, as step 7 suggests, but the core now makes it a bug of the handler.
- **`rest`/`path` views the request buffer**: a handler that answers Pending and needs the path copies it (documented on `NodeHandler::open`).
- **A pending Open suspends the directory connection it came on**; S is made into a connection (or refused with an epitaph) at completion, so the table needs the room then, not at the Open. A full table at completion is a `Refuse` with NoResource and the cookie released.
- **The size of a connection** is 80 bytes and the program's Loop table follows `MAX_CONNECTIONS` (repair item 1 of `docs/repairs/261103/ioservice.md`): `examples/files` adds a second `LoopServer` for its handler tree, and its `static_assert` against the port's 1,024 observers moves with every constant.
- **A handler node at a declared path** is `Tree::add_handler(parent, name, value)` after `make_parents()`, under the rules of `add_directory(path)` and `add_subtree(path, handler)` (`judge()` for the path, the overlap and the table): the pattern of step 6, with a third kind of node in `Storage::directories` and a third pointer in the table.
