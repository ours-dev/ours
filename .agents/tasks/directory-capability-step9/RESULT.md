## Delivered

It is step 9 of 9 of the Staging table of `.agents/tasks/directory-capability/DESIGN.md` (decision 7, option C′, the glue and the first use):

- **`LoopServer` glue** (`system/lib/ioservice`). `Action::Pending` makes the `Binding` answer `loop::Action::Suspend`; the `Binding` keeps the key `Loop::add()` answers (`m_key`); `LoopServer::complete(ticket, result)`, four overloads as the core's, calls `Server::complete()`, carries out the `Outcome` (a `Reply` is written on the connection's channel and a failed write goes to `write_failed()`; a `Bind` of a granted pending Open becomes a connection on the held server end and gets a slot; a `Refuse` is an epitaph on that end, closed), and then `Loop::resume`s the slot, in that order. It never releases the connection: it is released by its own callback after the resume, `release(cookie)` once. `Drop` closes the handle it carries, and so does every release (a private `LoopServer::release()`). The `LoopServer` passes the program's `NodeHandler` to its `Server`. Final shape: `auto complete(Ticket, OpenResult const &) -> ours::Status` (and `ReadResult`, `EntriesResult`, `VmoResult`): Ok when the Server took the result; NotFound or InvArgs as the Server refuses, with nothing written and nothing taken; BadState or NotFound from the resume when the slot was not suspended (a bug of the program).
- **`Outgoing::add_handler(path, handler, value = 0) -> Result<NodeId, Status>`** in the way of `add_subtree`: the same path refusals (InvArgs, AlreadyExists by segments across directories, Subtree nodes and Handler nodes, NoResource judged before anything is made), the handler in the same table (`MAX_PROTOCOLS` = 8 limits protocols, service nodes, Subtree nodes and Handler nodes together: said in the header and the README). `Outgoing` forwards `complete()` with four overloads and is itself the `LoopServer`'s `NodeHandler` (a second private base beside `Delegate`), translating the table index to the handler and the `value` it was registered with.
- **`examples/files`** serves `slow` at `/export/slow` through a Handler node: `SlowDocs` opens a directory and one file, `slow.txt` (`"slow hello\n"`), and answers a Read `Pending`; it writes the request on a channel pair of its own and a Loop slot on the other end ends it two turns later with `Outgoing::complete()`. New manifest declaration and expose, a root.cm offer, a routing_checks use. The existing `/files` cases pass unchanged.
- **routing_checks** (`check_slow()`, before the cases that end `files`): the directory and its refusals; the slow file read while a Read of another connection is answered; two Reads back to back, two replies in order, the second beginning where the first ended; a Read written and the channel closed at once, 40 times, after which a normal read of the slow file is answered.
- 38 host tests (17 in `loop_server_test.cpp`, 21 in `outgoing_test.cpp`), the ioservice README, change records `docs/changes/261103/{ioservice,examples-files,routing-checks}.md`, repair items (`docs/repairs/261103/ioservice.md` item 1 gains the two sizes, `docs/repairs/261103/routing-checks.md` item 2 is new).

## Deviations from the design
Where the design is silent or off. None changes what the maintainer decided; each is for the design text or the maintainer to take up.

- **The delay is two turns, not one.** The design says the slot "completes the ticket when it fires, a Loop turn later". With one turn, a `Binding` that answers `Rearm` instead of `Suspend` passed the whole target boot: the wake message is posted while the connection's callback is still running, so its packet is queued before the connection's own packet for the next message, the Read is ended first and nothing shows that the connection was read while it waited (the only trace was a `BadState` log line from `files`, which I reproduced). `SLOW_TURNS` = 2 puts the connection's packet between the two firings. The design's sentence "the Loop turn later" should say "a few turns, and why".
- **A completion inside the Binding's own callback cannot happen, so the `Binding` has no `Rearm` branch.** Step 7 asked for the case to be handled and tested, conditional on `complete()` being able to run there. Step 8's rule (a ticket is good only after the call that got it has returned `Pending`) makes it impossible: nothing runs between that return and the `Binding`'s own. A test pins the refusal (`ACompletionInsideTheCallThatGotTheTicketIsRefusedAndTheConnectionIsServed`: the handler gets NotFound, answers `Done`, and the connection is served); a second pins what can happen, a resume by someone else (`CompleteSaysWhenTheSlotWasNotSuspended`: the reply is written and `complete()` answers BadState). A flag and a `Rearm` branch would be code no test could reach.
- **`add_handler(path, handler, value = 0)` has a third parameter.** The design says the node "holds a value that tells the handler which of its trees this is" and step 8 made every `NodeHandler` call carry it; `Outgoing`'s own table index is not a number to show a program. The value is kept beside the handler.
- **`Outgoing` is a `NodeHandler` through a second private base.** The design does not say how the `Outgoing` becomes the `Server`'s handler; step 8's note suggested "a private base like `Delegate`". It is the implementation of an interface the `Server` requires (the same class is already the `LoopServer`'s `Delegate`), not a new hierarchy, but CLAUDE.md asks for a question before a base class: the alternative is a nested private helper class holding the table, which moves the six overrides and changes nothing else. I did not stop for it; say if you prefer the helper.
- **The example keeps no table of pending requests.** The design's example notes the ticket in "a table of its own, indexed by the connection index". `SlowDocs` writes the request into the message (ticket, offset, count, turns left), so the slot that ends it needs no state.
- **`LoopServer::complete()` returns a `Status`** (the design says the glue "calls `Server::complete`, writes the reply ... and `resume`s"): Ok / the Server's refusals / BadState or NotFound of the resume. The design does not say what the handler is told.
- **A `Binding` is 32 bytes** (the key), a table entry 32: the design's cost estimates do not include them.
- **The brief's routing_checks counts were stale** (above).

## The distance to "basically usable" for the whole feature
Covered by tests now: the language and the compiled format (steps 1 and 2), the route and its rights hops (1), `Outgoing::add_directory` (3), the root's `forward_directory()` on the target (4: read, list, rights shrink, subdir, the two widened offers, the unserved path, `NotDir`), the provider exit (5), the Subtree node (6), the Loop's Suspend and resume on the host and in the shell's `check_loop()` (7), the core's handler node (8), and the glue, `add_handler` and the slow directory (9, host and target).

What the design's Testing list covers that is not tested anywhere:
- `LoopServer::complete()` for `EntriesResult` and `VmoResult`, and a pending `read_dirents` or `get_backing_memory` end to end (the fake handlers answer those at once; the core's tests cover what each overload builds, and `finish()` is shared).
- A pending Open on the target (the example's Open answers at once), and a Handler node under a consumer entry opened by `fsio::export_namespace()` clones (a Clone of a handled connection is tested on the host only).
- The design's "Not verifiable yet": the provider that dies in the window of the fifth row, a restarted provider, the 64-message queue overflowing, a filesystem on a disk, a file's VMO from a provider that serves from a disk, an executable from a provider.
- No test of a handler whose wait never ends (no timeout, by design) and none of a `Binding` table smaller than the connection table with a pending request.
- A filesystem: nothing exercises the handler interface with a real tree of its own, cookies for many objects, or a Clone that has to wait.
