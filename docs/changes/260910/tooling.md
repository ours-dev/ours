# tooling —— 改动记录（2026-09-10）

## `tools/set.py` 在 macOS 自带的 Python 3.9 上根本跑不起来（2026-09-10）

**文件**
- `tools/set.py` —— 加 `from __future__ import annotations`

**症状**
配置构建目录的那条文档化入口，一行自己的代码都没执行就崩了：

```
$ python3 tools/set.py --list
Traceback (most recent call last):
  File ".../tools/set.py", line 68, in <module>
    def _clang_tool_dir() -> str | None:
TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'
```

`--list`、`bringup.x86`、任何参数，全都一样——错误发生在 import 期。

**原因**
`str | None` 是 PEP 604，**3.10 才有**。函数注解在没有
`from __future__ import annotations` 时是**定义期求值**的，所以模块一被加载，
`str.__or__(None)` 就抛 TypeError；函数体是否被调用无关紧要。

而 macOS 至今把 3.9 作为 `python3`（本机 `Python 3.9.6`）。文件里同时用到的
`list[str]` / `tuple[str, str]` 反而没事——PEP 585 在 3.9 就落地了——所以只有 `| None`
那三处触发，也因此更容易被忽略：文件看起来"用了新语法但没那么新"。

这不是理论问题：`scripts/qemu-debug.sh` 在构建目录不存在时给出的下一步就是
`tools/set.py <产品>.<架构>`，照着敲会直接吃到这个 traceback。

**改法**
把注解变成惰性求值，一行：

```python
# 改前
import argparse

# 改后
# PEP 604 annotations (`str | None`) are evaluated at definition time without
# this, and macOS still ships Python 3.9 as `python3` ...
from __future__ import annotations

import argparse
```

注解本身一个字没改。被否掉的方案是把 `str | None` 改写成 `Optional[str]`：那要改三处、
引入 `typing` 依赖，并且把代码往回写；`from __future__ import annotations` 是同一件事的
一行版本，而且对以后新写的注解同样有效。

**参照**
CPython PEP 563（`from __future__ import annotations`）与 PEP 604（`X | Y`）。

**验证**
```
$ python3 --version
Python 3.9.6
$ python3 tools/set.py --list
Products:  bringup
Arches:    x86 arm riscv
$ python3 tools/set.py bringup.x86
Generated .../out/bringup.x86/args.gn  (product=bringup, cpu=x86, triple=x86_64-elf, ...)
Running: .../prebuilt/gn/gn gen .../out/bringup.x86 --export-rust-project
Build:   ninja -C .../out/bringup.x86 //products/bringup:bringup
```
`ast.parse` 也过。

**故意没做**
- **没有给仓库定一个最低 Python 版本**。该定，但那要连 `tools/` 下其它脚本一起看，
  是另一件事。这里只让这个文件在实际会遇到的解释器上能跑。

## 调试菜单改成生成的，新增 kernel_image / kernel_package 不再被静默吞掉（2026-09-10）

**文件**
- `tools/gen_debug_menu.py` —— 新建，从源码树生成三个下拉框的选项
- `tools/set.py` —— `gn gen` 成功后顺手刷新菜单
- `scripts/qemu-debug.sh` —— 三种"镜像长出来了"的情况改成明确报错
- `ours.code-workspace` —— `inputs` 改成生成区（前后加哨兵注释）
- `docs/development/debugging.md` —— 新增「新增了一个 kernel_image / kernel_package 会怎样」

**症状**
问"新增一个 `kernel_image` 或 `kernel_package` 会怎样"，答案是三件坏事，全部实测确认过
（用构造出来的清单目录跑 `OUT=... ./scripts/qemu-debug.sh`）：

| 情况 | 改前的行为 |
|---|---|
| 同一产品里两个镜像共用一个 switchset | **静默挑一个**（字典赋值覆盖），`-> two` |
| 新镜像不属于任何产品 | **静默看不见**，错误信息里也不提它存在 |
| 一个镜像里有两个 kernel 环境的 ELF | **整个镜像被 `continue` 跳过**，然后报"这个目录里没有属于产品的镜像，ninja 跑了吗" |

第三条最恶劣：它把"你刚改的东西让内核无法识别"说成了"你没构建"。

菜单那一侧另有一个问题：三个列表是手写的，于是它们**已经是错的**——树里有
`build/switch/set/dbg.2`，`tools/set.py` 认识 `riscv`，两者菜单里都没有。

**原因**
两个不同的根因。

脚本这侧，收集循环把"不认识"和"不存在"混为一谈：

```python
    kernels = [r for r in records if r.get("environment") == "kernel"]
    if identity is None or len(kernels) != 1:
        continue                      # ← 分不清就当没有
    if identity["label"] not in owned:
        continue                      # ← 不属于产品就当没有
    ...
    candidates[switchset] = (identity, kernels[0])   # ← 撞了就覆盖
```

`continue` 和字典覆盖都是"少写一个分支"换来的，代价是**把人刚做的改动变成沉默**。

菜单那侧，根因是"VS Code 不能动态算选项"被当成了"所以只能手写"。不能动态算是真的
（`pickString.options` 是静态数组，`"type":"command"` 只能返回字符串，没有能跑 shell 的
内建命令），但**生成一次写进文件**是完全可行的第三条路，而且三层的来源全在源码树里，
根本不需要构建目录。

**改法**

脚本这侧，三处沉默各换成一句话。撞 switchset：

```python
# 改前
candidates[got] = (identity, kernels[0])

# 改后
if got in where:
    where[got] = ("AMBIGUOUS", where[got], (identity, kernels[0]))
else:
    where[got] = (identity, kernels[0])
```

不属于产品的镜像不再丢掉，而是收进 `foreign`，在"没有这个 switchset"时点名：

```
qemu-debug: product 'bringup' has no image built in switchset 'dbg.1'
qemu-debug: it offers: dbg.0 (one)
qemu-debug: note: newbie is built in 'dbg.1' but belongs to no product
```

内核数不为 1 的镜像收进 `broken`，并说清楚这通常是什么造成的：

```
qemu-debug:   one: 2 ELFs in the kernel environment -- //k:a(...), //k:b(...)
qemu-debug: a bootable image is expected to carry exactly one kernel; a second kernel_package would do this
```

菜单这侧，`tools/gen_debug_menu.py` 从树里读三层：

| 层 | 来源 |
|---|---|
| 产品 | `products/*.gni`（复用 `set.py` 的 `list_products()`） |
| 架构 | `set.py` 的 `VALID_CPUS` |
| switchset | `build/switch/set/*/BUILD.gn` 里实例化了 `kernel_switchset` 的目录 |

switchset 是**筛**不是 glob：同目录下还有 `phys.dbg_0`，判据取"这个目录实例化的是
`kernel_switchset` 还是 `phys_switchset`"，和 GN 自己的判据一致。

工作区文件里 `inputs` 变成哨兵包住的生成区：

```jsonc
        // BEGIN generated by tools/gen_debug_menu.py -- do not edit by hand
        "inputs": [ ... ]
        // END generated by tools/gen_debug_menu.py
```

哨兵之上那段解释性注释（为什么 inputs 归 tasks、为什么 label 不能重复 value）仍是手写的，
生成器不碰。

`tools/set.py` 在 `gn gen` 成功后调用它，**失败不致命**——这是给一个已经成功的 configure
加的便利，为了菜单让配置步骤失败是本末倒置。

被否掉的方案：**从 `out/` 目录生成菜单**。看起来更"准"，实则更差——一个构建目录只知道
自己被配置成的那一个产品和架构，用它生成会把菜单缩成"上次配了什么"。菜单是"可以问什么"
的列表；某个具体组合存不存在是脚本的事，而它答不上来时会把真的有的列出来。

**参照**
无，本项目自有设计。

**验证**
1. 三种增长情况各构造一个清单目录实测，输出见上；改前的行为也各自复现过一遍
   （`-> two`、看不见、"ninja 跑了吗"）。
2. 生成器：首次改写 → `products: bringup; arches: x86 arm riscv; switchsets: dbg.0 dbg.1 dbg.2`；
   再跑 → `is up to date`，不写文件；`--check` 退出码 0。
3. **端到端自适应**：临时建一个 `build/switch/set/probe.9/BUILD.gn`（`kernel_switchset`），
   跑 `tools/set.py bringup.x86` →
   `gen_debug_menu: rewrote ... switchsets: dbg.0 dbg.1 dbg.2 probe.9`，菜单里出现
   `probe.9`；脚本对它答 `product 'bringup' has no image built in switchset 'probe.9'`；
   删掉目录再跑一次，菜单回到三项。
4. 菜单现在比手写版多了 `riscv` 和 `dbg.2`——两个树里有、手写版漏掉的。
5. 工作区文件去注释后 `json.loads` 通过，`settings` 5 个键、2 个 launch 配置原样。
6. `ninja` 全绿；两个 switchset 各启动 + attach 一次，断点地址与之前一致
   （`0xffffff88400890a9` / `0xffffff88400760a9`）。
7. **仍然没在 VS Code 里点过三个框**：窗口在另一个全屏 Space。

**故意没做**
- **没有让第三层支持按镜像名选**。撞 switchset 时脚本建议"给其中一个单独的 switchset，
  或者按镜像名选"，但第二条路还没实现——等真出现两个镜像共用一个 switchset 再说，
  现在加等于为一个假想的形状设计接口。
- **没有把 `DESCRIPTIONS` 也生成掉**。那张表把值翻译成人话（`dbg.0` → "asserts compiled
  out, unit tests linked in"），推不出来，只能人写。缺一条不报错，选项就只显示值本身——
  对一个还没人描述过的新名字，这是对的结果，不该卡住生成器。
- **没有给仓库定最低 Python 版本**（见上一节）。

## 启动/调试脚本从 sh 换成 Python（2026-09-10）

**文件**
- `scripts/qemu_boot.py` —— 新建，取代 `scripts/qemu-boot.sh`（删除）
- `scripts/qemu_debug.py` —— 新建，取代 `scripts/qemu-debug.sh`（删除）
- `ours.code-workspace`、`tools/gen_debug_menu.py`、`docs/development/debugging.md`、
  `docs/repairs/260909/products.md` —— 引用改名

**症状**
不是 bug，是规矩：**这个仓库的工具脚本一律用 Python，不用 shell**。

但这两个文件也确实到了 shell 的边界。`qemu-debug.sh` 里已经内嵌了两段 python heredoc
（解析清单、轮询端口），也就是说它早就不是 shell 脚本，而是"一个 shell 壳子包着 Python"——
再加一个分支就要再开一段 heredoc。`qemu-boot.sh` 的 NUMA 分支则在用字符串拼参数
（`NUMA_ARGS="$NUMA_ARGS -object ..."`），配一句 `# shellcheck disable=SC2086` 才敢展开。

**原因**
shell 在两个地方按次数收费，而这两个脚本都已经付了很多次：

1. **没有列表**。`NUMA_ARGS` 是一个字符串，靠不加引号展开成多个参数，于是任何一个含空格的
   值都会静默变成两个参数。Python 里就是 `list[str]`，`subprocess` 直接收。
2. **没有结构化数据**。读一份 JSON 清单要 heredoc 出一个 python，结果再用 `sed -n 1p`
   一行行切回来——两次序列化，只为跨过语言边界。

**改法**

清单解析从"嵌在 shell 里的 python"变成普通函数。改前：

```sh
_resolved=$(ROOT="$ROOT" OUT="$OUT" ... python3 <<'RESOLVE'
import glob, json, os, sys
...
print(os.path.join(out, identity["obi"]))
print(os.path.join(out, kernel["debug"]))
print(identity["image"])
RESOLVE
) || exit $?

IMAGE=$(printf '%s\n' "$_resolved" | sed -n 1p)
ELF=$(printf '%s\n' "$_resolved" | sed -n 2p)
```

改后就是一次调用：

```python
image, elf, name = resolve(out, args.product, args.arch, args.switchset)
```

NUMA 参数从字符串拼接变成列表：

```sh
# 改前
NUMA_ARGS=""
for id in 0 1 2 3; do
    NUMA_ARGS="$NUMA_ARGS -object memory-backend-ram,size=${NODE_MEM}M,id=m$id"
done
...
# shellcheck disable=SC2086
exec "$ROOT/prebuilt/qemu/bin/qemu-system-x86_64" ... $NUMA_ARGS ...
```

```python
# 改后
for node, _ in NUMA_NODES:
    args += ["-object", f"memory-backend-ram,size={node_mem}M,id=m{node}"]
```

距离矩阵也从"写死十二行 `-numa dist,src=...`（注释说因为循环会吃掉调用者的参数）"变成一张
数据表 `NUMA_DISTANCES`，而调用者的参数就是 `argv`，不再有冲突。

几处行为刻意保持一致：

- **`qemu_boot.py` 结尾用 `os.execve`**，和 `exec` 一样把自己换成 QEMU。调用方
  （`qemu_debug.py`、VS Code 的任务终端）是朝它启动的那个 pid 发信号的，中间多一层还活着
  的进程会把信号吃掉。
- **`qemu_debug.py` 的清理**从 `trap cleanup EXIT INT TERM` 变成 `atexit` + `signal`，
  语义相同：VS Code 的 stop 任务发 SIGTERM，QEMU 必须跟着走。
- **环境变量接口没变**：`OUT`、`IMAGE`、`ELF`、`WORK`、`PORT`、`SMP`、`MEM`、`CPU`、`NUMA`
  都还在，命令行位置参数也还是 `<产品> <架构> <switchset>`。

文件名用下划线（`qemu_debug.py` 而不是 `qemu-debug.py`）——仓库既有约定，而且带连字符的
Python 文件没法被 import。

**参照**
无，本项目自有约定。

**验证**
1. `qemu_boot.py` 单独启动 dbg.1 镜像，跑到用户态、四个 CPU 都在跑线程，
   `terminating on signal 15`（不是三重错）：

   ```
   [info] handoff: jumping to kernel at 0xFFFFFF88400485AD, cr3=0x1FEDB000
   [... cpu0 info] userboot: kernel package holds 5 files
   [... cpu2 debug] I'm Thread 1
   [... cpu3 debug] I'm Thread 2
   ```
2. `qemu_debug.py` 两个 switchset 各启动 + attach 一次，断点地址与 sh 版**完全相同**
   （`0xffffff88400890a9` / `0xffffff88400760a9`）。
3. 七条错误路径逐条对照 sh 版输出，**逐字相同**：未知 switchset、未配置的架构、
   半个 IMAGE/ELF 覆盖、以及三种"镜像长出来了"的情况（撞 switchset / 不属于产品 /
   两个内核 ELF）。
4. SIGTERM 清理：起来之后 `kill` 掉脚本，QEMU 进程和 1234 端口都干净。
5. `tools/gen_debug_menu.py --check` 通过（工作区里的任务命令已指向 `.py`）。
6. 全仓已无指向这两个脚本的活引用；`docs/changes/` 和 `.agents/tasks/` 里的旧引用**保持
   原样**——那是历史记录，按约定只增不改。

**故意没做**
- **没有动其余四个 `.sh`**：`build/toolchain/copy_command.sh`（GN 的 copy 工具命令，每个
  copy action 都走它）、`docker/entrypoint.sh`、`kernel/lib/code_patching/tests/run_tests.sh`、
  `.agents/skills/vendor-import/scripts/vendor-clone.sh`。它们分属别的模块，而这个 worktree
  同时有其它会话在写；一次扫掉四个跨模块文件、又没法像这两个一样用"真启动一次"验证，
  风险不对等。`system/lib/boost.intrusive/.drone/drone.sh` 是 vendored 的第三方文件，
  不在范围内。
