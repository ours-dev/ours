# tooling —— 改动记录（2026-09-10）

## `tools/set.py` 在 macOS 自带的 Python 3.9 上根本跑不起来（2026-09-10）

**文件**
- `tools/set.py` —— 加 `from __future__ import annotations`

**症状**
配置构建目录的那条文档化入口，一行自己的代码都没执行就崩了：

```
$ python3 tools/set.py --list
Traceback (most recent call last):
  File ".../tools/set.py", line 68, in <module>
    def _clang_tool_dir() -> str | None:
TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'
```

`--list`、`bringup.x86`、任何参数，全都一样——错误发生在 import 期。

**原因**
`str | None` 是 PEP 604，**3.10 才有**。函数注解在没有
`from __future__ import annotations` 时是**定义期求值**的，所以模块一被加载，
`str.__or__(None)` 就抛 TypeError；函数体是否被调用无关紧要。

而 macOS 至今把 3.9 作为 `python3`（本机 `Python 3.9.6`）。文件里同时用到的
`list[str]` / `tuple[str, str]` 反而没事——PEP 585 在 3.9 就落地了——所以只有 `| None`
那三处触发，也因此更容易被忽略：文件看起来"用了新语法但没那么新"。

这不是理论问题：`scripts/qemu-debug.sh` 在构建目录不存在时给出的下一步就是
`tools/set.py <产品>.<架构>`，照着敲会直接吃到这个 traceback。

**改法**
把注解变成惰性求值，一行：

```python
# 改前
import argparse

# 改后
# PEP 604 annotations (`str | None`) are evaluated at definition time without
# this, and macOS still ships Python 3.9 as `python3` ...
from __future__ import annotations

import argparse
```

注解本身一个字没改。被否掉的方案是把 `str | None` 改写成 `Optional[str]`：那要改三处、
引入 `typing` 依赖，并且把代码往回写；`from __future__ import annotations` 是同一件事的
一行版本，而且对以后新写的注解同样有效。

**参照**
CPython PEP 563（`from __future__ import annotations`）与 PEP 604（`X | Y`）。

**验证**
```
$ python3 --version
Python 3.9.6
$ python3 tools/set.py --list
Products:  bringup
Arches:    x86 arm riscv
$ python3 tools/set.py bringup.x86
Generated .../out/bringup.x86/args.gn  (product=bringup, cpu=x86, triple=x86_64-elf, ...)
Running: .../prebuilt/gn/gn gen .../out/bringup.x86 --export-rust-project
Build:   ninja -C .../out/bringup.x86 //products/bringup:bringup
```
`ast.parse` 也过。

**故意没做**
- **没有给仓库定一个最低 Python 版本**。该定，但那要连 `tools/` 下其它脚本一起看，
  是另一件事。这里只让这个文件在实际会遇到的解释器上能跑。

## 调试菜单改成生成的，新增 kernel_image / kernel_package 不再被静默吞掉（2026-09-10）

**文件**
- `tools/gen_debug_menu.py` —— 新建，从源码树生成三个下拉框的选项
- `tools/set.py` —— `gn gen` 成功后顺手刷新菜单
- `scripts/qemu-debug.sh` —— 三种"镜像长出来了"的情况改成明确报错
- `ours.code-workspace` —— `inputs` 改成生成区（前后加哨兵注释）
- `docs/development/debugging.md` —— 新增「新增了一个 kernel_image / kernel_package 会怎样」

**症状**
问"新增一个 `kernel_image` 或 `kernel_package` 会怎样"，答案是三件坏事，全部实测确认过
（用构造出来的清单目录跑 `OUT=... ./scripts/qemu-debug.sh`）：

| 情况 | 改前的行为 |
|---|---|
| 同一产品里两个镜像共用一个 switchset | **静默挑一个**（字典赋值覆盖），`-> two` |
| 新镜像不属于任何产品 | **静默看不见**，错误信息里也不提它存在 |
| 一个镜像里有两个 kernel 环境的 ELF | **整个镜像被 `continue` 跳过**，然后报"这个目录里没有属于产品的镜像，ninja 跑了吗" |

第三条最恶劣：它把"你刚改的东西让内核无法识别"说成了"你没构建"。

菜单那一侧另有一个问题：三个列表是手写的，于是它们**已经是错的**——树里有
`build/switch/set/dbg.2`，`tools/set.py` 认识 `riscv`，两者菜单里都没有。

**原因**
两个不同的根因。

脚本这侧，收集循环把"不认识"和"不存在"混为一谈：

```python
    kernels = [r for r in records if r.get("environment") == "kernel"]
    if identity is None or len(kernels) != 1:
        continue                      # ← 分不清就当没有
    if identity["label"] not in owned:
        continue                      # ← 不属于产品就当没有
    ...
    candidates[switchset] = (identity, kernels[0])   # ← 撞了就覆盖
```

`continue` 和字典覆盖都是"少写一个分支"换来的，代价是**把人刚做的改动变成沉默**。

菜单那侧，根因是"VS Code 不能动态算选项"被当成了"所以只能手写"。不能动态算是真的
（`pickString.options` 是静态数组，`"type":"command"` 只能返回字符串，没有能跑 shell 的
内建命令），但**生成一次写进文件**是完全可行的第三条路，而且三层的来源全在源码树里，
根本不需要构建目录。

**改法**

脚本这侧，三处沉默各换成一句话。撞 switchset：

```python
# 改前
candidates[got] = (identity, kernels[0])

# 改后
if got in where:
    where[got] = ("AMBIGUOUS", where[got], (identity, kernels[0]))
else:
    where[got] = (identity, kernels[0])
```

不属于产品的镜像不再丢掉，而是收进 `foreign`，在"没有这个 switchset"时点名：

```
qemu-debug: product 'bringup' has no image built in switchset 'dbg.1'
qemu-debug: it offers: dbg.0 (one)
qemu-debug: note: newbie is built in 'dbg.1' but belongs to no product
```

内核数不为 1 的镜像收进 `broken`，并说清楚这通常是什么造成的：

```
qemu-debug:   one: 2 ELFs in the kernel environment -- //k:a(...), //k:b(...)
qemu-debug: a bootable image is expected to carry exactly one kernel; a second kernel_package would do this
```

菜单这侧，`tools/gen_debug_menu.py` 从树里读三层：

| 层 | 来源 |
|---|---|
| 产品 | `products/*.gni`（复用 `set.py` 的 `list_products()`） |
| 架构 | `set.py` 的 `VALID_CPUS` |
| switchset | `build/switch/set/*/BUILD.gn` 里实例化了 `kernel_switchset` 的目录 |

switchset 是**筛**不是 glob：同目录下还有 `phys.dbg_0`，判据取"这个目录实例化的是
`kernel_switchset` 还是 `phys_switchset`"，和 GN 自己的判据一致。

工作区文件里 `inputs` 变成哨兵包住的生成区：

```jsonc
        // BEGIN generated by tools/gen_debug_menu.py -- do not edit by hand
        "inputs": [ ... ]
        // END generated by tools/gen_debug_menu.py
```

哨兵之上那段解释性注释（为什么 inputs 归 tasks、为什么 label 不能重复 value）仍是手写的，
生成器不碰。

`tools/set.py` 在 `gn gen` 成功后调用它，**失败不致命**——这是给一个已经成功的 configure
加的便利，为了菜单让配置步骤失败是本末倒置。

被否掉的方案：**从 `out/` 目录生成菜单**。看起来更"准"，实则更差——一个构建目录只知道
自己被配置成的那一个产品和架构，用它生成会把菜单缩成"上次配了什么"。菜单是"可以问什么"
的列表；某个具体组合存不存在是脚本的事，而它答不上来时会把真的有的列出来。

**参照**
无，本项目自有设计。

**验证**
1. 三种增长情况各构造一个清单目录实测，输出见上；改前的行为也各自复现过一遍
   （`-> two`、看不见、"ninja 跑了吗"）。
2. 生成器：首次改写 → `products: bringup; arches: x86 arm riscv; switchsets: dbg.0 dbg.1 dbg.2`；
   再跑 → `is up to date`，不写文件；`--check` 退出码 0。
3. **端到端自适应**：临时建一个 `build/switch/set/probe.9/BUILD.gn`（`kernel_switchset`），
   跑 `tools/set.py bringup.x86` →
   `gen_debug_menu: rewrote ... switchsets: dbg.0 dbg.1 dbg.2 probe.9`，菜单里出现
   `probe.9`；脚本对它答 `product 'bringup' has no image built in switchset 'probe.9'`；
   删掉目录再跑一次，菜单回到三项。
4. 菜单现在比手写版多了 `riscv` 和 `dbg.2`——两个树里有、手写版漏掉的。
5. 工作区文件去注释后 `json.loads` 通过，`settings` 5 个键、2 个 launch 配置原样。
6. `ninja` 全绿；两个 switchset 各启动 + attach 一次，断点地址与之前一致
   （`0xffffff88400890a9` / `0xffffff88400760a9`）。
7. **仍然没在 VS Code 里点过三个框**：窗口在另一个全屏 Space。

**故意没做**
- **没有让第三层支持按镜像名选**。撞 switchset 时脚本建议"给其中一个单独的 switchset，
  或者按镜像名选"，但第二条路还没实现——等真出现两个镜像共用一个 switchset 再说，
  现在加等于为一个假想的形状设计接口。
- **没有把 `DESCRIPTIONS` 也生成掉**。那张表把值翻译成人话（`dbg.0` → "asserts compiled
  out, unit tests linked in"），推不出来，只能人写。缺一条不报错，选项就只显示值本身——
  对一个还没人描述过的新名字，这是对的结果，不该卡住生成器。
- **没有给仓库定最低 Python 版本**（见上一节）。

## 启动/调试脚本从 sh 换成 Python（2026-09-10）

**文件**
- `scripts/qemu_boot.py` —— 新建，取代 `scripts/qemu-boot.sh`（删除）
- `scripts/qemu_debug.py` —— 新建，取代 `scripts/qemu-debug.sh`（删除）
- `ours.code-workspace`、`tools/gen_debug_menu.py`、`docs/development/debugging.md`、
  `docs/repairs/260909/products.md` —— 引用改名

**症状**
不是 bug，是规矩：**这个仓库的工具脚本一律用 Python，不用 shell**。

但这两个文件也确实到了 shell 的边界。`qemu-debug.sh` 里已经内嵌了两段 python heredoc
（解析清单、轮询端口），也就是说它早就不是 shell 脚本，而是"一个 shell 壳子包着 Python"——
再加一个分支就要再开一段 heredoc。`qemu-boot.sh` 的 NUMA 分支则在用字符串拼参数
（`NUMA_ARGS="$NUMA_ARGS -object ..."`），配一句 `# shellcheck disable=SC2086` 才敢展开。

**原因**
shell 在两个地方按次数收费，而这两个脚本都已经付了很多次：

1. **没有列表**。`NUMA_ARGS` 是一个字符串，靠不加引号展开成多个参数，于是任何一个含空格的
   值都会静默变成两个参数。Python 里就是 `list[str]`，`subprocess` 直接收。
2. **没有结构化数据**。读一份 JSON 清单要 heredoc 出一个 python，结果再用 `sed -n 1p`
   一行行切回来——两次序列化，只为跨过语言边界。

**改法**

清单解析从"嵌在 shell 里的 python"变成普通函数。改前：

```sh
_resolved=$(ROOT="$ROOT" OUT="$OUT" ... python3 <<'RESOLVE'
import glob, json, os, sys
...
print(os.path.join(out, identity["obi"]))
print(os.path.join(out, kernel["debug"]))
print(identity["image"])
RESOLVE
) || exit $?

IMAGE=$(printf '%s\n' "$_resolved" | sed -n 1p)
ELF=$(printf '%s\n' "$_resolved" | sed -n 2p)
```

改后就是一次调用：

```python
image, elf, name = resolve(out, args.product, args.arch, args.switchset)
```

NUMA 参数从字符串拼接变成列表：

```sh
# 改前
NUMA_ARGS=""
for id in 0 1 2 3; do
    NUMA_ARGS="$NUMA_ARGS -object memory-backend-ram,size=${NODE_MEM}M,id=m$id"
done
...
# shellcheck disable=SC2086
exec "$ROOT/prebuilt/qemu/bin/qemu-system-x86_64" ... $NUMA_ARGS ...
```

```python
# 改后
for node, _ in NUMA_NODES:
    args += ["-object", f"memory-backend-ram,size={node_mem}M,id=m{node}"]
```

距离矩阵也从"写死十二行 `-numa dist,src=...`（注释说因为循环会吃掉调用者的参数）"变成一张
数据表 `NUMA_DISTANCES`，而调用者的参数就是 `argv`，不再有冲突。

几处行为刻意保持一致：

- **`qemu_boot.py` 结尾用 `os.execve`**，和 `exec` 一样把自己换成 QEMU。调用方
  （`qemu_debug.py`、VS Code 的任务终端）是朝它启动的那个 pid 发信号的，中间多一层还活着
  的进程会把信号吃掉。
- **`qemu_debug.py` 的清理**从 `trap cleanup EXIT INT TERM` 变成 `atexit` + `signal`，
  语义相同：VS Code 的 stop 任务发 SIGTERM，QEMU 必须跟着走。
- **环境变量接口没变**：`OUT`、`IMAGE`、`ELF`、`WORK`、`PORT`、`SMP`、`MEM`、`CPU`、`NUMA`
  都还在，命令行位置参数也还是 `<产品> <架构> <switchset>`。

文件名用下划线（`qemu_debug.py` 而不是 `qemu-debug.py`）——仓库既有约定，而且带连字符的
Python 文件没法被 import。

**参照**
无，本项目自有约定。

**验证**
1. `qemu_boot.py` 单独启动 dbg.1 镜像，跑到用户态、四个 CPU 都在跑线程，
   `terminating on signal 15`（不是三重错）：

   ```
   [info] handoff: jumping to kernel at 0xFFFFFF88400485AD, cr3=0x1FEDB000
   [... cpu0 info] userboot: kernel package holds 5 files
   [... cpu2 debug] I'm Thread 1
   [... cpu3 debug] I'm Thread 2
   ```
2. `qemu_debug.py` 两个 switchset 各启动 + attach 一次，断点地址与 sh 版**完全相同**
   （`0xffffff88400890a9` / `0xffffff88400760a9`）。
3. 七条错误路径逐条对照 sh 版输出，**逐字相同**：未知 switchset、未配置的架构、
   半个 IMAGE/ELF 覆盖、以及三种"镜像长出来了"的情况（撞 switchset / 不属于产品 /
   两个内核 ELF）。
4. SIGTERM 清理：起来之后 `kill` 掉脚本，QEMU 进程和 1234 端口都干净。
5. `tools/gen_debug_menu.py --check` 通过（工作区里的任务命令已指向 `.py`）。
6. 全仓已无指向这两个脚本的活引用；`docs/changes/` 和 `.agents/tasks/` 里的旧引用**保持
   原样**——那是历史记录，按约定只增不改。

## `cl`：在 lldb 里读 CPU_LOCAL 变量（2026-09-10）

**文件**
- `scripts/lldb_ours.py` —— 新建，提供 `cl` 命令
- `ours.code-workspace` —— 两个 launch 配置加 `initCommands` 自动加载
- `docs/development/debugging.md` —— 新增「读 CPU_LOCAL 变量：`cl`」

**症状**
在调试器里读 per-CPU 状态**没有一种正确的写法**，而错的那种不出声。

```
(lldb) p X86_PCPU
(ours::X86PerCpu) { tss = { sp0 = 0 ... } }      ← 全零，看着像"还没初始化"
```

实际上这份不是任何 CPU 的数据，是**链接期模板**。真正的值在别处，而 `p` 不会有任何提示。

**原因**
CpuLocal 用的是 Linux 的 model B（`docs` 里另有记载）：符号 `&var` 指向模板，
`%gs` 存 `base(cpu) - origin()`，每次访问是 `%gs:&var`。于是：

```
真实地址 = &var(模板，已 slide) + 该 CPU 的 offset
```

而调试器只知道 `&var`。offset 有两个来源，缺一不可：

- **当前 CPU**：`%gs`。`ArchCpuLocal::install()` 把 offset 写进 `IA32_GS_BASE`
  （`kernel/arch/x86/kernel/include/ours/arch/cpu_local.hpp`）。
- **任意 CPU**：`CpuLocal::CPU_OFFSETS[cpu]`，即 Linux 的 `__per_cpu_offset[]`。

加法是**回绕**的：offset 是 `isize`，physmap 布局下为负
（`0xffffffffbff6e000` 就是 `-0x40092000`），所以按 2^64 取模，和硬件一致。

**改法**
`cl` 三种用法各对应一种取 offset 的方式，输出把中间量也打出来，便于核对：

```
(lldb) cl CURRENT_CPUNUM
current  (ours::CpuNum) ours::mm::CpuLocal::CURRENT_CPUNUM = 0
        template 0xffffff88400a49a0  offset 0xffffffffbff6e000 -> 0xffffff88000129a0
```

三个实现上不显然、但都是实测逼出来的决定：

**1. 停在用户态时必须读 `k_gs_base` 而不是 `gs_base`。** 这是实测撞出来的——四个 vCPU 里
有一个停在 userboot 的自旋循环：

```
thread #2: 0x00000000002012d2        ← ring 3
    cs = 0x33   gs_base = 0x0   k_gs_base = 0xffffffffbff85000
```

内核入口 `swapgs`，所以 ring 3 时 per-CPU offset 在 `IA32_KERNEL_GS_BASE`，`%gs` 是用户态
那份（本内核 userboot 里是 0）。照 `gs_base` 算，**每个变量都会"解析"回自己的模板**——
一片零，看着像数据。`cl` 按 `cs & 3` 挑寄存器：

```python
user_mode = (cs.GetValueAsUnsigned() & 3) == 3
name = "k_gs_base" if user_mode else "gs_base"
```

**2. "是不是 CPU_LOCAL"用链接脚本的边界判，不用节名。** `.init.data.cpu_local*` 会被并进
`.init.data`（`kernel/kernel.ld:202`），而 `.init.data` 里绝大部分不是 per-CPU 的。
真正的判据是 `[__cpu_local_start, __cpu_local_end)`（同文件 :175、:204），刚好圈出 46 个变量。
第一版用节名，等于对半个 `.init.data` 都肯套 offset。

**3. `CPU_OFFSETS` 按裸内存读，不走 children。** 它是 `std::array`，而 lldb 展开
`std::array` 靠 formatter；freestanding 构建里没有那个 formatter，`GetChildAtIndex(2)`
直接返回无效值：

```
error: cl: CPU 2 is outside ours::mm::CpuLocal::CPU_OFFSETS
```
改成按 `地址 + cpu*8` 读 8 字节，与 formatter 无关。

还有一个小坑：`X86_PCPU` 是 `extern "C" inline`，`FindGlobalVariables` 返回**两条**
（两个 TU 各描述一次）。第一版把"多于一条"当成有歧义直接拒绝。改成比较 load address——
地址相同就是同一个对象。

**参照**
Linux 的 `__per_cpu_offset[]` 与 `per_cpu()`；crash/gdb 的 `per_cpu` 辅助命令是同类东西。

**验证**
全部在真实运行的四核内核上做的（`qemu_boot.py -gdb tcp::1234`，跑满 40 秒后 attach）：

1. `cl CURRENT_CPUNUM` 在四个 vCPU 上分别得到 0/1/2/3，**跟着 `thread select` 走**——
   其中 thread #2 停在用户态，正是靠 `k_gs_base` 才对：

   ```
   thread select 1 → 0    thread select 2 → 1
   thread select 3 → 2    thread select 4 → 3
   ```
2. `cl -a CURRENT_CPUNUM` 打出 16 个 unit（MAX_CPU），每个都读回自己的编号 0..15。
3. `cl X86_PCPU` 打出聚合体，`tss.sp0 = 18446743558380613632`（内核栈，非零）。
4. `cl CLKDEV_STORAGE 1` 打出 CPU 1 的 APIC timer：`m_name = "LVT"`、`m_mode = Oneshot`。
5. `cl LAPIC_TIMER_EVENT`（不是 per-CPU）被拒绝并给出该用 `p`。
6. `cl NOSUCHVAR` 给出清楚的找不到。
7. `cl -l` 列出 46 个，与 `llvm-nm` 按同一区间筛出来的 47 条**只差 `__gktl_counter_start`**
   一条——那是计数器块自己的标记，不是变量，脚本按 `__` 前缀滤掉了。

**故意没做**
- **没有做动态 per-CPU 分配（`CpuLocal::allocate()`）的读取**。`cl` 接的是**变量名**，
  而动态分配没有名字，只有 handle。要读那些得先有办法拿到 handle，是另一件事。
- **没有按 online mask 过滤 `-a`**。现在列的是"有 unit 的 CPU"，MAX_CPU=16 全都有，
  即使只启了 4 个 vCPU。加 online 过滤要再读 `Cpu::online_mask()`，而"有 unit"本身就是
  这条命令能回答的问题，先不引入第二个概念。
- **没有做 `cl -w` 之类的写入**。读已经解决了眼下的问题；写进 per-CPU 状态是另一种风险。

## `cpus` 和 `nodes`：调度器、运行线程、内存节点（2026-09-10）

**文件**
- `scripts/lldb_ours.py` —— 新增 `cpus`、`nodes`，以及共用的 canary 校验
- `docs/development/debugging.md` —— 两节说明
- `docs/repairs/260910/mm.md` —— 新建，记 `NUM_ONLINE_NODES` 的问题

**症状**
`cl` 解决了"读一个 per-CPU 变量"，但真正想问的三件事仍然要手工拼：
**每个 CPU 在跑什么线程、调度器队列里有多少、内存还剩多少**。手工拼的路径是
`cl` 出一个指针 → 抄地址 → `p *(T *)0x...`，一个 CPU 三步，四个 CPU 十二步。

**原因**
这三件事的数据都在，只是**入口名字长得没法用**：

```
ours::mm::CpuLocal::Current<ours::task::Thread*>::CURRENT_INSTANCE
ours::mm::CpuLocal::Current<ours::task::sched::Scheduler>::CURRENT_INSTANCE
```

而且它们各自还要再解一层：Thread 要读名字/状态/flags，Scheduler 要读
`m_runtime.num_queued_threads`，节点要走 `PmNode::NODES` 再走 zone 队列。

**改法**

```
(lldb) cpus
cpu  running                                      queued  weight  note
  0  'Idle/0' tid=3 Running [Idle | NoFree]            0       0
  1  'userboot' tid=18 Running [Detached]              1    2549
  2  'Sample1' tid=19 Running [Detached]               1    2549
  3  'Sample2' tid=20 Running [Detached]               1    2549
     (12 more with a unit but no scheduler -- never onlined: 4, 5, ...)

(lldb) nodes
node 0 @ 0xffffff801febd978  start_pfn=0
    spanned    130780 frames     510 MiB
    present    129451 frames     505 MiB
    zone Dma      @ ...  present=3752   managed=2507
    zone Dma32    @ ...  present=125699 managed=123334
```

四个设计决定，都是实测逼出来的：

**1. 指针用 canary 验真，而且区分"0"和"不对"。** 内核对象开头的 `gktl::Canary` 的 magic
是类型全名的 consteval 哈希（`kernel/lib/gktl/include/gktl/canary.hpp:15`）。同一个算法
用 Python 重算，三个类型全部对上：

```
ours::task::Thread            -> 485190896    观测 485190896   MATCH
ours::mm::PmNode              -> 4078567354   观测 4078567354  MATCH
ours::task::sched::Scheduler  -> 2869030934   观测 2869030934  MATCH
```

`Canary()` 默认构造把 magic 置 0，所以 **magic==0 是"从没构造过"，非 0 不匹配才是
"这片内存是别人的"**。合成一句 "canary bad" 的话，十二个没上线的 CPU 会被报成十二个故障——
第一版就是这样，四行有用的信息被埋掉了。现在它们折成一行。

**2. 两个来源交叉核对。** `running` 来自 per-CPU `Current<Thread*>`，`queued`/`weight` 来自
`Scheduler`；调度器自己还记着 `curr_thread` 和 `which_cpu`。这些是分别更新的，所以命令
比对它们，不一致就写进 note 列——可能只是停在上下文切换中间，也可能是真 bug，但都是
第一个该看的东西。

**3. `nodes` 走全局 `PmNode::NODES`，不走 per-CPU 的 `Current<PmNode*>`。** 要看的是所有
节点。zone 队列是 fallback 顺序表，同一个 zone 出现多次，按首次出现去重。

**4. `std::atomic<usize>` 按第一个 child 读。** freestanding 构建里没有 libc++ 的
formatter，`GetValue()` 对 atomic 返回 None；它的唯一 child 就是存储。同样的理由，
`PmNode::NODES` 这种 `std::array` 也是按裸内存读的（`cl` 那一节已经踩过一次）。

**顺带发现一个 mm 的问题**：`PmNode::NUM_ONLINE_NODES` **从来没有被赋过值**，
一个节点的机器上读出来是 `1879048187`，而且这个符号在镜像里根本不存在（没人引用，
存储被回收）。已记 `docs/repairs/260910/mm.md`；`nodes` 故意不打印它。

**参照**
Linux 的 `nr_online_nodes` / `node_states[N_ONLINE]`；crash 工具的 `ps` / `kmem -z`
是同类命令。

**验证**
在真实运行的四核内核上（`qemu_boot.py -gdb tcp::1234`，跑满 40 秒后 attach）：

1. `cpus` 四行分别是 `Idle/0`(tid 3)、`userboot`(tid 18)、`Sample1`(19)、`Sample2`(20)，
   状态 `Running`、flags 正确；后十二个 CPU 折成一行。
2. `nodes` 打出 510 MiB spanned / 505 MiB present，两个 zone（Dma、Dma32），
   数值与 QEMU 的 `-m 512` 对得上。
3. canary 三个类型全部匹配（见上表）。
4. `cl` 原有的七条路径回归通过。

**故意没做**
- **没有走运行队列**。`Thread::m_scheduling_context.m_runqueue_hook` 是一棵侵入式红黑树的
  节点，不是链表；走它要在调试器里手算 offsetof 并处理树结构，而且在半途停下来的内核里
  可能读到正在改的中间态。`num_queued_threads` 已经回答了"有没有堆积"，先到这里。
- **没有列出全部线程**。需要一个全局线程链表；有没有、在哪，还没查。
- **没有 buddy 分配器的按 order 空闲统计**。zone 上没有空闲计数器，要走 free list；
  和运行队列同一个问题，等真需要时再说。

## `kthread`：一个线程为什么没在跑（2026-09-10）

**文件**
- `scripts/lldb_ours.py` —— 新增 `kthread`；`cpus` 的 weight 列改名 `rqweight`
- `docs/development/debugging.md` —— 一节说明
- `docs/repairs/260910/task-sched.md` —— 新建，记 `m_curr_cpu` 等三个字段没人维护

**症状**
`cpus` 回答了"每个 CPU 在跑什么"，但下一个问题——**为什么是它，别的为什么没跑**——
仍然要手工 `p *(Thread *)0x...` 然后在四十多个成员里翻。

**原因**
翻的时候还容易翻错地方。真正的答案集中在三处，而它们都不在结构体的显眼位置：

- `m_waiter_state.m_waitqueue`（`wait_queue.hpp:88`）——阻塞它的队列。
  **`Parked` 而这里是 null，就是丢了唤醒路径**。
- `m_resource_lock` / `m_pi_lock` 的 `m_lockval`——`spin_lock.hpp:120-124` 定义了语义：
  **0 = 空闲，否则 = 持有者 CPU 号 + 1**。一串线程互卡时，这一个字直接点名该看哪个 CPU。
- `m_profile.effective.weight` —— 为 0 是硬故障，`avg_vruntime()` 会除以它
  （`profiles.hpp:20-27`）。

**改法**
一条命令把这些一次打出来，并且只对**确实错了**的加 `!!`：

```
(lldb) kthread 2
'Sample1' tid=19 @ 0xffffff8000a2c000
  state    Running   signals None   flags Detached
  blocked  waitqueue=0x0  status=Ok  interruptible=Yes
  locks    resource=free  pi=free
  stack    [0xffffff880402d000, 0xffffff8804031000) 16384 bytes  sp=0xffffff8804030fc0
```

**故意不报 `Rescheduling`**。`context.hpp:129-136` 自己记着两个已知缺陷：
`m_transient_state` 的 `Rescheduling` 永远不会被清、`DequeueDelayed` 从不被写入。
报它等于每一行都报——一个每次都响的告警等于没有告警。同理，`"boot"` 线程一辈子禁抢占
是故意的（`thread.cpp:121-130`），也不报。

命令叫 `kthread` 不叫 `thread`：lldb 已经有 `thread`，脚本不让覆盖（实测报
`"1" is not a valid subcommand of "thread"`）。

`cpus` 的 `weight` 列同时改名 `rqweight`——它是运行队列的总权重，而 `kthread` 打的是
线程自己的权重，两个都叫 weight 且数值不同（0 vs 503）是个陷阱。

**顺带查实一个 task-sched 的缺陷**：`m_curr_cpu` / `m_last_cpu` / `m_wake_cpu`
**从来不被维护**。四个线程跑在 CPU 0/1/2/3 上，三个字段全是 0；全仓只有三处赋值，
前两处在 `Scheduler::init_first_thread()`（一次性引导路径，`scheduler.cpp:190-191`），
第三处在 `fair.cpp:323`——而 bring-up 跑的是 RR。已记
`docs/repairs/260910/task-sched.md`。`kthread` 对这种情况打的是"这三个字段没人维护"
并指回文档，而不是每行都报一次"跑错核"；修好之后那处判断的另一条分支会自动开始工作。

**参照**
Linux 的 `task_struct::on_cpu` / `wake_cpu`；crash 工具的 `ps -l` / `foreach bt`。

**验证**
真实运行的四核内核上：

1. `kthread 0..3` 四个线程全部打出，字段与 `p *(Thread *)` 逐项核对一致。
2. `kthread 0x<addr>` 直接按地址取同一个线程，输出相同。
3. `kthread 9`（没上线的 CPU）→ `cpu9 has no current thread`。
4. canary 不匹配的地址 → `<not a Thread>`，不打印垃圾。
5. `curr/last/wake_cpu all 0` 告警在四个线程上都出现，与 grep 出来的赋值点一致。
6. `Idle/0` 的 `sp` 落在自己栈外但状态是 `Running`，告警**正确地没有触发**。
7. `cl` / `cpus` / `nodes` 回归通过。

**故意没做**
- **没有走运行队列**、**没有全局线程列表**、**没有 buddy 按 order 统计**：前两个要处理
  侵入式红黑树/链表的 offsetof 和半途停下的中间态，第三个要走 free list。`kthread` 覆盖了
  "为什么没在跑"，这三个覆盖的是"还有谁"，等真需要时再说。

## 终端里的 lldb 不会自动加载脚本（2026-09-10）

**文件**
- `.lldbinit` —— 新建
- `scripts/qemu_debug.py` —— ready 之后打印完整的 attach 命令行
- `docs/development/debugging.md` —— 命令行那节补上 import 与它的原因

**症状**
F5 会自动加载 `scripts/lldb_ours.py`（两个 launch 配置的 `initCommands`），
**但终端里 `lldb` 不会**。而文档给的那条命令行恰好没带 import：

```bash
lldb -o 'target create out/.debug/kernel.elf' \
     -o 'target modules load --file kernel.elf --slide 0xffffff8840000000' \
     -o 'gdb-remote localhost:1234'
```

照着敲，attach 是成功的，`cl` / `cpus` / `nodes` / `kthread` 一个都没有——
而且没有任何提示说少了什么。

**原因**
`initCommands` 是 launch 配置的字段，只对经它启动的会话生效。仓库里此前也没有
`.lldbinit`，`~/.lldbinit` 同样没有，所以终端会话没有任何加载点。

**改法**
三处，各解决一部分：

1. **`.lldbinit`**（仓库根）里放上那一行。但它**没法让自己被加载**——lldb 默认不信任当前
   目录的 `.lldbinit`（cd 进一个目录就执行任意代码，这个默认是对的）。lldb 自己会说：

   ```
   error: There is a .lldbinit file in the current directory which is not being read.
   ```

   想要它生效是一次性的：`echo 'settings set target.load-cwd-lldbinit true' >> ~/.lldbinit`。
2. **`qemu_debug.py` 在 ready 之后把完整命令行打出来**，包含 import 和 slide。
   这条路零配置，而且顺带把 slide 从"读者自己去查"变成"就在屏幕上"。
3. **文档那条命令行补上第一行**，并写清为什么不能省。

**参照**
无。lldb 的 `target.load-cwd-lldbinit` 默认值与那条 error 信息是上游行为。

**验证**
把脚本打印的那一行**原样 eval 执行**，命令确实在：

```
$ ./scripts/qemu_debug.py
qemu-debug: attach with:  lldb -o 'command script import scripts/lldb_ours.py' -o ...
$ eval "$LINE -o 'cl -l' -o quit"
error: There is a .lldbinit file in the current directory which is not being read.
ours: cl <var> [cpu] | cpus | nodes | kthread [cpu|0xaddr]
46 CPU_LOCAL variables in [0xffffff8840092000, 0xffffff88400a49b0):
```

第一行正是 lldb 在确认 `.lldbinit` 的那条默认行为；第二三行说明 import 走的是命令行那条路，
和 `.lldbinit` 无关。

**故意没做**
- **没有写 `~/.lldbinit`**。那是用户全局配置，不该由仓库里的东西替人改；`.lldbinit`
  连同一行说明放在这里，开不开由人决定。
