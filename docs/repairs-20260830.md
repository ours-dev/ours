## 二、真 bug（不是缺实现，是写错了）

### 1. 取地址会把已分配的页标记成空闲 → 同一块内存发两次

`kernel/mm/include/ours/mm/memory_model.hpp` `frame_to_phys`

原来用 `frame->as_ptr<PmFrame>()`，它会把 role 盖成 `Role::Pmm` —— 而 buddy 用
`Role::Pmm` 表示「这一页空闲」。所以**取一个已分配页的物理地址，就把它标成了空闲**，
之后它的 buddy 被释放时会把活内存合并进空闲块，再次分配出去。改成不写状态的
`static_cast`。

### 2. `AutoPreemptDisabler` 的行为和名字相反

`kernel/include/ours/task/auto_preempt_disabler.hpp`

```cpp
AutoPreemptDisabler() : m_disabled(true) { enable(); }   // 构造时 enable_preemption()
```

构造一个「抢占禁用器」反而**开启**抢占，且留下 `m_disabled == false`，析构什么都不做。
兄弟类 `AutoEagerReschedDisabler` 坏法不同：`disable()` 的守卫 `if (!m_disabled)` 判假，
什么都没做，析构却去 `enable()` 一个从未被关闭的东西。

影响面不止显式使用处 —— `kernel/include/ours/sync/spin_lock.hpp:143` 用它做
`LOCKDEP_STATE_SAVER`，**每次自旋锁获取都经过它**。

两个都改成 `m_disabled(false)` + `disable()`。

### 3. `flush_pending_remote` 丢掉本地重调度请求

`kernel/kernel/task/preemption_state.cpp`

原来结尾调 `clear_pending()`，把整个挂起掩码连同 `NoResched` 标志一起清空 —— 但只有
远程请求被兑现了。当 eager 重新启用而抢占仍被禁用时（本地冲刷被跳过），本地请求被
静默丢弃。

对照 Zircon `PreemptionState::FlushPendingContinued`：remote-only 冲刷以
`preempts_pending_ &= current_cpu_mask` 结尾，即**保留**本地位。已照此修正。

### 4. `FORCE_INLINE` 不是 `inline`

`system/public/ours/compiler.hpp`

`[[gnu::always_inline]]` 只是给优化器的提示，**不赋予 inline 链接性**。头文件里定义的
自由函数因此在每个 TU 都有外部链接的定义 —— 链接时重复符号。这个错误只有链接才暴露，
而这棵树此前从未链接过。

现在宏保持纯属性，14 处定义显式写 `inline`。

### 5. `create()` 与 `init()` 争同一把非重入锁

`kernel/mm/object_cache.cpp`

`MemCache::create` 持有 `g_cache_lock` 后调 `init()`，而 `init()` 又去 acquire 同一把锁。
`sync::Mutex` 是 CAS 非重入的（owner 线程指针存在 state 里），**第一次建 cache 就死锁**。

### 6. `MemCache` 成员未初始化 / 初始化自错误的参数

`kernel/mm/object_cache.cpp` 构造函数

- `m_user_align` 全树从不赋值，但 `compute_layout` 拿它当对齐参数用（未初始化读；若为 0，
  `align_up` 把 stride 塌成 0，随后除零）
- `m_user_size` 从 **`align`** 初始化，不是 `size`
- `m_node_caches` 是 `std::array` 成员且无初始化器 → 垃圾指针，而 `~MemCache` 会遍历
  全部并 `free()`

### 7. slab 的 order 与对象数算错

`kernel/mm/object_cache.cpp`

两个独立的错误叠加：

- `(order << PAGE_SHIFT)` 应为 `BIT(order) << PAGE_SHIFT`。order=0 时算出 **0 个对象**，
  新建的 slab 一出生就「满了」
- `get_order()` 数的是**页**不是字节（`pmm.hpp` 里就是这么定义的），却被喂了字节数，
  把 order 整整放大了 `PAGE_SHIFT`

修复前后（`MAX_FRAME_ORDER` 是 10）：

| 对象大小 | 修前 order | 修前对象数 | 修后 order | 修后对象数 |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 3（32 KB） | 1536 | 0（1 页） | 512 |
| 4096 | **12（16 MB，超上限）** | 12 | 0 | 1 |

### 8. logz4 日志缓冲区溢出

`kernel/lib/logz4/log.cpp`

`std::vformat_to` 接裸 `char*` 时**完全无界**，会写满格式化结果需要的全部长度 —— 一条长
日志直接冲垮 512 字节静态缓冲区。加了有界输出迭代器，并预留一字节给换行。顺带
`write(s, N)` 把字符串字面量的 NUL 也发到串口了，改为 `N - 1`。

（这段代码此前从未被编译过，见第四节。）

### 9. 命名失同步（定义存在，只是名字没跟上）

- `kernel/mm/pmm.cpp`：`g_max_phys_addr` / `g_min_phys_addr` vs 头文件的
  `MAX_PHYS_ADDR` / `MIN_PHYS_ADDR`
- `kernel/platform/pc/interrupt.cpp`：`platform_handle_irq_preamble/postamble` vs
  头文件与调用方的 `platform_start/finish_handling_irq`（签名完全一致）
- `kernel/mm/pmm.cpp`：`free_frame` vs 头文件的 `free_frames`；`alloc_frame` vs
  `alloc_frames`

## 三、连不上的链路（缺实现，不是写错）

### 帧分配（`09f70a0`）

```
PmNode::get_frame_from_zone_queues   恒定 nullptr
  PmZone::alloc_frames                恒定 nullptr
    PmZone::alloc_frame               已实现 ✓
```

外加 `ZoneQueues::for_each_zone` 函数体为空 —— 回调永远不执行。**内核里每一次分配都落到
这里**，全部在最底层失败。

`for_each_zone` 现在遍历 `SharedAffinity` 队列（它本身就是回退顺序：`insert_local_zone`
放本地 zone，`connect` 按亲和度追加远程）。返回 void 的回调遍历全部；返回值的回调在第一个
为真的结果处短路。

### slab 分配器

`create_boot` 原本返回 `Unimplemented`，整个 slab 层在 init 就失败。`allocate` 慢路径找到
slab 后从不取对象。`slab::init` 从不构建空闲链表。现在这条主线是通的：

- `create_boot` 在 `LazyInit` 裸存储上原地构造再 `init`
- `init()` 里 CpuCache 与 NodeCache 的顺序对调 —— NodeCache 要从 `g_node_cache` 分配，
  而自举时那就是正在建的 cache 本身；CpuCache 先就位后，node cache 就能从一块新 slab
  里切出自己的 NodeCache
- 空闲链表穿过对象本身，偏移由 `SlabBody::next_offset` 携带

**一个取舍要你确认**：我去掉了 per-CPU partial 链表。它和 node partial 链表并存时，
「slab 在哪张表上」是一个被两把不同的锁守着的状态位，会丢 slab：

> CPU A 从自己的 partial 链表取到一个已满的 slab 正要摘掉；CPU B 同时 free 进去，看到
> `was_full` 想挂到 node 链表，但 `is_linked()` 还是 true 于是放弃；随后 A 摘掉它 ——
> slab 有空闲对象却不在任何链表上，永久丢失。

现在**每个 node 一张表、一把锁**，锁指针存在 slab 自己的 body 里，所以两个 CPU 对
「该拿哪把锁」的答案必然一致。拿回 per-CPU 表需要 per-slab 锁或 slub 那种
`cmpxchg_double`，注释里写明了。

### 页角色机制重构

`PageFrame` 改成头/身体分离：`m_status`（role/flags/order + zone/section/node）跨角色存活，
只有 `m_body` 随角色变。三个 POD 角色体，`become<Body>()` 是唯一写 role 的地方，
`try_as` 查询、`as` 断言。用 `ustl::mem::start_lifetime_as`（新增，基于
`__builtin_memmove`，实测零开销）使其在标准上有定义。

`VmPage` / `PmFrame` / `Slab` / `PmFolio` 都是 `PageFrame` 的别名，约 100 个调用点签名未动。

三条 `static_assert` 护栏：描述符大小等于 memmap 步长、三个角色体都必须可平凡复制/析构、
都必须放得下。**「角色体只能放 POD」现在是编译错误**。

## 九、QEMU 运行时环境（新增）

`prebuilt/` 里现在有 QEMU 11.1.1 与 GRUB 2.12，`scripts/qemu-boot.sh` 一条命令引导：

```sh
./scripts/qemu-boot.sh
```

**取件方式**：QEMU 对 macOS 没有官方二进制（qemu.org 指向 Homebrew/MacPorts），所以取的是
Homebrew bottle —— 但**只下载、解包到 `prebuilt/`，没有安装 brew，也没碰任何系统目录**。
qemu 闭包 29 个 formula，grub 工具链 9 个。

三个必须知道的坑，都写在脚本注释里：

1. **dylib 路径**：bottle 里的二进制记录的是 `/opt/homebrew/...` 绝对路径。不必逐个
   `install_name_tool` —— dyld 在记录路径不存在时会查 `DYLD_FALLBACK_LIBRARY_PATH`，
   指向解包出来的 `lib/` 即可。
2. **不能用 `-kernel`**：QEMU 的 `-kernel` 只实现 Multiboot **1**、bzImage、PVH。我们的
   shim 头是 `0xE85250D6`（Multiboot **2**）。用 `strings` 查过 qemu 二进制，里面只有
   `multiboot.c` / `multiboot,kernel`，没有任何 multiboot2 痕迹。所以必须走 GRUB。
3. **`grub-mkrescue` 用不了**：它坚持要编译期 `pkglibdir` 下的 `unicode.pf2` 和 locale，
   而那是 `/opt/homebrew/...`，且没有环境变量可覆盖（二进制里只有 `GRUB_DISTRIBUTOR`、
   `GRUB_ENABLE_CRYPTODISK`、`TMPDIR`）。改用 `grub-mkimage`（`-d` 指定模块目录即可，
   不需要字体）+ `mtools` 做 FAT 镜像，UEFI 直接引导 —— bottle 只带 `x86_64-efi` 平台，
   没有 BIOS 的 `i386-pc`，而 QEMU 自带 edk2 固件。

### 已确认的运行时问题

**A. CPU 模型必须至少 x86-64-v2**（已在脚本里设 `-cpu Nehalem`）

内核用 `-march=x86-64-v2` 构建，而 QEMU 默认的 `qemu64` 大致是 v1、不提供 POPCNT。
第一条 `popcntq` 就 #UD：

```
81: v=06 (#UD)  RIP=0x9e2
82: v=0d (#GP)  同一 RIP     ← IDT 未就绪，分发 #UD 时再 #GP
    → #DF → triple fault → 重启

9e2: f3 48 0f b8 f1    popcntq %rcx, %rsi
```

位置在 `obi::ContainerView::from`（对齐检查里的 `has_single_bit`）。这不是内核 bug，是
测试环境与构建目标不匹配 —— 但它会伪装成「内核一启动就重启」，值得记住。

**B. 当前卡点：physload 的 ELF 被拒**

```
boot-shim: loader params at 0x{:X}
[info]: `ours.obi` is at 0x{:X}, size {} bytes
ACPI-V{}, RSDP={}
panic: Invalid physload ELF: {}
```

已经走过：OBI 容器解析 ✓、boot package ✓、item 0 取到 ✓、Multiboot2 内存图 ✓。
失败在 `kernel/arch/x86/phys/bootshim/shim.cpp:81` 的 `ElfImage::init`。

item 0 确实是 physload（`obit list` 显示 `0 physload 72824`），文件是 ELF64 / **DYN** /
x86-64 / 5 个 program header。

**可诊断性问题**：`ElfImage::init` 三个失败点（`Parser::parse_as`、`native_image()`、
`LoadPolicy::make_plan`）全都返回同一个 `Status::InvalidArgument`，所以 panic 分不出是
哪一个。下一步该先让它们返回可区分的状态。

**C. phys 侧日志不带格式化，这是有意的，不是 bug**

`{}`、`{:X}` 原样打印，因为 `kernel/phys/BUILD.gn:27` 定义了 `PHYS_ENVIRONMENT=1`，
该宏下 `print`/`println` 直接丢弃参数（`print.hpp:62-85`）。`panic.hpp` 注释写明了理由：
引导器阶段没有内存服务，不值得为此引入 `std::format` 的分配机制。

代价是 phys 阶段的诊断信息里看不到任何数值 —— 上面 B 的排查因此只能靠读代码。
是否值得换成一个不分配的轻量格式化器，是个待定的取舍。
