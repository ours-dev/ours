## 二、真 bug（不是缺实现，是写错了）

> 本节以及第三、四、五节记录的都是**已经修完**的东西，列出「原来是什么样」是为了让你判断
> 改法对不对，不是待办清单。还没做的在第六节。



### 1. 取地址会把已分配的页标记成空闲 → 同一块内存发两次

`kernel/mm/include/ours/mm/memmap.hpp` `frame_to_phys`

原来用 `frame->as_ptr<PmFrame>()`，它会把 role 盖成 `Role::Pmm` —— 而 buddy 用
`Role::Pmm` 表示「这一页空闲」。所以**取一个已分配页的物理地址，就把它标成了空闲**，
之后它的 buddy 被释放时会把活内存合并进空闲块，再次分配出去。改成不写状态的
`static_cast`。

### 2. `AutoPreemptDisabler` 的行为和名字相反

`kernel/include/ours/task/auto_preempt_disabler.hpp`

```cpp
AutoPreemptDisabler() : m_disabled(true) { enable(); }   // 构造时 enable_preemption()
```

构造一个「抢占禁用器」反而**开启**抢占，且留下 `m_disabled == false`，析构什么都不做。
兄弟类 `AutoEagerReschedDisabler` 坏法不同：`disable()` 的守卫 `if (!m_disabled)` 判假，
什么都没做，析构却去 `enable()` 一个从未被关闭的东西。

影响面不止显式使用处 —— `kernel/include/ours/sync/spin_lock.hpp:143` 用它做
`LOCKDEP_STATE_SAVER`，**每次自旋锁获取都经过它**。

两个都改成 `m_disabled(false)` + `disable()`。

### 3. `flush_pending_remote` 丢掉本地重调度请求

`kernel/kernel/task/preemption_state.cpp`

原来结尾调 `clear_pending()`，把整个挂起掩码连同 `NoResched` 标志一起清空 —— 但只有
远程请求被兑现了。当 eager 重新启用而抢占仍被禁用时（本地冲刷被跳过），本地请求被
静默丢弃。

对照 Zircon `PreemptionState::FlushPendingContinued`：remote-only 冲刷以
`preempts_pending_ &= current_cpu_mask` 结尾，即**保留**本地位。已照此修正。

### 4. `FORCE_INLINE` 不是 `inline`

`system/public/ours/compiler.hpp`

`[[gnu::always_inline]]` 只是给优化器的提示，**不赋予 inline 链接性**。头文件里定义的
自由函数因此在每个 TU 都有外部链接的定义 —— 链接时重复符号。这个错误只有链接才暴露，
而这棵树此前从未链接过。

现在宏保持纯属性，14 处定义显式写 `inline`。

### 5. `create()` 与 `init()` 争同一把非重入锁

`kernel/mm/object_cache.cpp`

`MemCache::create` 持有 `g_cache_lock` 后调 `init()`，而 `init()` 又去 acquire 同一把锁。
`sync::Mutex` 是 CAS 非重入的（owner 线程指针存在 state 里），**第一次建 cache 就死锁**。

### 6. `MemCache` 成员未初始化 / 初始化自错误的参数

`kernel/mm/object_cache.cpp` 构造函数

- `m_user_align` 全树从不赋值，但 `compute_layout` 拿它当对齐参数用（未初始化读；若为 0，
  `align_up` 把 stride 塌成 0，随后除零）
- `m_user_size` 从 **`align`** 初始化，不是 `size`
- `m_node_caches` 是 `std::array` 成员且无初始化器 → 垃圾指针，而 `~MemCache` 会遍历
  全部并 `free()`

### 7. slab 的 order 与对象数算错

`kernel/mm/object_cache.cpp`

两个独立的错误叠加：

- `(order << PAGE_SHIFT)` 应为 `BIT(order) << PAGE_SHIFT`。order=0 时算出 **0 个对象**，
  新建的 slab 一出生就「满了」
- `get_order()` 数的是**页**不是字节（`pmm.hpp` 里就是这么定义的），却被喂了字节数，
  把 order 整整放大了 `PAGE_SHIFT`

修复前后（`MAX_FRAME_ORDER` 是 10）：

| 对象大小 | 修前 order | 修前对象数 | 修后 order | 修后对象数 |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 3（32 KB） | 1536 | 0（1 页） | 512 |
| 4096 | **12（16 MB，超上限）** | 12 | 0 | 1 |

### 8. logz4 日志缓冲区溢出

`kernel/lib/logz4/log.cpp`

`std::vformat_to` 接裸 `char*` 时**完全无界**，会写满格式化结果需要的全部长度 —— 一条长
日志直接冲垮 512 字节静态缓冲区。加了有界输出迭代器，并预留一字节给换行。顺带
`write(s, N)` 把字符串字面量的 NUL 也发到串口了，改为 `N - 1`。

（这段代码此前从未被编译过，见第四节。）

### 9. 命名失同步（定义存在，只是名字没跟上）

- `kernel/mm/pmm.cpp`：`g_max_phys_addr` / `g_min_phys_addr` vs 头文件的
  `MAX_PHYS_ADDR` / `MIN_PHYS_ADDR`
- `kernel/platform/pc/interrupt.cpp`：`platform_handle_irq_preamble/postamble` vs
  头文件与调用方的 `platform_start/finish_handling_irq`（签名完全一致）
- `kernel/mm/pmm.cpp`：`free_frame` vs 头文件的 `free_frames`；`alloc_frame` vs
  `alloc_frames`

## 三、连不上的链路（缺实现，不是写错）

### 帧分配（`09f70a0`）

```
PmNode::get_frame_from_zone_queues   恒定 nullptr
  PmZone::alloc_frames                恒定 nullptr
    PmZone::alloc_frame               已实现 ✓
```

外加 `ZoneQueues::for_each_zone` 函数体为空 —— 回调永远不执行。**内核里每一次分配都落到
这里**，全部在最底层失败。

`for_each_zone` 现在遍历 `SharedAffinity` 队列（它本身就是回退顺序：`insert_local_zone`
放本地 zone，`connect` 按亲和度追加远程）。返回 void 的回调遍历全部；返回值的回调在第一个
为真的结果处短路。

### slab 分配器

`create_boot` 原本返回 `Unimplemented`，整个 slab 层在 init 就失败。`allocate` 慢路径找到
slab 后从不取对象。`slab::init` 从不构建空闲链表。现在这条主线是通的：

- `create_boot` 在 `LazyInit` 裸存储上原地构造再 `init`
- `init()` 里 CpuCache 与 NodeCache 的顺序对调 —— NodeCache 要从 `g_node_cache` 分配，
  而自举时那就是正在建的 cache 本身；CpuCache 先就位后，node cache 就能从一块新 slab
  里切出自己的 NodeCache
- 空闲链表穿过对象本身，偏移由 `SlabBody::next_offset` 携带

**一个取舍要你确认**：我去掉了 per-CPU partial 链表。它和 node partial 链表并存时，
「slab 在哪张表上」是一个被两把不同的锁守着的状态位，会丢 slab：

> CPU A 从自己的 partial 链表取到一个已满的 slab 正要摘掉；CPU B 同时 free 进去，看到
> `was_full` 想挂到 node 链表，但 `is_linked()` 还是 true 于是放弃；随后 A 摘掉它 ——
> slab 有空闲对象却不在任何链表上，永久丢失。

现在**每个 node 一张表、一把锁**，锁指针存在 slab 自己的 body 里，所以两个 CPU 对
「该拿哪把锁」的答案必然一致。拿回 per-CPU 表需要 per-slab 锁或 slub 那种
`cmpxchg_double`，注释里写明了。

### 页角色机制重构

`PageFrame` 改成头/身体分离：`m_status`（role/flags/order + zone/section/node）跨角色存活，
只有 `m_body` 随角色变。三个 POD 角色体，`become<Body>()` 是唯一写 role 的地方，
`try_as` 查询、`as` 断言。用 `ustl::mem::start_lifetime_as`（新增，基于
`__builtin_memmove`，实测零开销）使其在标准上有定义。

`VmPage` / `PmFrame` / `Slab` / `PmFolio` 都是 `PageFrame` 的别名，约 100 个调用点签名未动。

三条 `static_assert` 护栏：描述符大小等于 memmap 步长、三个角色体都必须可平凡复制/析构、
都必须放得下。**「角色体只能放 POD」现在是编译错误**。

## 九、QEMU 运行时环境（新增）

`prebuilt/` 里现在有 QEMU 11.1.1 与 GRUB 2.12，`scripts/qemu-boot.sh` 一条命令引导：

```sh
./scripts/qemu-boot.sh
```

**取件方式**：QEMU 对 macOS 没有官方二进制（qemu.org 指向 Homebrew/MacPorts），所以取的是
Homebrew bottle —— 但**只下载、解包到 `prebuilt/`，没有安装 brew，也没碰任何系统目录**。
qemu 闭包 29 个 formula，grub 工具链 9 个。

三个必须知道的坑，都写在脚本注释里：

1. **dylib 路径**：bottle 里的二进制记录的是 `/opt/homebrew/...` 绝对路径。不必逐个
   `install_name_tool` —— dyld 在记录路径不存在时会查 `DYLD_FALLBACK_LIBRARY_PATH`，
   指向解包出来的 `lib/` 即可。
2. **不能用 `-kernel`**：QEMU 的 `-kernel` 只实现 Multiboot **1**、bzImage、PVH。我们的
   shim 头是 `0xE85250D6`（Multiboot **2**）。用 `strings` 查过 qemu 二进制，里面只有
   `multiboot.c` / `multiboot,kernel`，没有任何 multiboot2 痕迹。所以必须走 GRUB。
3. **`grub-mkrescue` 用不了**：它坚持要编译期 `pkglibdir` 下的 `unicode.pf2` 和 locale，
   而那是 `/opt/homebrew/...`，且没有环境变量可覆盖（二进制里只有 `GRUB_DISTRIBUTOR`、
   `GRUB_ENABLE_CRYPTODISK`、`TMPDIR`）。改用 `grub-mkimage`（`-d` 指定模块目录即可，
   不需要字体）+ `mtools` 做 FAT 镜像，UEFI 直接引导 —— bottle 只带 `x86_64-efi` 平台，
   没有 BIOS 的 `i386-pc`，而 QEMU 自带 edk2 固件。

### 已确认的运行时问题

**A. CPU 模型必须至少 x86-64-v2**（已在脚本里设 `-cpu Nehalem`）

内核用 `-march=x86-64-v2` 构建，而 QEMU 默认的 `qemu64` 大致是 v1、不提供 POPCNT。
第一条 `popcntq` 就 #UD：

```
81: v=06 (#UD)  RIP=0x9e2
82: v=0d (#GP)  同一 RIP     ← IDT 未就绪，分发 #UD 时再 #GP
    → #DF → triple fault → 重启

9e2: f3 48 0f b8 f1    popcntq %rcx, %rsi
```

位置在 `obi::ContainerView::from`（对齐检查里的 `has_single_bit`）。这不是内核 bug，是
测试环境与构建目标不匹配 —— 但它会伪装成「内核一启动就重启」，值得记住。

**B. 当前卡点：physload 的 ELF 被拒**

```
boot-shim: loader params at 0x{:X}
[info]: `ours.obi` is at 0x{:X}, size {} bytes
ACPI-V{}, RSDP={}
panic: Invalid physload ELF: {}
```

已经走过：OBI 容器解析 ✓、boot package ✓、item 0 取到 ✓、Multiboot2 内存图 ✓。
失败在 `kernel/arch/x86/phys/bootshim/shim.cpp:81` 的 `ElfImage::init`。

item 0 确实是 physload（`obit list` 显示 `0 physload 72824`），文件是 ELF64 / **DYN** /
x86-64 / 5 个 program header。

**可诊断性问题**：`ElfImage::init` 三个失败点（`Parser::parse_as`、`native_image()`、
`LoadPolicy::make_plan`）全都返回同一个 `Status::InvalidArgument`，所以 panic 分不出是
哪一个。下一步该先让它们返回可区分的状态。

**C. phys 侧日志不带格式化，这是有意的，不是 bug**

`{}`、`{:X}` 原样打印，因为 `kernel/phys/BUILD.gn:27` 定义了 `PHYS_ENVIRONMENT=1`，
该宏下 `print`/`println` 直接丢弃参数（`print.hpp:62-85`）。`panic.hpp` 注释写明了理由：
引导器阶段没有内存服务，不值得为此引入 `std::format` 的分配机制。

## 十、Mutex 交接路径与 C++26

`2d0b6ff` → `a6ca9a0` → `ce2774a` 三个提交是同一处的反复推敲，只看最后一个即可。

`OwnedWaitQueue::lock_for_notify_operation` 原本返回 `bool` 表示「是否锁住」、真正的结果
（要唤醒的线程）走**出参**，而那个 bool 在 `Mutex::release_slowpath` 里根本没人处理
（`if (!...) { /* ??? */ }`）。连带后果是继任线程和要发布的状态必须先默认初始化、再在
if/else 两支各赋一次，还要一个 `do_wake` 标志把同一个答案带到函数末尾。

现在返回一个可解构的聚合体，在 `if` 的条件里解构（P0963R3）：

```cpp
if (auto [locked, to_wake] =
        m_waiters.lock_for_notify_operation<Thread::UnparkList>(1, default_hook)) {
    auto *const new_owner = &*to_wake.front();
    publish(static_cast<State>(reinterpret_cast<usize>(new_owner)) | State::Contended);
    m_waiters.notify_threads_locked(ustl::move(to_wake), default_hook, NotifyControl::None);
} else {
    publish(State::Available);
}
```

中间试过一版返回 `ustl::Option<UnparkList>`（`a6ca9a0`），又改了回来：条件里已经确认非空，
而 `Option` 的每次访问都要走 `operator*` → `value()` → `require_some()`，等于反复问一个
刚回答过的问题。结构化绑定直接绑到成员，没有这层。

`locked` 保留为独立成员：**「锁住了但队列为空」和「没锁住」是两种状态**，当前两个调用方
都不关心区别，所以由 `operator bool` 合并，但数据还在。

**构建标准升到了 `c++2c`**（`build/config/cxx_version.gni`）。P0963R3 是 C++26 特性，在
`-std=c++23` 下会触发 `-Wc++26-extensions`，而构建是 `-Werror`。选择升标准而不是加
`-Wno-`，理由是压警告等于假装它不是 C++26 特性；且 `system/lib/hsien` 本来就在用
`-std=c++26`。代价只有一处：`std::is_trivial_v` 在 C++26 弃用，那条 `static_assert` 改成
它本来就等价的合取式。要回退只需把 `ours_cxx_version` 改回 `"23"` 并加 `-Wno-c++26-extensions`。

## 十二、WaitQueue 两阶段唤醒（`4feec1f` / `51bd985`）

**先更正第六节的一处说法。** 我原本写「基类 `WaitQueue::lock_for_notify_one/all` 本身就是
桩，下面没有东西可搭」——**这是错的**。`WaitQueue` 的唤醒路径本来就是写好的：`park_thread`、
`unpark_thread`、`enqueue_waiter`、`dequeue_waiter`、`wake_dequeued_thread`、`notify_one`、
`notify_all` 全都有实体。只有**两阶段**那一对是桩。我把「一个变体缺失」放大成了「整个机制
缺失」。

两阶段存在的理由很具体：**有些调用方必须在「waiter 已确定被唤醒、但还没真正运行」这个中间点
做事**。`Mutex::release_slowpath` 要在摘链和唤醒之间把新 owner 发布进 `m_state`，
`Event::signal` 要在放掉 guard 前记录结果。`notify_one`/`notify_all` 一步做完，插不进去。

一个容易搞错的细节：**`lock_for` 说的是「阶段」不是「加锁动作」**，调用方已经持锁。
`Event::signal` 先 `Guard guard{m_wq.get_lock()}` 再调它，函数内部若再加一次，非重入的
SpinLock 会当场死锁。所以实现里是 `assert_held()`，并按 `Scheduler` 的既有惯例升级为
`TA_REQUIRES(get_lock())`。

顺带抽出 `dequeue_front_locked`——`notify_one`、`notify_all` 和新增这两个之间，摘链那五行
是完全重复的。

**消掉的实际后果**：

- `Event::signal` 之前**永远唤不醒任何人**（拿到 `none()` 直接返回）。
- `Mutex::release_slowpath` 之前每次有争用的释放都走兜底分支——锁降为 Available 而等待者
  一个都没被唤醒，然后永久阻塞。（第一节表格里我曾把这条描述成「降为 Available」，不准确：
  真正的后果是**丢唤醒**。走到慢路径就意味着 `try_release` 的 CAS 失败、Contended 已置位，
  所以「没有接手线程」本来只该是竞态兜底，不该是常态。）

## 十七、physboot 建 vmours 页表时的只读权限（2026-09-02）

起因是一个很具体的问题：physboot 那段 setup 内核页表的代码，在重定位内核之后有没有把该
只读的地方改回只读。答案是没有——`fix_mapping()` 只照 PT_LOAD 的 `p_flags` 映射一次，
PT_GNU_RELRO 从头到尾没进过这条路径。顺着查下去，同一条链上还有几处，一起改了。

顺序本身是对的，不需要改：physboot 是 `load` → `relocate` → `build_kernel_aspace`，而
`ElfImage::relocate()` 写的是 `m_pa_load`，也就是 identity map 下的物理地址，跟高半区那份
映射无关。所以 RELRO 完全可以在建映射时就直接映成只读，不需要先 RW 再 protect。

### 1. RELRO 现在参与映射

`eftl` 的 `RelroRegions` 早就有了，只是 phys 侧一个调用者都没有。现在 `LoadPlan` 把每个
PT_GNU_RELRO 原样记下来（`relro_intervals()`），`ElfImage::fix_mapping()` 在遍历段的时候按
RELRO 边界把段切成若干段连续页，落在 RELRO 里的那段去掉写权限。

**在建映射时切、而不是事后 protect**，是因为 `Paging::protect()` 遇到一个只被 RELRO 覆盖了
一部分的大页会直接返回 `InvalidArgument`——那时已经没有东西可以把它拆开了。而 `map()` 是
按每次调用的剩余长度决定要不要用大页的，分开调用天然就不会跨越 RELRO 边界。

页对齐的规则值得记一笔，两个方向都试过才定下来：

- **起点向上取整。** RELRO 不一定是段的开头——本仓库的 kernel.ld 就把 `.init_array` 放在
  `.init.data` 后面——起点向下取整会把前面真正会被写的数据一起冻掉。
- **终点只在 RELRO 一直延伸到段内容末尾时才向上取整**，那时该页剩下的部分是这个段自己的
  填充，没人会写；否则向下取整。只向下取整的话，像 `.dynamic` 这种整段只有 0xd0 字节的
  会被算成空区间，保护直接白给。

### 2. 只读在 phys 阶段本来是没有强制力的

两个都在 `start64.S`：

- **EFER.NXE 从来没开过**。原来只设了 `LME`。而 `fix_mapping()` 对 rodata/data/bss 不带
  `Executable`，PTE 的 bit 63 就会被置上；NXE=0 时那是保留位，内核第一次访问 `.data` 就该
  吃一个 reserved-bit #PF。对比 AP 那条路（`bootstrap16.S`）是 LME 和 NXE 一起设的，BSP
  这条是漏的。现在 NX 和长模式一样当作硬性要求：CPUID `80000001` EDX 的 bit 29 和 bit 20
  一起查，缺任一个就停在 `.Lunsupported_cpu`。
- **CR0.WP 也没开**。`Cr0::Wp` 要等到 `x86_init_mmu_percpu()` 才置 1，在那之前 Ring 0 写只读
  页根本不 fault。现在开启分页的那条指令就带上 WP。phys 自己所有映射都是 `PermMask`，不会
  被它挡住。

### 3. physmap 不再可执行

`PHYSMAP_MMU_FLAGS` 原来是 `PermMask | Present`，把 0..32GB 物理内存整块映成 RWX，内核镜像
自己也在里面——高半区那份 RO/NX 可以直接从 physmap 别名绕过去。现在是 `Readable |
Writable | Present`。可写别名还在（physmap 就是干这个的），可执行别名没了。

### 4. `.init` 挪到镜像尾部

按你的要求。physboot 是一整块连续物理内存装下整个镜像，`.init` 原来夹在 relro 和 `.bss`
中间，回收它等于在这块分配的中间打洞。现在顺序是 `… .data → .data.rel.ro → .bss → .init.*`，
`__init_end == __executable_end`（原来的 ASSERT 是 `__bss_end == __executable_end`，已改）。

同时把 `.ccrt_init` 从 `.init.rodata` 后面挪到 `.init.data` 旁边并单独占一页：`.init_array`
是可写的，跟只读的 `.init.rodata` 挤在同一页里，会直接触发装载策略的
`OverlappingPageMappings`；单独占页之后它那段 RELRO 也才真的能被保护到（否则起点向上取整
就把区间取空了）。

### 5. `reclaim_init_area()` 此前是静默空转

```cpp
auto start = PhysMap::virt_to_phys(KERNEL_INIT_START);
```

`KERNEL_INIT_START` 是内核镜像的虚拟地址，不在 physmap 窗口里，`PhysMap::virt_to_phys()`
对它返回 0——首尾都是 0，接着 `end - start < PAGE_SIZE` 直接 return。也就是说 init 区从来
没有被真正回收过。现在走 `kernel_image_virt_to_phys()`（`KERNEL_PHYS_BASE + (va -
IMAGE_START)`）。顺带补上 `KERNEL_VIRT_BASE`——它一直只有声明没有赋值，`get_kernel_virt_base()`
到今天为止返回的都是 0。

`init_vmm.cpp` 的 `PHYS_VMOS` 预留表原先有两个空洞：`[__executable_start, __code_start)`
（`.dynamic`/`.rela.dyn`/build-id 那一段）和 `[__relro_start, __relro_end)`。两段都没有 VMA
覆盖，VmAspace 后续可以把这些地址再分出去，跟已加载的镜像重叠。补了 `k:head` 和 `k:relro`，
现在整张表按镜像顺序排列且无空隙。

### 验证到什么程度

## CpuLocal 改回 Linux 的寻址模型（model B）

原来的实现是 model A：`%gs` 装当前 CPU 的 unit 绝对基址，访问位移是变量在 unit 内的偏移。
现在改成 Linux x86-64 用的 model B：`%gs` 装 `CPU_OFFSETS[cpu]`（即 `base(cpu) - origin()`，
Linux 的 `__per_cpu_offset[]`），访问位移是变量自己的地址。

跟着改的是"货币"。调用方过去拿裸 offset，`resolve()` 每次要补一次 `origin +`；现在拿
handle（`origin + offset`），静态变量的 handle 就是 `&var`，动态分配的 handle 由
`Mapper::handle_of_address()` 换算——和 Linux `mm/percpu.c` 的 `__addr_to_pcpu_ptr()`
是同一件事。于是静态和动态用同一条加法解析，`PerCpu` 里存的也从 `m_offset` 变成 `m_handle`，
空值从 `~usize(0)` 变成 0（handle 永远不会落在 0 附近，可以直接用 null 表示空）。

改动的文件：`kernel/mm/cpu_local.cpp`、`kernel/mm/include/ours/mm/cpu_local.hpp`、
`kernel/arch/x86/kernel/include/ours/arch/cpu_local.hpp`、
`kernel/arch/x86/kernel/include/ours/arch/x86/percpu.hpp`、
`kernel/kernel/prof/prof_console.cpp`（`.offset() == NOWHERE` 改成 `!g_buffer`）。
`start.S` 里那条 `.extern __cpu_local_start` 一并删掉，已经没人用了。

### 顺带修掉了上面记的那个构建失败

前面"验证到什么程度"一节记的 `kernel.syscall.S.o` 失败——`CPU_LOCAL_ACCESS` 宏在汇编里做
`VAR - __cpu_local_start` 减法而该符号由链接脚本提供——正是 model A 无法在汇编侧成立的表现。
汇编器的原话是 `symbol '__cpu_local_start' can not be undefined in a subtraction expression`。
model B 不需要这个减法，宏变成：

```
#define CPU_LOCAL_ACCESS(VAR) % gs:(VAR)(% rip)
```

`(%rip)` 不是可选的。vmours 是链接在 0、由 `ElfImage::relocate()` 重定位的 static PIE，
绝对位移会把链接期地址编码进指令，镜像一搬就读错地方。Linux 的 `__percpu_rel` 是同一个理由。

### 验证到什么程度

用 `out/bringup.x86/compile_commands.json` 里的真实 flags 编了 `cpu_local.cpp`、
`object_cache.cpp`、`descriptor.cpp`、`prof_console.cpp`，无 error（只剩 `pm_node.hpp`、
`thread.hpp` 里既有的 thread-safety 告警）。`syscall.S` 和 `start.S` 用同一套 include/define
汇编通过，反汇编确认三处 percpu 访问都变成了 `%gs:(%rip)` 加 `R_X86_64_PC32 X86_PCPU`
重定位，addend 分别是 0 和 0x10，对得上 `sp0` 在 4、`sp2` 在 20 的布局。

`clang-format` / `clang-tidy` 对动过的文件干净；剩下的是 `CPU_OFFSETS` 这类
SCREAMING_SNAKE 静态量的 `readability-identifier-naming` 和整个 `Mapper` 访问器的
`modernize-use-nodiscard`，都是既有告警，不在本次改动引入的行上。

整树链接过了：`ninja -C out/bringup.x86 -k 0` 119/119，exit 0，`vmours` 和
`vmours.with-tests` 都链出来了，OBI 镜像也打包成功。上面记的 `kernel.syscall.S.o` 失败
随 model B 一起消失。

反汇编核对了 `vmours` 里 syscall 入口的三处 percpu 访问，位移全部落在正确的字段上：

```
__cpu_local_start = X86_PCPU = 0x6c000     __cpu_local_end = 0x7e7f8

7103: movq %rsp, %gs:0x64f09(%rip)   → 0x710b+0x64f09 = 0x6c014 = X86_PCPU+20 (user sp)
710b: movq %gs:0x64ef1(%rip), %rsp   → 0x7113+0x64ef1 = 0x6c004 = X86_PCPU+4  (kernel sp)
7156: movq %gs:0x64eb6(%rip), %rsp   → 0x715e+0x64eb6 = 0x6c014 = X86_PCPU+20
```

### 顺带量出来一个隐患

实测静态区 `0x7e7f8 - 0x6c000 = 0x127f8`（约 74KB），于是
`static_span = 76KB`、`unit_size = 92KB`、`chunk_span = 92KB × 16 = 1.4MB`。
Dense 的门槛是 `chunk_span ≤ ARCH_CPU_LOCAL_CHUNK_SLOT = 2MB`，**只剩约 36KB 余量**：
静态 per-CPU 数据再涨 36KB，Dense 就掉进 Scattered，而 Scattered 不能 grow。

`MAX_CPU` 从 16 提到 32 会立刻触发：那时 unit_size 上限变成 `2MB / 32 = 64KB`，
比现在的 92KB 还小，Dense 直接失效。也就是说 **`ARCH_CPU_LOCAL_CHUNK_SLOT` 是个跟
MAX_CPU 强耦合的硬编码值**，扩 CPU 数之前得先把它改成从 `chunk_span()` 推出来。

### QEMU 启动：走到 CpuLocal::init_early() 之后三重故障

`scripts/qemu-boot.sh`（SMP=1）跑起来了，phys 链路全通，串口 marker 停在 `U`：

```
AJKSGC <ctor indices> B L H U
                            ^ CpuLocal::init_early() 之后，task::init_early() 之前
```

`-d int,cpu_reset` 抓到的是 #PF → #DF → Triple fault：

```
v=0e e=0000 cpl=0 IP=0010:ffffff8840023270 CR2=fffffff7dfd34004
```

`0xffffff8840023270` 是 `ours::mm::current_node()`，整个函数就一条指令：

```
movl %gs:0x4, %eax
```

**位移是 0x4。** 来源在 [pm_node.hpp:417](kernel/mm/include/ours/mm/pm_node.hpp)：

```cpp
class PmNode::Current: public CpuLocal::Current<PmNode *> {
    static auto nid() -> NnId { return CpuLocal::read(CURRENT_INSTANCE->m_id); }
```

`CURRENT_INSTANCE` 是个 `CPU_LOCAL PmNode *`。`CURRENT_INSTANCE->m_id` 在编译期
解引用了模板里那份（值为 0 的）指针，于是 `&(nullptr->m_id)` = 4，被当成 handle 交给
`%gs`。`hard_affinity()` 和 `nid(CpuNum)` 是同一个写法，同样坏。

### 这不是 model B 引入的

两种模型对同一个对象算出的线性地址必然相同：

```
model A: gs = replica              位移 = 4 - origin   → replica + 4 - origin
model B: gs = replica - origin     位移 = 4            → replica - origin + 4
```

完全一致。这三个访问器在 model A 下会踩同一个地址。之所以以前没暴露，是因为
`vmours` 根本链接不出来（见上面 `syscall.S` 那一节）——现在链得出来了，第一次真跑，
就撞上了。

### 还有第二层问题

`current_node()` 在 `task::init_early()` 里就被调到，而 `PmNode::Current::set()`
要等 `PmNode::Current::init()`（gktl::InitHook）才会给 `CURRENT_INSTANCE` 填值。
就算把访问器改成先读 per-CPU 指针再解引用，这时候读到的仍是空指针。

`STATIC_CPU_TO_NODE` / `DYNAMIC_CPU_TO_NODE` 这两个普通静态数组看起来正是为这个早期
窗口准备的，但 `nid()` 没有走它们。**未决**：`nid()` 该不该改成读
`DYNAMIC_CPU_TO_NODE[cpunum]`。

### 修法：Thread 多一个不分配栈的构造接口

不让 IdleThread 兼任启动线程，而是给 `Thread` 加一个与 `spawn_etc()` 并列的入口：

```cpp
static auto create_first(KoId, char const *, sched::BaseProfile const &, Self *) -> void;
```

它只 placement-new 出 `Thread`、用 `Stack::init_first()` 采纳当前正在跑的那个静态栈，
然后挂进 `SPAWNED_THREADS`。`spawn_etc()` 里其余三步都不做：`m_task_state.init()` 和
`m_arch_thread.init()` 描述的是一个还没开始跑的线程，而 `Scheduler::on_thread_init()`
会做 CPU 索引的 `Scheduler::Current` 查找，这时 CpuLocal 只装了当前 CPU 的 offset。
对标 Zircon 的 `ConstructFirstThread()`。

`task::init_early()` 改成用它建一个静态的 `BOOT_THREAD`，`IdleThread` 一行没动
——所有 CPU 的 idler 本来就由 `task::init()` 统一建，之前 early 那次是重复的。

**生效了**：marker 走到了 `T`，`init_arch_early()` 跑完（IDT/IST 绑定日志都打出来了），
`X` 也打出来了。

### 下一个：任何异常都会变成三重故障

现在死在 `init_platform_early()` 里。第一个内核态异常是 #GP：

```
92: v=0d e=0000 cpl=0 IP=0010:ffffff884002247f
```

`0x2247f` 在 `ours::mm::PmNode::init()`，指令是 `movq %r14, (%rax,%r12)`，
`%rax` 来自 `movq 0xc8(%r13), %rax`。无错误码的 #GP 基本就是非规范地址。

**但这个 #GP 现在没法诊断**，因为紧接着：

```
93: v=06 IP=ffffff88400061d0    ← #GP 的 stub
94: v=06 IP=ffffff8840006160    ← #UD 的 stub
... 反复 ... → #DF → Triple fault
```

`0x61d0`/`0x6160` 是 ISR stub，第一条指令都是 `clac`（`0f 01 ca`）。
[idt.S:38](kernel/arch/x86/kernel/idt.S) 无条件发这条指令，注释还是从 Zircon 抄来的：

> DO NOT REMOVE THIS CLAC, code in idt.c assumes it is here.

Zircon 那句的意思是 **`idt.cc` 会在运行期把它 patch 成 NOP**（没有 SMAP 时）。
ours 没有这段——`grep -i 'smap\|clac' kernel/arch/x86/kernel/idt.cpp` 空，
`ours_kernel_has_code_patches = false`。

于是在任何不支持 SMAP 的 CPU 上（QEMU 的 Nehalem 模型，以及 Broadwell 之前的所有真机；
内核本身也只按 `-march=x86-64-v2` 编译），**第一个异常就会滚成三重故障，真正的错因被吞掉**。

顺序：先解决 clac，否则后面每一个 bug 都只能看到 Triple fault。

### 第一步：让 IDT 跳过 clac，而不是改写代码

Zircon 的 `idt_setup()` 不打补丁——它把门的入口地址往后挪过那条指令。ours 的
`idt.S` 把 IDT 铺成 256 组 `.quad <stub>; .quad 0`，`rectify_idt()` 再把每格改写成真正的
门描述符，所以只要在改写时给地址加上 `CLAC_SIZE`（3）即可：

```cpp
auto const clac_shift = x86_has_feature(CpuFeatureType::Smap) ? usize(0) : CLAC_SIZE;
```

stub 只能经 IDT 进入，没有别的路径会碰到被跳过的那条指令，也不需要把代码页改成可写。
跳过还是语义正确的：AC 只对 SMAP 有意义，没有 SMAP 时本来就没有东西要清。
`x86_has_feature()` 自己跑 CPUID，不依赖任何特性缓存，早期调用安全。

**生效了**：不再有 #UD 级联，#GP 真的进到了 C++ 处理器。

### 第二步：fault 型异常必须 panic，不能返回

`x86_dispatch_exception()` 里这些异常全是 `log::info("#XX"); break;`——打一行就返回。
对 fault 型异常（CPU 压的是**触发指令自身**的地址）这等于原地重犯，于是变成无限循环：
QEMU 的 `-d int` 日志涨到 37GB，串口刷满同一行 `#GP`。

把 16 个 fault 型异常改成 `panic_exception()`；#DB、#BP 是 trap（压的地址已经越过指令），
NMI 是外部事件，这三个保持原样。`panic_exception()` 同时改成转储现场——内核态异常没有
别的见证者，halt 之后不会再有输出，所以指令地址、错误码和寄存器必须当场打出来。`rip`
额外打一个镜像内偏移，因为 vmours 是重定位的 static PIE，绝对地址每次都不同，而偏移可以
直接拿去 `llvm-objdump -d` 里查。

### 第三步：#GP 的根因是 PmNode 从来没被创建

有了现场，一次就定位了：

```
#GP General protection fault: vector=13, error_code=0x0
  rip=0xffffff884002282f (+0x2282f)  cs=0x10
  rax=0x17f9705b60f0001  r12=0x0  r13=0x0  r14=0xffffff801fed59b8
```

```
22828: movq 0xc8(%r13), %rax     ; r13=0 → 读地址 0xc8
2282f: movq %r14, (%rax,%r12)    ; rax 非规范 → #GP
```

低端内存被 phys 阶段恒等映射着，所以读 `0xc8` 不报 #PF，读出来的是实模式 IVT 的残留，
拿它当指针写才炸。`r13` 是 `zone_queues()` 的返回值，而它就是 `&m_zone_queues`——说明
`this` 是空的。

根因在 `PmNode::bootstrap()`：

```cpp
// Create all nodes.
nodes.for_each([](NnId nid) {});      // 空的

// Initialize all nodes.
nodes.for_each([](NnId nid) {
    auto const status = PmNode::node(nid)->init();   // NODES[nid] 仍是 nullptr
```

"Create all nodes" 这一步从来没写过。而 `NODES[m_id] = this` 恰恰是 `init()` 的最后一行，
形成循环依赖：没有任何地方分配 PmNode。`OURS_DEBUG=0` 把 `init()` 开头的 canary 校验编掉了，
所以空指针一路走到底才暴露。

跟 CpuLocal 无关。**未决**：节点该怎么分配——`init()` 里的 PmZone 走的是
`EarlyMem::allocate<PmZone>(1, m_id)`，同样的形式大概就是答案。

### 一路修下去：三个从没写过的初始化步骤

装上现场转储之后，故障一个接一个暴露出来，都是同一类问题——写好了框架，中间一步没落地：

1. **`PmNode::bootstrap()` 的 "Create all nodes" 是个空 lambda。** `NODES[nid]` 永远是空，
   下一句就在空指针上调 `init()`。补上创建，并把 `NODES[nid]` 的登记从 `init()` 末尾挪到
   创建处——后面的 `connect()` 要跨节点走，整张表必须先填满。
2. **`MemoryModel::init()` 把 root section 表分配到局部变量就丢了**，`m_root_section`
   被读四处、从来没被写过。加一行赋值。
3. **`Impl::allocate()` 把 `gaf` 参数整个忽略。** PMM 路径硬编码 `GAF_KERNEL`，早期路径
   直接走 `EarlyMem::allocate` 不清零。section 表把"没有条目"编码成全零条目，拿到未清零的
   内存就变成一堆随机的 present 条目指向前一个占用者留下的东西——那个反复出现的
   `0x3f8832424448b40` 其实是残留的机器码。修法是让它真的按 `gaf` 办事，
   `Gaf::Zero` 在早期路径上手工清零（`GAF_KERNEL` 是 `ThisNode|Reclaim|Write`，
   不像 `GAF_BOOT` 那样自带 `Zero`）。

三个都跟 CpuLocal 无关。现在启动停在 `FrameBuddy::release_inner()` 末尾的 `ud2`——
编译器在不可达路径上插的陷阱，说明合并循环走到了它认为不可能的分支。**未查。**

### MemoryModel 重构：编译期二选一，CRTP

按用户的设计改成两个互斥的实现，`MemoryModel` 只是选中那个的名字：

- `priv::MemoryModel<Derived>`（[priv/memory_model.hpp](kernel/mm/include/ours/mm/priv/memmap.hpp)）
  是 CRTP 基类，装两个模型共享的那一半：遍历节点和 zone、判断哪些 pfn 是真的、初始化每个
  描述符。模型之间真正的差别只有两件事——pfn 怎么变成 `PmFrame *`，以及一个范围的描述符
  怎么被创建出来——这两件事留给派生类。
- 用 CRTP 而不是虚函数：`pfn_to_frame()` 压在内核每一次物理内存查找下面，必须完全内联掉；
  虚表会在这条路上放一次间接调用。它同时把"用哪个模型"变成编译期事实，这正是"只编译其中
  一个"得以成立的前提。
- `SparseModel` 就是原来那个 `MemoryModel`（多级 section 表），
  `priv::VflatModel`（[priv/vflat_model.hpp](kernel/mm/include/ours/mm/priv/vflat_memmap.hpp)）
  是一整块按 pfn 直接索引的 `PmFrame` 数组，落在保留虚拟窗口里，对标 Linux 的
  SPARSEMEM_VMEMMAP。
- 开关是 `mm_vflat_model`（[kernel/kernel_params.gni](kernel/kernel_params.gni)），
  经 `config("memory")` 变成 `MM_VFLAT_MODEL`；`kernel/mm/BUILD.gn` 据此只把选中的那个
  `.cpp` 放进 sources，未选中的那个根本不编译。

**验证**：默认构建的 `compile_commands.json` 里只有 `memory_model.cpp`，
`gn gen --args='mm_vflat_model=true'` 之后只有 `vflat_model.cpp`。默认路径启动后停在
完全相同的 `#UD`、寄存器逐个一致，确认这一步是纯重构、没有行为变化。

### 再改一版：按 Linux 的方式缩小接口

Linux 的 memory model 根本不是一个对象。`include/asm-generic/memory_model.h` 整个接口
就是两个宏加一个函数——`__pfn_to_page` / `__page_to_pfn` / `pfn_valid()`——三个模型
（FLATMEM / SPARSEMEM / SPARSEMEM_VMEMMAP）的差别**只有这两个表达式**。memmap 的建立在
`mm/mm_init.c`，section 表在 `mm/sparse.c` 的文件内静态变量里，都不属于"模型"。

对照之下，上面那版 CRTP 是在解决一个不该存在的问题：把 memmap 建立塞进模型，才需要一个
基类让两个模型"共享"它。而它本来就不需要属于任何模型——它只是碰巧调用 `pfn_to_frame()`。

（顺带核实：单例 `get()` 并没有静态初始化 guard 的开销，两个模型都是平凡构造、常量初始化。
所以这一条不成立，不是缩小接口的理由。）

第一步，把 memmap 建立搬出去：

- 新增 [memmap_init.hpp](kernel/mm/include/ours/mm/memmap_init.hpp) /
  `memmap_init.cpp`，对标 `mm/mm_init.c`。`init_memory_model()` 负责模型自己的前奏加
  遍历所有可用范围调 `add_range()`；`init_memmap()` 负责按 zone 填描述符。四个内部函数
  `init_memmap_zone/range/reserved` 都是匿名命名空间里的自由函数。
- CRTP 基类 `priv::MemoryModel<Derived>` 整个删除，两个模型都不再有基类。
- section 算术（`pfn_to_secnum` 等）从 `priv` 提到 `ours::mm`：`PmFrame` 无论哪个模型
  都带一个 secnum，这不是 sparse 的私事。
- 新增自由函数 `pfn_valid()`，对标 Linux 的同名函数。
- `init_pmm.cpp` 的 `MemoryModel::get().init(true)` 换成
  `init_memory_model()` + `init_memmap()` 两句。

## FrameBuddy 的 ud2:memmap 没清零

那个 `ud2` 不在合并逻辑里,是**侵入式链表的断言**。反汇编 `release_inner()` 里跳进 `ud2` 的三条分支:

```
leaq 0x10(%rsi), %rax    ; rax = &frame->m_hook
movq 0x10(%rsi), %rdx    ; rdx = frame->m_hook.next
testq %rdx, %rdx
je   ok                  ; next == null → 未挂链
cmpq %rax, %rdx
jne  ud2                 ; 既不是 null 也不指向自己 → 陷阱
```

`PmFrame::m_hook` 是 `AutoUnlink` 模式的 `ListMemberHook`,未挂链的表示就是全零。而描述符由
`SparseMemMap::activate_section()` 经 `Impl::allocate<PmFrame>(..., GAF_KERNEL, nid)` 分配,
`GAF_KERNEL` 不含 `Gaf::Zero`,早期路径又走不清零的 `EarlyMem` —— 于是 hook 里是上一位占用者
留下的字节,第一次 `insert_frame()` 就炸,而且是以"不可达路径陷阱"的形式炸,栈上什么线索都没有。

`PmFrame::init()` 补不了这个洞:它只对真实存在的 pfn 调用,而 section 里每个描述符
（包括空洞的）最终都会上某个链表。修法是给那次分配加 `Gaf::Zero`。Linux 能用
`memblock_alloc_try_nid_raw` 分配未清零的 memmap,正是因为 `__init_single_page()`
第一句就是 `mm_zero_struct_page()`——同样的代价,晚一页付。

## 顺序:build_memmap 提到 PmNode::bootstrap 之前

`build_memmap()` 原来用 `PmNode::for_each_nid(Possible)` 外套 `visit_usable(nid)`,而
`bootmem` 本来就在每个 region 上标了 `region.node`——这个对 PmNode 的依赖是假的。删掉之后
`build_memmap()` 就能排到 `PmNode::bootstrap()` 前面,描述符先于 zone 存在。Linux 的
`sparse_init()` 同样直接读 memblock、从不碰 `pg_data_t`,所以 `free_area_init()` 能把它排在
per-node 循环之前。

顺带修掉 `PmZone` 构造函数的初始化列表:它从 `m_name` 直接跳到 `m_flags`,`m_node` 和 `m_nid`
从未初始化,`nid` 参数根本没用上。zone 内存同样来自不清零的 `EarlyMem`,所以 `which_node()`
返回垃圾,而 `PmNode::get_frame_from_zone_queues()` 正拿它做节点过滤。

## 现在卡在哪:buddy 空转

不再有异常,改成静默挂起。用 QEMU monitor 采样 RIP 定位(`-monitor telnet:...`,
`info registers` + `x/48gx $rsp`):

```
RIP = +0x22819  ours::mm::PmNode::alloc_frames() 的重试循环
栈:  alloc_frames() ← CpuLocal::Mapper::build_dense()
     ← Mapper::init() ← CpuLocal::init()
```

`PmZone::alloc_frames()` 返回空,`PmNode::alloc_frames()` 于是 `reschedule()` 后无限重试——
此时既没有回收守护线程,也没有别的线程能让出内存。两个问题:

1. **`EarlyMem::do_handoff()` 跑完之后 buddy 依然拿不出内存。** `do_handoff()` →
   `free_unused_memory()` → `visit_free()` → `free_frames_phys_range()`,要查这一条链
   到底放进去了多少。
2. **启动期无限重试本身就是 bug。** 没有回收能力时应该直接失败返回,让调用方拿到
   `OutOfMem`。Linux 的 `__alloc_pages_slowpath()` 会查 `gfp_mask & __GFP_DIRECT_RECLAIM`
   以及回收是否真的可能,不可能就走 `nopage`。

### 排查 buddy 空转:排除了三条,还没定位

**已修(真 bug,但不是这次的原因)**:`free_frames_pfn_range()`(`kernel/mm/early_mem.cpp`)
把 bootmem 的空闲区间还给 buddy 时,只按剩余长度缩 order,**从不检查 `start` 是否按
`2^order` 对齐**。buddy 用 `pfn ^ BIT(order)` 找伙伴,这个式子只对对齐块成立;喂进去错位块,
合并就会去动不相干的邻居。Linux 的 `__free_pages_memory()` 第一行就是
`order = min(MAX_PAGE_ORDER, __ffs(start))`,补上了。

**排除的三条**:

1. `PmZone::free_frame()` 的 pcpu 分支确实是空 lambda(帧会被丢掉,`m_managed_frames`
   还照记),但 `MAX_PCPU_CACHE_ORDER == 0`,`order < 0` 恒假 —— 这段是死代码,现在伤不到人。
   等 pcpu cache 真要启用时它会立刻变成事故。
2. `PmZone::alloc_frames()` 开头的 `is_below_high_wmark()` 早退。它读的是
   `Flags::BelowHighWmark`,而构造函数只设 `Flags::Initialized`,全树没有一处设过这个位。
   顺带一提 `m_watermarks` 这个成员**声明了,全树零引用**。
3. 对齐修好之后 RIP 和栈完全没变,所以对齐不是这次挂起的原因。

**仍未解释**:`m_fset.acquire_frame(order)` 为什么拿不出东西。`build_dense()` 要的是
order 4/2/1/0 这种小块,`do_handoff()` 应该已经把大部分内存以 order 10 的块放进去了。
下一步得看 `do_handoff()` 实际放进去多少 —— 需要插桩或者用 monitor 读
`PmZone::m_managed_frames`。

**留个工具**:静默挂起时不用改代码就能扒栈 ——
`sh scripts/qemu-boot.sh -monitor telnet:127.0.0.1:55599,server,nowait`,然后
`(printf 'info registers\n'; sleep 2) | nc 127.0.0.1 55599`,再 `x/48gx $rsp` 取返回地址,
用 `llvm-nm --numeric-sort` 反查符号。unix socket 不行,scratchpad 路径超过 104 字节上限。

### 定位到了:分配上下文从来没被填过

加了一行 `log::info` 报告 `do_handoff()` 实际交出多少内存,答案是 **14 个区间、126900 帧、
495 MiB** —— buddy 不空,问题在分配侧。

顺着 `PmNode::alloc_frames()` 往下:

```
alloc_frames() → alloc_frames_preamble()        ← 空实现
               → get_frame_from_zone_queues()
                   if (!context.allowed_nodes.test(zone.which_node())) return nullptr;
               → alloc_frames_slowpath()        ← while(1)
```

`alloc_frames_preamble()` 整个是个 TODO 桩,于是 `context.allowed_nodes` 保持默认构造(全零),
`test()` 恒假,**每个 zone 都被过滤掉**。而 `GAF_BOOT` 带 `DirectReclaim`,慢路径的 `while(1)`
既不 break 也等不到回收,就成了死循环。这是第六个"框架写好、中间一步没落地"。

修法:把调用方本来就有的 `fallback` nodemask 送进 context。`Gaf::ThisNode` 收窄到本地节点,
但只当偏好——交集为空时退回调用方的掩码,否则一个自己没有内存的节点就永远分不到东西。

### 接着是 nid() 那个 %gs:0x4

分配走通之后立刻 #PF 在 `movl %gs:0x4, %ecx`,正是本文档开头记的
`PmNode::Current::nid()`。`CURRENT_INSTANCE` 是个 per-CPU `PmNode *`,
`CURRENT_INSTANCE->m_id` 在**编译期**解引用了模板里那份空指针,折成常量 4 交给 %gs。

改成读 `DYNAMIC_CPU_TO_NODE[cpunum]`。不只是避开那个折叠——CURRENT_INSTANCE 要等
`PmNode::Current::init()` 这个 init hook 才有值,而分配远在那之前就开始问节点号了。
这正是 Linux 给 `early_per_cpu(x86_cpu_to_node_map)` 的角色。
`hard_affinity()` 和 `nid(CpuNum)` 是同一个写法,后者一并改了,前者**仍未修**。

### 现在卡在:自锁

```
RIP = +0x19cf0  ours::sync::spinlock::SpinLock<...>::acquire
栈:  CpuLocal::Mapper::build_dense → PmNode::alloc_frames
     → PmZone::alloc_frame → ... → FrameBuddy::release
```

单 CPU 上同一把锁被重入。第一次真实分配就撞上,大概率是 `alloc_frame()` 持锁期间走到了
释放路径(拆分高阶块时把两半放回去),而释放路径自己又去拿同一把锁。**未查。**

### 页表页来源改成分阶段分派

`alloc_table()`(`kernel/arch/x86/mm/page_table.cpp`)原来写死 `alloc_frames(GAF_KERNEL|Gaf::Zero)`,
也就是 buddy。这把每一次页表编辑都绑死在"buddy 已存在"之后:`CpuLocal::Mapper` 只是碰巧排在
buddy 后面才能用,`VflatMemMap::populate_memmap()` 排在前面,所以只能返回 `NotSupported`。

新增 `mm::alloc_page_table(size, alignment, node)` / `free_page_table()`(`ours/mm/pmm.hpp`),
按 `pmm_enabled()` 在 EarlyMem 和 buddy 之间分派,早期路径手工清零。对标 Linux 的
`alloc_low_pages()` 按 `after_bootmem` 分派。早期拿到的页表页不归还——`do_handoff()` 只放
bootmem 仍视为 free 的部分,而已分配的不是 free;内核页表本来也不释放。

这一步把 `VflatMemMap` 的阻塞解掉了,也让 `CpuLocal::Mapper` 那个私有 `m_aspace` 的理由消失。

### FrameSet 的锁挪到 PmZone

按设计,`FrameSet` 不该有自己的锁:zone 是唯一接触它的东西,而 zone 自己有锁。两把锁串在同一条
路径上,只是让"一次调用里既分配又释放"的代码有两个地方可以自锁。现在 `FrameSet::acquire_frame`
/ `release_frame` 无锁,由 `PmZone::alloc_frame` / `free_frame` 持 `PmZone::m_lock`。
`PmZone::m_lock` 此前声明了但全树无人使用。

### 现在卡在:自旋锁,位置未定

`RIP` 稳定落在 `ours::sync::spinlock::SpinLock<(Option)4>::acquire`。

到此为止能确定的就只有这一条。两次尝试定位都不可靠:

- 从 `$rsp` 附近捞返回地址捞到 `CpuLocal::Mapper::build_dense`,但那是栈上的陈旧值——
  改掉页表页来源之后同一个位置仍然自旋,而那条路径的形状已经变了。
- `RDI` 指向 `ktl::KMALLOC_CACHE` 区间内,看着像 slab 的锁;但 `MemCache` 根本没有
  SpinLock 成员(只有静态的 `CACHE_LOCK` mutex),而且采样发生在自旋循环**内部**,
  `RDI` 未必还是 `this`。

沿 `%rbp` 链回溯拿到了(内核带 `-fno-omit-frame-pointer`,链完整):

```
+0x19cf0  SpinLock<(Option)4>::acquire
+0x21783  MemCache::create(char const*, usize, usize, Option, Arc<MemCache>*)
+0x6ccc8  init_vm_cow_pages_cache()
+0x14839  gktl::set_init_level(InitLevel, int)
+0x68131  start_kernel
```

**所以 `init_pmm()` 整个跑完了** —— 之前两次定位(`build_dense`、slab 的 `KMALLOC_CACHE`)
都是从 `$rsp` 邻域挑出来的陈旧值,方向都错了。真正的位置是某个 init level 的钩子
`init_vm_cow_pages_cache()` 里建 cache。

`MemCache::init()` 的 `Guard{CACHE_LOCK}` 大概率被内联进了 `create()` 的帧,所以自旋的
很可能就是 `CACHE_LOCK`。而 `create()` 顶上那段注释写着,这个位置以前**已经因为同一把锁
死锁过一次**:

> No CACHE_LOCK here. It guards GLOBAL_CACHES, which init() below appends to under that
> same lock -- and Mutex is a plain CAS lock that stores the owning thread, so taking it
> here deadlocked the moment the first cache was ever created.

单 CPU 上要死锁只有两种可能:上一次获取没有配对释放,或者又递归了一次。
`init()` 在取 `CACHE_LOCK` 之前会先调 `NodeCache::on_mem_cache_init()`,那条路径会分配,
值得先看它有没有绕回来。

**下一步**:确认自旋的是不是 `CACHE_LOCK`(用 monitor 读它的 owner 字段),
以及是谁先拿住的。

**还没验证的**:SMP > 1、实机、`mm_vflat_memmap=true` 的完整链接。

### 补：`.init` 挪到尾部的 A/B 实测（2026-09-02）

你问挪到尾部会不会有问题，我用同一批目标文件、只换链接脚本做了 A/B（改动前的工作区脚本
vs 改动后），逐项核对。

**布局本身没问题**，两边完全对称：

| | 改动前 | 改动后 |
|---|---|---|
| PT_LOAD 数 | 10 | 10 |
| 文件大小 | 11884760 | 11885040（+280 B） |
| `__init_end == __executable_end` | 否（0x59000 / 0x83000） | 是（0x84000） |
| `.init.rodata.schedules` 归属 | `None`（孤儿） | `None`（孤儿，同上） |

几个本来担心的点都排掉了：`.bss` 变成 NOBITS 夹在中间之后，LLD 让它和后面的 `.init.text`
共用同一个文件偏移（都是 0x3f000），没有产生 0x29470 的文件空洞；`p_offset ≡ p_vaddr
(mod maxpagesize)` 依然成立，因为两侧边界都是页对齐的。`load_at()` 是按段各自 memcpy 的，

孤儿段、都是 0 字节——**`__schedules_start == __schedules_end`，调度类注册表是空的**。
`task.ld` 里 `*(.init.rodata.schedules)` 没有 `KEEP`，而链接开了 `--gc-sections`。这跟本次
改动无关，但 BUILD.gn:176 那段注释说加上 task.ld 就修好了注册表，实际并没有。

### 真正暴露出来的两个问题（未处理）

都不是「挪到尾部」引起的，而是因为 `reclaim_init_area()` 以前是静默空转、现在真的会还页了。

**1. `labour_routine()` 自己就在 `.init.text` 里。** `main.cpp:35` 调完
`reclaim_init_area()` 之后还继续往下执行——执行的正是刚刚交还给伙伴系统的那几页。只要别的
CPU 分到这些页写一下，正在跑的代码就被覆盖了。Linux 是把 `kernel_init` 标成 `__ref` 放进
`.ref.text` 专门避开这件事的；这里需要把调用点搬出 `.init.text`。

**2. `[__init_start, __init_end)` 从来没有被 unmap。** `reclaim_init_area()` 只还页，不动页表，
`k:init` 这个 VMA 也不销毁。还完之后内核仍然持有一段 RWX 映射指向已经属于分配器的物理页。
Linux 的 `free_init_pages()` 在还页的同时会处理直映射的权限。这里至少要 unmap，或者退一步
先去掉可执行位。

zcode 的 percpu 落地后整树能链接了，`./scripts/qemu-boot.sh` 现在一路走到内核里，早期

诊断手段记一笔，后面还会用：`qemu-boot.sh` 后面直接跟 QEMU 参数就行，
`-qmp unix:/tmp/ours-qmp.sock,server,nowait` 挂上之后用 `human-monitor-command` 发

### 第一站：`current_node()` 返回越界的节点号（已修）

现象是启动打完 `Released 14 regions, 126900 frames (495 MiB) to the buddy allocator`
之后彻底不动。RIP 冻在 `SpinLock::acquire()` 的自旋分支上，调用栈：

```
MAIN_ENTRY → start_kernel → set_init_level(PlatformEarly)
  → init_vm_cow_pages_cache()      ← 该级别上的 init hook
    → MemCache::create()
      → SELF_CACHE->allocate()  ==  MemCache::allocate(gaf, nid, cpu_cache)
        → SpinLock::acquire()   ← 永远拿不到
```

寄存器给出了根因：`RDX=1`，那是 `nid`；而这个构建 `NUMA_MAX_NODE == 1`，
`m_node_caches` 只有一个元素。`m_node_caches[1]` 读到的是紧跟其后的
`m_managed_hook`，被当成 `NodeCache *`；`NodeCache` 的第一个成员正是 `SpinLock lock`，
于是自旋在一个 `GLOBAL_CACHES` 的链表指针上——那个值恒非零，永远解不开。锁地址
`KMALLOC_CACHE + 0x78`、锁「值」`KMALLOC_CACHE + 0x100`（正好一个 `sizeof(MemCache)=0x88`
的步长），就是这么来的。

`nid` 为什么是 1：`STATIC_CPU_TO_NODE` / `DYNAMIC_CPU_TO_NODE` 初值全填 `NUMA_MAX_NODE`，
这是「还不知道属于哪个节点」的哨兵值，而唯一会覆盖它的是拓扑源——x86 上是 SRAT 解析，
非 NUMA 构建根本不编译进来（`x86_init_numa()` 一进门就 `return`），没有 SRAT 的机器也不会
提供。于是哨兵值一路留到 `current_node()`，被交给按 `NUMA_MAX_NODE` 长度开的数组去索引。

`MemCache::allocate(Gaf, NnId)` 里其实有 `DEBUG_ASSERT(nid < NUMA_MAX_NODE,
"current_node() returned an unusable node")`，但这个构建 `OURS_DEBUG=0`，断言被编掉了。

**修法**：在 `PmNode::bootstrap()` 里，确定了 possible 节点集合之后、创建/初始化各节点
之前，把仍然停在哨兵值上的 CPU 绑到第一个有内存的节点。位置必须在这里而不是
`PmNode::Current::init()`——那个 hook 挂在 `InitLevel::CpuLocal + 1`，而 slab 早在
`init_pmm()` 里就开始问自己在哪个节点了，差好几个 init level。Linux 用
`dummy_numa_init()` / `init_cpu_to_node()` 补的是同一个洞。也必须在 `PmNode::init()`
之前，因为那一趟要读 `STATIC_CPU_TO_NODE` 建每个节点的 hard affinity（顺带说明：修之前
所有节点的 affinity 掩码都是空的）。

启动确认卡点前移了。

### 第二站：`alloc_frames_slowpath()` 的 `while (1)` 空转（未修）

现在停在：

```
start_kernel → init_vmm() → mm::alloc_frames(GAF_KERNEL, 0)
  → PmNode::Current::alloc_frames → PmNode::alloc_frames + 0x100
```

也就是 `init_vmm_preheap()` 里分配 ZERO_PAGE 那一步。`-d int` 显示内核期间零异常，
是真死循环，不是缺页循环。

两件事叠在一起：

1. **`get_frame_from_zone_queues()` 拿不到帧**，尽管 buddy 里刚放进去 126900 个。
   循环体里 `movq 0xb8(%r13), %r14` 的 `%r13` 是 0——某个 zone/queue 指针是空的。低地址
   在 `x86_init_mmu_early()` 把 `pgd[0] = pgd[511]` 之后是通向 physmap 的，所以读 `0xb8`
   不会缺页，只会读到垃圾然后接着转。这是真正要查的那一个。
2. **`alloc_frames_slowpath()` 会把失败变成挂死**：`GAF_KERNEL` 带 `DirectReclaim`
   不带 `NoRetry`，而 `alloc_frames_direct_reclaim()` 和 `alloc_frames_direct_compact()`
   都还是 `return 0` 的桩，于是 `while (1)` 里没有任何一条路径能推进状态。在两个桩填上
   之前，这里至少应该跳出去让调用方拿到 nullptr、走到 `panic("Failed to allocate the
   zero page")`——那样至少能看见错误，而不是静默转圈。

## 十九、把断言真正打开（2026-09-02）

上一节那个越界索引本来是有断言守着的——`MemCache::allocate` 里写着
`DEBUG_ASSERT(nid < NUMA_MAX_NODE, "current_node() returned an unusable node")`——却什么
也没说就挂了。查下来 `DEBUG_ASSERT` 在**任何**配置下都是空的，三个问题叠在一起。

### 1. `assert.hpp` 测的是一个谁都没定义的宏

```c
#ifdef DEBUG
#define DEBUG_ASSERT(condition, ...)  ... ASSERT(condition, __VA_ARGS__) ...
#else
#define DEBUG_ASSERT(condition, ...)
#endif
```

构建定义的是 `OURS_DEBUG`（0 或 1，跟着 `kernel_debug_level` 走，见
`//kernel/products:kernel_debug` 和 `//build/switch:debug_level_*`），全树没有任何地方定义
`DEBUG`。`kernel/products/BUILD.gn` 里那段注释其实写对了——「`<ours/assert.hpp>` tests
OURS_DEBUG」——只是头文件没跟上。改成测 `OURS_DEBUG`。

保留 `if constexpr` 而不是换成 `#if`：这样即使诊断关掉，断言的条件和参数照样参与编译，
不会烂成「打开就编不过」。外层的 `#if defined(OURS_DEBUG)` 仍然要留，给那些根本没拿到这个
定义的 TU（宿主工具、测试）兜底——否则 `if constexpr (OURS_DEBUG)` 是编译错误而不是静默关闭。

### 2. `dev.dbg_1` 镜像连的是 `dbg.0` 工具链

`kernel/products/image/dev.dbg_1/BUILD.gn` 里依赖写的是
`vmours(//build/switch/set/dbg.0:kernel_${target_cpu}.dbg.0)`。`build/switch/set/dbg.1`
（`lk_debug_level = 1`）一直存在，但没有任何人引用——所以这个「调试镜像」在策略上跟
`kernel.dev` 是同一个东西。改成连 `dbg.1`。

现在要带断言启动就是：

```sh
IMAGE=$PWD/out/bringup.x86/kernel.dev.dbg_1.obi ./scripts/qemu-boot.sh
```

### 3. `panic()` 的 `{}` 吃掉字符串参数

打开之后第一条断言打出来是 `[error] Assertion failed on `——条件文本没了。原始串口字节确认
就是断在 `on ` 后面，不是被截断。

原因是 `ASSERT` 传给 `panic()` 的 `#condition` 是**字符数组**（`char const[7]`），不是指针。
同一段代码在 Apple 的 libc++ 下打印正常，在本项目那份 libc++（`_LIBCPP_ABI_NAMESPACE=__ours`
的定制构建）下，数组走到参数存储里没有被 decay 成 `const char*`，格式化出来是空。整数一直
是好的，所以之前没人注意到——日志里带 `{}` 的几乎都是数值。

修在 `panic()` 里而不是 `ASSERT` 里，因为断言的附加消息（`DEBUG_ASSERT(cond, "Error type
magic")`）同样是数组，一个地方修掉全部：`detail::as_format_arg()` 把 char 数组 decay 成
`std::string_view`，其余类型原样转发；外面套一层 lambda，是因为
`std::make_format_args()` 要左值，而 `as_format_arg()` 可能返回 prvalue，绑到 lambda 参数上
才能活过整个格式化调用。

改完输出变成 `Assertion failed on source`。

> 注意 logz4 自己的 `log::vlog` 路径没走 `panic()`，同样的数组参数问题在那边应该还在。
> 目前日志里带 `{}` 的字符串参数大多是 `char const *` 变量（指针，没问题），所以先记下来。

### 断言打开后抓到的第一个问题（未修）

```
MAIN_ENTRY → start_kernel → ccrt::init_global_static_objects()
  → __cxx_global_var_init → ours::time::Clock::override_source()
    → DEBUG_ASSERT(source)   ← source 是空的
```

静态初始化顺序问题。`Clock::CLOCK` 是 `static inline Clock`，它的构造函数
（`kernel/kernel/time/clock.cpp:5`）调 `override_source(&ClockSource::Default::get())`，而
`ClockSource::Default::get()` 返回的是 `*CLKEVT`——一个 `static inline ClockSource *`，初值
为空，只有 `ClockSource::Default::init()` 会填，而那要等到 `time::init()`，比全局构造晚得多。

也就是说 `Clock::Clock()` 拿到的是空指针解引用的结果，接着 `m_cycle_last = source->read()`
在 release 构建里就是一次对空指针的调用。它之所以没有当场炸，是因为
`x86_init_mmu_early()` 把 `pgd[0] = pgd[511]` 之后低地址是通向 physmap 的，读得到垃圾而不
缺页——和第十八节第二站是同一类掩盖。

顺带：默认的 `kernel.dev`（dbg.0）镜像行为不变，仍然停在第十八节第二站的 ZERO_PAGE 分配上，
本次改动没有引入回归。

## 二十三、`Clock` 的构造函数解引用空指针（2026-09-02）

`Clock::Clock()` 原来在构造函数里装 `ClockSource::Default::get()`，而它返回的是
`*CLKEVT`——一个只有 `ClockSource::Default::init()` 才会填的 `static inline ClockSource *`，
而那要等到 `time::init()`。`SystemClock::CLOCK` 和 `SteadyClock::CLOCK` 都是
`static inline`，构造函数跑在 `ccrt::init_global_static_objects()` 里，是 `start_kernel`
的第一件事，比 `time::init()` 早了十几级。所以那里的 source 恒为空，
`m_cycle_last = source->read()` 是一次穿过空 vtable 的调用。

之所以一直没炸：低地址在 `x86_init_mmu_early()` 把 `pgd[0] = pgd[511]` 之后是通向 physmap
的，读得到垃圾而不缺页——和第十八节第二站、第十九节那个是同一类掩盖。

改成从「没有 source」开始：`ticks()` 本来就对空 source 返回 0，`change_source()` 也本来就
把第一个真实 source 走 `override_source()`。构造函数现在只给 `m_canary` 上正确的 magic
（它原来是 0，一旦断言打开 `verify<Self>()` 就是下一个要炸的地方），其余字段显式清零。

`numerator_` / `denominator_` 保持 0 而不是 1/1：tick→ns 的比例是 clock source 的属性，在
它到来之前假装 tick 就是 ns 是个错误答案，而 0 会在 `update_time()` 的断言上变成可诊断的。
顺带说一句，**全树没有任何地方给 `Clock::numerator_` / `denominator_` 赋过值**，
`update_time()` 里的 `cycles_delta * numerator_ / denominator_` 目前必然除零——这在流程上还
没走到，先记在这里，`update_time()` 里加了断言把它变响。

## 二十四、把 CpuLocal 和堆从 `init_pmm()` 里拿出来（2026-09-02）

第二十二节记的第 2 条：挂在 `CpuLocal + 1` 的 `RegisterNode` 跑在第一次 `alloc_frames()`
之后，导致 per-CPU 的 `PmNode *` 是空的。追下去这不是 hook 注册错了级别，是**级别本身在撒谎**。

### 三个错位

1. **`CpuLocal::init()` 和 slab 都在 `init_pmm()` 里面**，而它们都不是物理内存管理器。
   放在那里的唯一理由是依赖顺序（per-CPU 区要从 buddy 拿页，slab 又要 per-CPU 区），
   但这个顺序约束被藏在了一个名字里根本没提它的函数内部。
2. **`InitLevel` 枚举的顺序和真实顺序不一致**：枚举里是
   `PlatformEarly → Heap → Vmm → CpuLocal`，而真实的起来顺序是
   `PlatformEarly → CpuLocal → Heap → Vmm`。所以 `CpuLocal` 这一级在数值上排在 `Vmm`
   后面，`main.cpp` 也就只能在 `init_vmm()` 之后才公布它。
3. `set_init_level(level, delta)` 会把**所有 level 小于 `level + delta` 的 hook 一次跑完**
   （`kernel/lib/gktl/src/init_hook.cpp`），所以公布顺序必须和枚举数值顺序一致，
   不能靠调用顺序纠正。

合起来的效果：`CpuLocal + 1` 读起来像「per-CPU 存储刚起来之后」，实际含义是
「`init_vmm()` 之后」，差了三级。

### 改法

先确认依赖链是可以理顺的，不是真的成环——关键一点是
**`CpuLocal::init()` 走的是显式节点号的 `alloc_frames(nid, gaf, order)`**
（`cpu_local.cpp:350,394`），只需要节点**编号**（一个普通静态数组），不需要
`CURRENT_INSTANCE`。`CpuLocal::Dyn::grow()` 里那个不带 nid 的 `alloc_frames` 是运行期路径，
不在 init 上。所以：

```
init_pmm()          memmap + PmNode::bootstrap（此处分配节点编号）+ init_memmap + buddy
CpuLocal::init()    要 buddy 和一个有效 nid，不要 CURRENT_INSTANCE
PmNode::Current::init()   要 CpuLocal + PmNode 对象；发布 CURRENT_INSTANCE
init_cache()        MemCache::init + init_kmalloc + init_memory_resource
init_vmm()
```

落地成四处改动：

- **`gktl/init_hook.hpp`**：`CpuLocalInternal/CpuLocal` 从 `Vmm` 之后挪到 `PlatformEarly`
  和 `Heap` 之间，枚举顺序即真实顺序。
- **`kernel/mm/init_pmm.cpp`**：`init_pmm()` 到 `EarlyMem::do_handoff()` 为止；新增
  `mm::init_cache()` 承接 `MemCache::init()` / `ktl::init_kmalloc()` /
  `ktl::init_memory_resource()` / `set_init_stage(InitStage::Pmm)`。
- **`kernel/top/main.cpp`**：`CpuLocal::init()`、`init_cache()`、`init_vmm()` 三步在
  `start_kernel` 里按依赖顺序显式驱动，每一级在它真正成立的地方公布。
- **三个 `Vm*CacheInit` hook** 从 `PlatformEarly` 挪到 `Heap`——它们都 `MemCache::create()`，
  本来就需要 slab；之前能跑是因为 slab 藏在 `init_pmm()` 里、恰好更早起来了。

顺带清掉 `init_vmm.cpp` 里重复的 `set_init_stage(InitStage::Pmm)`（`init_cache()` 里已经有
一处，而且位置相同）。

> **更正**：我一开始把 `init_vmm.cpp` 里那个空的 `init_heap()` 也当成残留桩删掉了，是错的
> ——那是**未来 vmalloc 实现**的占位。已经放回去，并且把我新加的那个改名成
> `mm::init_cache()` 让路：VMM 有它自己的堆（vmalloc，虚拟连续、物理离散，必须等地址空间
> 建好），和内核对象堆（slab + kmalloc）是两回事，不该抢同一个名字。`init_vmm_preheap()`
> 里的 "preheap" 指的也正是这个 vmalloc。

### 一条通用规则

**当 X 发生在另一个函数内部时，不要用 init hook 表达「紧接在 X 之后」。**
hook 适合承载「任何需要 X 的人」这种无序订阅；顺序约束属于调用方，就该写成显式调用，
并且级别要在它真正成立的地方公布。`InitLevel::Heap` 一直没人走到，也是同一个原因——
slab 实际在 `init_pmm()` 里起来，没有任何地方公布 `Heap`。现在有了。

### 验证状态

编译通过，`clang-format` / `clang-tidy` 干净，启动无回归。但**运行时效果还看不到**：
当前卡点 `task::init_early()` 在这一段之前，boot 还没走到这里。

## 二十五、`task::init_early()`：两个问题，第二个是编译器把 per-CPU 读折叠掉了（2026-09-02）

启动卡在 `(U)` 和 `(T)` 之间，也就是 `task::init_early()` 里。断言打开之后一共暴露出两个。

### 1. `CpuLocal::with_current()` 断言的是另一个掩码

```
task::init_early() → Thread::create_first() → SpinLock::acquire()
  → CpuLocal::with_current() → DEBUG_ASSERT(Cpu::online_mask().test(cpu))
```

`with_current()` 需要的是「调用它的这个 CPU 有没有可用的 per-CPU 单元」，也就是
`CPU_OFFSETS[cpu]` 有没有意义。这件事 `CpuLocal` 自己就在记：它有一份私有的
`STATES[State::Online]`，`init_early()` 里就给 BP 置上了（`cpu_local.cpp:748`）。

但断言查的是全局的 `ours::Cpu::online_mask()`，那是另一个问题的答案——「这个 CPU 走完架构
初始化了没有」——而 BP 要到 `init_arch_early()` **末尾**才被置位
（`arch/x86/kernel/init.cpp:86`），比 `task::init_early()` 晚一整步。于是在那之前的每一次
per-CPU 访问都会踩这条断言。改成查 `CpuLocal` 自己的 `has_unit(cpu)`。

（`for_each()` / `fold()` 也在遍历 `Cpu::online_mask()`。那是「该覆盖哪些 CPU」的语义问题，
不在当前流程上，先记着。）

### 2. `CpuLocal::access()` 被优化器整个折叠掉

改完上一条，卡点前进到 `init_early()` 末尾的 `DEBUG_ASSERT(thread)`：
`Thread::Current::set()` 之后 `get()` 回来是空的。反汇编说明了一切：

```
movq %r14, %gs:CURRENT_INSTANCE     ← set()：走 %gs 内联汇编
movq %gs:CURRENT_CPU_OFFSET, %rax   ← get()：读了偏移
leaq ...; callq strlen              ← 然后直接进 panic 路径，没有 test，没有分支
```

编译器在**编译期**就断定 `thread` 是空的。原因是 `access()` 写成了

```cpp
return *reinterpret_cast<T *>(reinterpret_cast<u8 *>(&t) + Self::read(CURRENT_CPU_OFFSET));
```

`&t + offset` 走出了 `t` 这个对象，而优化器有权假设从一个对象派生出来的指针仍然指向那个
对象——于是它把整个算术折掉，直接读 `CURRENT_INSTANCE` 的**模板副本**：一块清零的、除了
`init_early()` 的 memcpy 之外没人写过的镜像。写那条之所以没事，是因为它走 `%gs` 内联汇编，
优化器看不透。

修法是给指针加一道屏障，让编译器无法把结果和 `t` 关联起来——一个空 asm，指针进、指针出：

```cpp
FORCE_INLINE static auto relocate(void *base, isize offset) -> void * {
    auto *address = static_cast<u8 *>(base) + offset;
    asm("" : "+r"(address));
    return address;
}
```

这正是 Linux 的 `RELOC_HIDE()`，用在同一个地方、出于同一个原因。改完生成的是真实计算：

```
leaq CURRENT_INSTANCE(%rip), %rax
movq %gs:CURRENT_CPU_OFFSET, %rcx
addq %rax, %rcx
```

**这一类坑不是第一次出现**：`pm_node.hpp` 里 `nid()` 的注释已经描述过同一现象的另一个变体
（`CURRENT_INSTANCE->m_id` 在编译期折成常量 4），当时的对策是绕开 `access()` 改读普通数组。
现在 `access()` 本身被修好了，那条绕行仍然成立（它另有「太早，指针还没发布」的理由）。

### 结果

启动一口气推进了好几步：过 `task::init_early()`、过 `init_arch_early()`、进
`init_platform_early()` → `init_pmm()`，走到 zone 建立，停在下一条断言：

```
[error] Assertion failed on !(flags() & Flags::Initialized) with message: Duplicated to initialize a frame
```

也就是 memmap 初始化里同一个 frame 被初始化了两次。这是下一站。

## 二十六、`kernel/time` 审查（2026-09-02）

只读不改。对照物：Linux `kernel/time/{clockevents,clocksource,tick-common,hrtimer,timekeeping}.c`
和 Zircon `kernel/kernel/timer.cc`。按「先炸的先列」排序，末尾给修复顺序。

### A. 事件链断在两处——现在没有任何调度 tick，也没有任何定时器会到期

**A1. `Timer` 到 `TimerScheduler` 是断的。** `TimerScheduler::activate_timer()` 是空函数
（`timer_scheduler.cpp:12`），`Timer::forward(Duration)` 也是空的（`timer.cpp:21`）；
`Timer::set_deadline()`、`Timer::forward(Time, Duration)`、`TickDevice::update_jiffies_tick/time()`、
`ClockSource::Default::init()` 都是**只有声明没有定义**。后果：`Thread::Current::sleep_etc()` 和
`WaitQueue::park_thread_postamble()` 里的超时永远不会触发——带超时的睡眠等于无限睡眠。

**A2. `TickDevice` 的周期处理函数只推进 jiffies。** `TickDevice::handle_periodic_event()` 做的全部事
情是 `ClockSource::Default::advance_ticks(1)` 再补编程下一次事件；它不调 `TickSched`，也不调
`task::Scheduler::Current::tick()`。全树唯一调 `Scheduler::Current::tick()` 的地方是
`TickSched::handle_event()`，而它只能由一个 `Timer` 驱动（A1 说了永远不会到期），且
`TickSched::emulate()` 全树无人调用，`time::init()` 是空函数。

Linux 的对应链是 `tick_handle_periodic()` → `tick_periodic()` → `do_timer()`（只在
`tick_do_timer_cpu` 上推进 jiffies）+ `update_process_times()` → `scheduler_tick()` +
`run_local_timers()`。方案：

1. `handle_periodic_event()` 里先判断 `Cpu::id() == ClockSource::Default::CPUNUM` 再推进
   jiffies（现在每颗 CPU 的设备都推，SMP 上 jiffies 跑 N 倍快；头文件里写的「Requires: 当前 CPU
   是 CPUNUM」没有任何代码兑现）。
2. 之后无条件调一个 `TickSched::on_tick(now)`：`Scheduler::Current::tick(now)` +
   `prof::Sampler` + `TimerScheduler::Current::run_local_queues()`。Legacy 模式下 `TickSched` 就
   是这个入口，不需要 `Timer`；HpTick 模式下才由 `Timer` 驱动同一个函数。
3. `time::init()` 里初始化 `ClockSource::Default`（把 `CPUNUM` 设成 BSP）并对每颗 CPU
   `TickSched::emulate(Legacy)`；AP 起来时在 `start_nonboot_cpu()` 里再做一次。

### B. 会立刻出错的正确性问题

**B3. `ClockEventDevice::program_event()` 的「现在」是 epoch 0。**
`clock_event_device.cpp:100` 写的是 `auto const now = TimePoint<>();`，于是 `delta = expiry - 0`
是绝对时间，永远被 `std::clamp` 钳到 `m_max_delta`——每次编程都是最大间隔。Linux
`clockevents_program_event()` 用 `ktime_get()`。改成 `SteadyClock::now()`。

**B4. `TickDevice::program_event()` 的「无穷」比较是错的。** 它拿
`ustl::NumericLimits<TimePoint<>>::max()` 当哨兵，但 `std::numeric_limits` 对 `time_point` 没有特
化，主模板的 `max()` 返回 `T()`——也就是 epoch 0。所以 `TimerQueue::update_next_deadline()` 在队列
为空时传进来的 `TimePoint<>::max()` 走不进 shutdown 分支，反而按 B3 的 `max_delta` 反复编程；
而一个恰好等于 0 的 deadline 会把设备关掉。改成和 `INFINITE_TIME` 比较。Linux 的对应是
`KTIME_MAX` → `clockevents_switch_state(ONESHOT_STOPPED)`。

**B5. `ClockEventDevice::entroll(self)` 的默认参数自相矛盾。** 它展开成
`entroll(self, HZ, 128, HZ)`：`min_delta = 128 > max_delta = 100`，`configure()` 第一行的
`DEBUG_ASSERT(min_delta < max_delta)` 必炸；LAPIC 定时器（`init_apic_timer()`）走的正是这条。
就算断言关着，`freq = HZ = 100` 会让 `m_scaler` 变成 1e7 ns/tick，LAPIC 的 delta 换算全错。
方案：删掉无参重载，LAPIC 用校准出来的频率调带参版本；Linux 的 `clockevents_config_and_register()`
就是三个参数全必填。

**B6. `TickDevice::rebind_device()` 有三个错。**
(a) `handler` 先被 `ustl::move` 进新设备，紧接着 Oneshot 分支又拿这个已被搬空的 `handler` 去
`switch_to_oneshot()`——oneshot 模式下换设备会丢掉处理函数。
(b) `irq::set_affinity(m_clkdev->irqnum(), m_clkdev->cpumask())` 用的是**旧**设备的中断号和掩码。
(c) `check_new_device()` 无条件接受：没有 rating 比较、没有 feature 检查、没有 per-CPU 优先。
LAPIC 只有 `Feature::Oneshot`，被绑到还处在 Periodic 模式的 `TickDevice` 上时
`switch_mode(Periodic)` 返回 `Unsupported`，返回值被丢弃，设备停在 `Detached`。
Linux `tick_check_new_device()` 的规则：新设备 cpumask 必须含本 CPU；per-CPU 设备优先于全局设备；
rating 高者胜；oneshot-capable 优先。`ClockEventDevice` 需要加一个 `rating` 字段。

**B7. `ClockSource::enroll()` 把频率丢了，通知也发错了对象。**
`hz` 参数没有任何用途；`SystemClock::notify(self)` 传的是 `self` 而不是刚选出的 `best`；只通知
`SystemClock`，`SteadyClock::CLOCK` 永远没有 source——而全树用的都是 `SteadyClock::now()`，
它会在 `update_time()` 的断言上停下（§二十三加的那条），断言关着就是除零。
`select_best_source()` 的 for 循环第一次迭代必 `break`，`Flags::Unstable` 完全不起作用；它读
`REGISTERED_SOURCES` 不拿 `REGISTERED_SOURCES_MUTEX`。
方案：`ClockSource` 记住 `freq` 并算出 `(mult, shift)`——`calculate_mult_shift()` 已经写好在
`mod.cpp` 里，全树无人调用；`Clock::override_source()` 从 source 取比例；enroll 先通知
`SteadyClock`；选择用 rating 并跳过 Unstable。

**B8. `Timer::cancel()` 只置位，而 `Timer` 是栈对象。** `run_expired_timers()` 从不检查
`m_cancalled`；`sleep_etc()` / `park_thread_postamble()` 里的 `Timer` 在线程被别的原因唤醒后
就析构了，但节点还挂在 `m_active_timers` 里——`~Timer()` 的 `DEBUG_ASSERT(!is_linked())` 先炸，
关掉断言就是 use-after-free。「懒删除避免锁竞争」的注释在栈对象上不成立。
方案照 Zircon `Timer::Cancel()`：拿队列锁摘链；若回调正在别的 CPU 上执行，自旋等
`active_cpu_` 回到 INVALID 再返回（`Timer::m_active_cpu` 字段已经有了，没用上）。Linux 对应
`hrtimer_cancel()` / `timer_delete_sync()`。

### C. 并发与锁

**C9. `TimerQueue` / `TimerScheduler` 没有任何锁。** `activate()` 来自线程上下文（`sleep_etc`
里在 `pi_lock` 下，IRQ 关着），`run_expired_timers()` 来自中断——同一个 `Set` 被两个上下文改。
Zircon 是每 CPU 一把 `timer_lock`（IrqSave 自旋锁），Linux 是 `base->lock`。方案：
`TimerScheduler` 持一把 per-CPU `SpinLock`；跑回调时先摘链、置 `active_cpu`、放锁，再调回调
（Zircon `TimerQueue::Tick()` 的顺序），回调里才能安全地重新 `activate()`。

**C10. `Clock::update_time()` 是「读时改状态」。** `now()` 在中断和线程里并发调用就会撕裂
`m_time_shift` / `m_cycle_last`；`m_seq` 声明了没用。另外 `cycles_delta * numerator_` 对 HPET
（14.3 MHz，`numerator_ ≈ 1e9`）几秒就溢出 64 位；32 位 source 还需要 mask（Linux
`clocksource->mask`）。建议照 Zircon `current_mono_time()`：`now = affine(read())`，读路径纯函数不
写任何东西，只在换 source 时在 seqlock 下改 base；换算用 `(mult, shift)` 或 `mtl::scale`（它已经是
128 位中间值）。

**C11. `ClockSource::Default::read()` 为读一个字拿 IrqSave 自旋锁。** jiffies 在 Linux 是一次
volatile 读。改 `std::atomic<Ticks>` relaxed 读；`advance_ticks()` 只在 CPUNUM 上调（见 A2）。

**C12. `HpetClockSource::m_cache` 不是原子的。** contended 路径在别的 CPU 上裸读，持锁方裸写。
Linux `read_hpet()` 用 `union hpet_lock` 的 cmpxchg。改 `std::atomic<u64>`。

**C13. `ClockEventDevice::GCED_MUTEX` 是睡眠锁，却用 `Guard<Mutex, IrqSave>`。** 现在只在 init 期
无争用地过一遍所以没事，但这个组合本身是错的。

### D. 未初始化与 canary——和 §二十三 `Clock` 同一类

**D14.** `TickDevice`、`TickSched`、`ClockSource`、`TimerQueue` 的 `m_canary` 都用了空构造
（magic 0），而各自的方法都 `verify<Self>()`：断言一开，`TickDevice::program_event()`、
`ClockSource::enroll()`、`TimerQueue::run_expired_timers()` 第一次进入就炸。
`TimerScheduler` / `TimerQueue` 没有构造函数，`cpunum_` / `m_cpunum` / `m_running` /
`m_clock_source` 全是垃圾；`Timer` 的 `m_queue` / `m_active_cpu` 同样没初始化。

**D15.** `NOOP_DEVICE` 是 `INIT_DATA`，但每 CPU `TickDevice` 的模板拷贝里 `m_clkdev` 指着它；
没拿到真实设备的 CPU 在 init 段回收后持有悬空指针。改成普通 static，或 `m_clkdev = nullptr`
并在 `program_event()` 里判空。

### E. 驱动侧

**E16. HPET `set_next_event_tick()` 没有「写完比较器再确认没错过」。** 读计数器、加 delta、写比
较器之间计数器还在走，delta 小时比较器一写就已经落后，oneshot 模式下这次中断永远不来，tick
停摆。Linux `hpet_next_event()` 写完后再读一次计数器，落后就返回 `-ETIME` 让上层重试。
`set_next_event_time()` 是空实现却返回 `Ok`，应在 vtable 里填 `nullptr`。

**E17. i8253 `set_mode_periodic()` 写的 latch 是 0**（=65536 分频，18.2 Hz），不是 HZ。Linux
`LATCH = (PIT_TICK_RATE + HZ/2) / HZ`。

**E18. LAPIC。** `set_next_event_tick()` 的除数编码索引错（§二十二第 2 条已记）；
`set_next_event_tick_deadline()` 的 `delta < 0` 对 `usize` 是死代码；校准
（`calibrate_apic_clock_single`）靠 `ClockSource::Default::read()` 被 PIT/HPET 的周期中断推进，
依赖 A2 那条链。

**E19. `arch_time_init()` 注册的是 virq 0，unmask 的是 `apic_io_isa_to_global(0)`。** 有 ISA
override（IRQ0 → GSI2 很常见）时两者不是同一根线。另外 `hpet.hpp` 的 `HPET_CLKEVT` /
`is_hpet_enabled()` / `hpet_enable()` / `hpet_disable()`，`arch/time.hpp` 的 `time::hpet_init()` /
`pit_init()`，`platform/timer.hpp` 的整套 `current_mono_ticks()` 等，都是悬空声明。

### F. 接口设计

**F20. `Deadline` 的隐式构造是个坑。** `Deadline(Duration)` 的含义是「自 epoch 起的绝对时刻」，
`Deadline()` 是 epoch 0。`thread.cpp:300` 的 `join(nullptr, time::Deadline())` 本意是无限等，
实际是「立刻超时」。`Timer::operator<` 按 `latest()` 排序，但 slack 的合并语义
（earliest/latest 区间）没有任何地方用到。建议照 Zircon：`Deadline::after(Duration, slack)` /
`Deadline::at(TimePoint)`，构造函数 `explicit`，默认值 = infinite；`TimeSlack` 带 mode
（Early / Late / Both）。

**F21. 两套时间表示并存。** `Ticks` / `Time` 都是 `usize`（`system/public/ours/types.hpp`），
和 chrono 的 `TimePoint<>` / `Duration` 并存；无符号让所有 `< 0` 检查失效。建议 `Ticks` 用
`i64`（Zircon `zx_ticks_t`），删掉 `Time`。`cfg.hpp` 用 `#define HZ` 且放在 include 之前，
污染全局命名空间，改 `constexpr`。

**F22. 杂项。** `m_cancalled` → `m_cancelled`；`entroll` → `enroll`；`ClockSource::Default` 的成
员叫 `CLKEVT`（它是 ClockSource，不是 ClockEventDevice）；`ClockSource::m_priority` 无人设置；
`SystemClock::now()` / `ticks()` 声明未定义，`REAL_BASE` 未用；`timer_queue.hpp` 尾注释写成
`TIMER-QUEUE`。

### 建议的修复顺序

按启动会先撞上什么来排，每步单独验证：

1. D14 / D15：canary 和未初始化字段——不修这个，断言一开什么都跑不到。
2. B7 + C10：`ClockSource` → `Clock` 的频率贯通，`now()` 改成纯函数——`SteadyClock::now()`
   能出正确时间，调度器和 mutex 自旋才有意义。
3. B3 / B4 / B5：`program_event` 的 now、无穷比较、`entroll` 默认参数。
4. B6：`check_new_device` 的 rating + feature + per-CPU 规则。
5. A1 / A2：把周期 tick 接到 `TickSched` → `Scheduler::tick()` → `run_local_queues()`。
6. B8 + C9：`TimerScheduler` 加锁、实现 `activate` / 同步 `cancel` / `forward`。
7. E：HPET 的错过检测、PIT 的 latch、LAPIC 的除数编码和中断号。
8. F：`Deadline` 接口、`Ticks` 类型、命名。

## 二十七、`kernel/time` 第一步：并掉 `TimerScheduler`，补齐 canary 与未初始化字段（2026-09-02）

对应第二十六节的 D14 / D15，外加一个你定的结构调整：**丢掉 `TimerScheduler`，让 `TimerQueue`
兼职它的工作**。

### 并入

`TimerScheduler` 除了一个 `TimerQueue perclock_[MaxNumClocks]` 数组和两个空函数之外没有任何自己
的状态，于是 `TimerQueue` 直接成为 per-CPU 对象（继承 `mm::CpuLocal::Current<TimerQueue>`，和
`TickSched` 一样），原来「每个 clock 一个 queue」变成它私有的 `ClockBase m_bases[]`——每个 base
是一个 `Set<Timer>` 加一个 `offset`，就是 Linux `hrtimer_cpu_base` 里嵌 `hrtimer_clock_base[]`
的形状；Zircon 的 `TimerQueue` 也是 per-CPU 对象、上面没有任何东西。`timer_scheduler.{hpp,cpp}`
删除，`Timer::activate()` 现在调 `TimerQueue::activate_timer()`（仍是空的，第六步填），
`TickSched::handle_event()` 调 `TimerQueue::get().run_expired_timers()`。

顺带去掉的：原 `TimerQueue::m_clock_source` 指针——没有任何读写，per-clock 的时间换算已经由
`ClockBase::offset` 表达。`m_next_timer_deadline` 提到队列一级（`m_next_deadline`），因为一颗
CPU 只有一个 tick 设备，「下一次编程时刻」是跨 clock 取 min 的，不属于单个 clock。

### 绑定 CPU 号

`TimerQueue` 的构造函数只跑在模板拷贝上，写不进 CPU 号。补了 `TimerQueue::init(cpunum)`，由
`time::init()` 从 BSP 遍历 `cpu_possible_mask()` 对每个 unit 调一次——照抄 `task::init()` 绑
`Scheduler` 的做法。为什么不放到 AP 自己的启动路径：BSP 上发起的 sleep / 等待队列超时可能在
AP 起来之前就要挂到它的队列上，队列若还是 `INVALID_CPU_NUM` 就不知道该编程谁的 tick 设备。
`time::init()` 之前是空函数，这是它的第一项工作。

### canary 与未初始化字段

| 对象 | 之前 | 现在 |
|---|---|---|
| `TickDevice` / `TickSched` / `ClockSource` / `TimerQueue` | `m_canary()`，magic 为 0，任何 `verify<Self>()` 必炸 | `m_canary(this)` |
| `TickSched::m_last_tick` / `m_next_tick` | 未初始化 | 0 |
| `TimerQueue::m_cpunum` / `m_running` / `m_next_deadline` | 未初始化 | `INVALID_CPU_NUM` / `nullptr` / `INFINITE_TIME` |
| `Timer::m_queue` / `m_active_cpu` / `m_cancelled` | 未初始化 | `nullptr` / `INVALID_CPU_NUM` / `false` |
| `TimeSlack::m_slack` | `= default` 构造留下未定值 | `Duration{}` |

### `NOOP_DEVICE`：比 D15 多出一个问题

## 二十六、`init_memmap()` 把同一段 frame 初始化两次（2026-09-02）

断言 `!(flags() & Flags::Initialized)` / "Duplicated to initialize a frame"。挂起时的寄存器
直接指出了现场：`R12 = R13 = 0x1000`（DMA/DMA32 边界）、`R15 = 0x1F8ED`（region
`[0x1EF02, 0x1F8ED)` 的结尾）。

`init_memmap_zone()` 在 zone 和 region 不相交时，返回的是**被 clamp 过的** `start`，也就是
一个 zone 边界，和 region 毫无关系：

```
region [0x1EF02, 0x1F8ED)
  zone DMA   [0x0, 0x1000)      clamp 后 start == end == 0x1000 → 不相交
                                但 return 0x1000，把调用方的游标拉回去了
  zone DMA32 [0x1000, 0x1FEF4)  于是从 0x1000 开始重新初始化到 0x1F8ED，
                                而 [0x1000, 0x1EE41) 是上一个 region 已经做过的
```

也就是说 0x1000 以上的每一个 region 都会让 DMA32 从头再来一遍。改成返回调用方原本的
`start`——「这一趟什么也没做，你的游标没动」。

（`init_memmap()` 的 zone 循环里还有一句 `hole_start_pfn = end_pfn;`，写的是 region 的结尾
而不是刚初始化到的位置。当前 zone 是连续的，所以结果一样；zone 之间一旦出现空隙就会漏掉
那段的 reserved 描述符。记录，未改。）

修完启动推进到：memmap 建好、126847 个 frame 交给 buddy、`CpuLocal::init()` 和
`init_cache()` 都通过——日志里开始出现 `cpu0` 前缀，per-CPU 日志生效了；第二十四节挪到
`Heap` 级别的三个 `Vm*CacheInit` hook 也在正确的位置跑了起来，**那次 init 顺序重构至此得到
运行时验证**。下一站：


## 二十七、`VmaCache` / `ThreadCache` 的 init hook 从来没被写出来（2026-09-02）

## 三十一、`k:padding` 把 cpu-local 窗口的第一页改成了只读（2026-09-02）

这一节是 dbg.0 镜像（`kernel.dev.obi`，`vmours.with-tests`）上撞到的，dbg_1 镜像暂时看不到：
它在第二十七节末尾那条 `Error type magic` 断言上就停了，而那是 `DEBUG_ASSERT`，dbg.0 里
编译掉了，于是 dbg.0 反而走得更远，在下一次拿自旋锁时缺页：

```
[cpu0 error] Unhandled page fault: vector=14, error_code=0x3
[cpu0 error]   rip=0xffffff884001a0f4 (+0x1a0f4)  rax=0xffffff8800000000
```

error_code 的 P|W 说明页在、但不许写。`+0x1a0f4` 落在 `SpinLock<>::acquire()` 里给
`sync.spinlock.num_held` 计数器做 `lock incq (%rax)` 的那条指令，`%rax` 是
`CpuLocal::with_current()` 算出来的 `&slot + CPU_OFFSETS[cpu]`。而 `0xffffff8800000000`
恰好等于 `KERNEL_ASPACE_BASE + ARCH_PHYSMAP_SIZE`，也就是 `aspace_layout.hpp` 里的
`ARCH_CPU_LOCAL_VIRT_BASE`：`CpuLocal::init()` 走的是 dense 布局，chunk 0 放在窗口第 0 个
slot，CPU 0 的 unit 从窗口起点开始，`__gktl_counter_start` 又是 unit 的第一个东西。

### 谁把它改成只读的

把 QEMU 的 gdbstub（`qemu-boot.sh -s -S`）接到 `/usr/bin/lldb` 上，`target modules load
--slide 0xffffff8840000000` 之后在 `ArchVmAspace::protect` 和 `panic_exception` 上下断点：

```
start_kernel → init_vmm() → init_vmm_preheap()      init_vmm.cpp:111 alloc_frames
  → PmNode::Current::alloc_frames → PmZone::alloc_frame → SpinLock::acquire → #PF
```

缺页之前最后一次 `protect()` 的实参是 `va=0xffffff8800000000, n=1, mmuf=Read`。它来自
`init_vmm_preheap()` 预置 VMA 表里的最后一项：

```cpp
{.name = "k:padding",
 .base = PhysMap::VIRT_BASE + PhysMap::SIZE,   // == ARCH_CPU_LOCAL_VIRT_BASE
 .size = MAX_PAGE_SIZE,
 .vmaf = VmaFlags::Read},
```

`entrol_preset_vma()` 对每一项都做 `create_subvma()` 再 `reserve()`，而 `VmArea::reserve()`
的最后一步是 `arch_aspace().protect(base, n, mmuf)`——"映射已经在了，只改权限"。对镜像各段
和 physmap 来说这正是想要的；对 `k:padding` 来说，它把 cpu-local 窗口的第一页改成了只读。

`k:padding` 比 cpu-local 窗口更早（a7d729e 之前就有），本意是在 physmap 尾巴上放一页护栏
防止越界写。后来窗口被安排在 physmap 紧后面，两者就重叠了，只是一直没人走到这里。

### 修法

不是把护栏挪走，而是承认这段地址空间有主。预置表里的 `k:padding` 换成 `k:cpulocal`，覆盖整个
`[ARCH_CPU_LOCAL_VIRT_BASE, +ARCH_CPU_LOCAL_SIZE)`，读写。`PhysVma` 加一个 `Backing`：

- `Mapped`：VMM 起来之前就已经映射好、且永远映射着的范围（镜像各段、physmap）。VMA 占住
  地址并把权限盖到已有映射上，原有行为。
- `AddressSpace`：只占地址。里面的页由别人（这里是 `CpuLocal::Mapper::build_dense()`）
  按需一个 slot 一个 slot 地映射并自己管理，VMM 不能碰、也不能假设它们已经映射。
  `entrol_preset_vma()` 对这种项做完 `create_subvma()` 就返回，不 `reserve()`。

覆盖整个窗口而不只是现在用到的 chunk 0，是为了以后 `Dyn::grow()` 再要一个 slot 时，不会撞上
VMM 已经分出去的地址。physmap 尾部的护栏在这个布局里没有位置可放；physmap 本身有自己的
VMA 划界，也不需要它。

修完 dbg.0 镜像越过了这里；dbg_1 还是停在第二十七节记录的 magic 断言上（这一节的问题在
它后面，修掉断言后 dbg_1 会在同一处受益）。dbg.0 的下一站就在同一个函数里，
`init_vmm_preheap()` 给零页做的那次 `alloc_frames(GAF_KERNEL, 0)`：

```
PmNode::Current::alloc_frames → PmNode::alloc_frames(this=0x0)
  → alloc_frames_slowpath → get_frame_from_zone_queues(ZoneQueues this=0x48)
```

`PmNode::Current` 的实例指针此时还是空的——`PmNode::Current::init()` 挂在更晚的 init
hook 上——`alloc_frames` 拿着空 `this` 去读 zone 队列，慢路径就此空转。这是另一个问题，
另起一节。

## 三十二、`PmNode::Current::init()` 从来没把节点指针发布到 per-CPU 槽里（2026-09-02）

第三十一节末尾记的下一站。dbg.0 越过预置 VMA 之后，`init_vmm_preheap()` 给零页做
`alloc_frames(GAF_KERNEL, 0)`，栈是：

```
PmNode::Current::alloc_frames → PmNode::alloc_frames(this=0x0)
  → alloc_frames_slowpath → get_frame_from_zone_queues(ZoneQueues this=0x48)
```

`PmNode::Current::get()` 返回的是 per-CPU 的 `PmNode *`，这里是空指针；dbg.0 没有
`DEBUG_ASSERT(local_node)`，就拿着 `this=0` 往下走，`&m_zone_queues` 算出 `0x48`，慢路径在
一个不存在的 ZoneQueues 上空转。

### 为什么是空的

用 lldb 在 `init_vmm` 上停下来看：

- `Cpu::STATES` = `{Possible: 0, Present: 0, Online: 1}`——possible mask 是空的。填它的
  `assign_cpunum_for_apic()` 是 `platform_init_apic()` 在 `InitLevel::Irq` 才跑的 MADT
  解析，而 `RegisterNode` hook 挂在 `CpuLocal + 1`，早了三级。`bootstrap()` 里那段"possible
  mask 已经填好了，MADT 在 `PlatformInitLevel::StartUp` 解析"的注释是错的，一并改掉。
- `DYNAMIC_CPU_TO_NODE[0] == STATIC_CPU_TO_NODE[0] == 0`：`bootstrap()` 的 `claim_cpu`
  用 `set_nid_early()` 把两张表都填成了 fallback 节点。
- CPU 0 那份 `CpuLocal::Current<PmNode *>::CURRENT_INSTANCE`（模板地址 `0x82080`，加
  `CPU_OFFSETS[0]` 后是 `0xffffff8800012080`）读出来是 0。

于是 `PmNode::Current::init()` 的两条路都走不到 `Current::set()`：

```cpp
Cpu::possible_mask().for_each(          // 空 mask，一个 CPU 都不迭代
    [](CpuNum cpu) { set_nid(cpu, STATIC_CPU_TO_NODE[cpu]); });
```

就算 mask 里有 CPU 0，`set_nid(0, 0)` 也会因为 `old_nid == new_nid` 提前返回——那个提前返回
对它本来的用途（运行时把 CPU 挪到另一个节点，没变就没事做）是对的，但首次发布指针不该借道它。

### 修法

`init()` 改成自己发布：对 possible mask 里的每个 CPU **加上正在运行的这颗**（和 `bootstrap()`
一样点名），读 `DYNAMIC_CPU_TO_NODE`，还在哨兵上的跳过（`bootstrap()` 之后才出现的 CPU，起来时
走 `set_nid()`），否则拿节点锁、置 `m_work_cpus`、`Current::set(node, cpu)`，无条件。
`set_nid()` 本身不动。

修完 dbg.0 过了零页分配，停在下一处：

```
[cpu0 error] Failed to map 1 pages at 18446743523953737728   // 0xffffff8000000000, physmap 起点
[cpu0 error] #UD Invalid opcode: vector=6  rip=+0x2b073        // ours::mm::VmMapping::~VmMapping()
```

有人在 physmap 起点映射一页失败，随后撞上 `ud2`。另起一节。dbg_1 仍停在第二十七节的
magic 断言上。

## 三十三、canary 当类型标签用，而 `gktl::magic<T>()` 恒等于 0（2026-09-02）

第三十二节末尾那条 `Error type magic` 断言，dbg_1 从第二十七节起就停在这里。栈：

```
init_vmm_preheap → entrol_preset_vma("k:head") → VmArea::reserve
  → VmObjectPaged::create(gaf, size=0, Pinned) → commit_range
  → Canary::verify<VmObjectPaged>()   ✗
```

### 两个缠在一起的缺陷

**其一：`gktl::magic<T>()` 对任何类型都返回 0。**

`magic<T>()` 走 `TypeName<T>::value()`，而 `strip_type_name()` 整个函数体都在
`#if defined OURS_PRETTY_FUNCTION` 里，`#else` 分支返回空 `string_view`。这个宏在全树
**没有任何地方定义过**——`grep -rn OURS_PRETTY_FUNCTION kernel system build` 除了
`type_info.hpp` 自己一无所获。空串喂给 `magic(string_view)`，循环一次都不转，`h` 保持 0。

用宿主 clang 照抄那段逻辑验证过：

```
magic("VmObjectPaged")    = 1834327018
magic<VmObjectPaged>()    = 0
magic<VmObjectPhysical>() = 0
magic<PmNode>()           = 0
```

后果是全树 117 处 `m_canary.verify<Self>()` 都在拿 0 比 0。所有 `m_canary(this)` 的构造
也写 0，所以两边恒等、永远通过——canary 机制整体是个摆设，一次损坏都发现不了。这是另一个
问题，见下一节。

**其二：`VmObject` 让 canary 和类型标签共用一个字段。**

```cpp
enum class Type {
    Paged = gktl::magic("VmObjectPaged"),      // 字符串字面量 → 1834327018
    ...
};
VmObject::VmObject(Type type, Flags vmof) : m_canary(static_cast<u32>(type)) ...
auto type() const -> Type { return static_cast<Type>(m_canary.magic()); }
```

于是 canary 里装的是**字面量**的哈希，而 `verify<Self>()` 比的是**类型名**的哈希（0）。两者
不可能相等，`VmObjectPaged` 的六个方法每一个都必然断言失败。

有意思的是 `VmObjectPhysical` 躲过了：它写的是 `verify(static_cast<u32>(Type::Physical))`，
非模板重载，两边都是字面量哈希，自洽。同一个类族里两个子类用了两套约定，只有一套是错的。

### 修法

拆开这两个职责，canary 只做 canary，类型读本来就已经存在的 `m_type`：

- `Type` 改成普通枚举值，不再是 magic。
- `VmObject` 的构造函数多收一个 `u32 magic`，由派生类传自己的 `gktl::magic<Self>()`——只有
  派生类知道自己在被造成什么。这正是 `VmAreaOrMapping` 已经在用的形状（`Base(MAPPING_MAGIC, ...)`）。
- `type()` 和 `as<Derived>()` 改读 `m_type`。
- `VmObjectPhysical` 那两处也统一成 `verify<Self>()`，整个类族一套约定。

这样今天能过（两边都是 0），等 `magic<T>()` 修好之后两边同时变成真哈希，仍然成立。

修完 dbg_1 越过断言，九个预置 VMA 全部登记成功，包括第三十一节新加的 `k:cpulocal`：

```
Reserve area k:head:     [FFFFFF8840000000, FFFFFF8840006000)
Reserve area k:code:     [FFFFFF8840006000, FFFFFF884003C000)
...
Reserve area k:physmap:  [FFFFFF8000000000, FFFFFF8800000000)
Reserve area k:cpulocal: [FFFFFF8800000000, FFFFFF8804000000)
```

## 三十四、`MappingCoalescer` 把映射失败吞掉了（2026-09-02）

上一节修完，两个镜像一起停在：

```
[cpu0 error] Failed to map 1 pages at 0xFFFFFF8000000000
[cpu0 error] #UD Invalid opcode: vector=6
```

`Failed to map` 只是一行日志——`MappingCoalescer::commit()` 打完就 `return Status::Ok`：

```cpp
auto status = ...map_bulk(va_, pa_, nr_pages_, mmuf_, ...);
if (Status::Ok != status) {
    log::error("Failed to map {} pages at {}", nr_pages_, va_);
}
...
return Status::Ok;          // ← 失败到此为止
```

两个调用点也都不接返回值：`coalescer.append(...)` 和 `coalescer.commit()` 都是裸调用。于是
`map_paged()` / `map_physical()` 无论如何都返回 `Ok`，VMM 把一个背后根本没有页表的 `VmMapping`
当成功交出去。这就是为什么一次彻底失败的映射，对上层来说是"成功"的。

### 修法

`commit()` 返回真实状态，两个调用点逐个检查并向上传播，`append()` 和 `commit()` 都加
`[[nodiscard]]`——这类错误在运行时是隐形的，只有编译器能拦住它再次发生。

要点是 `va_`/`nr_pages_`/`total_mapped_` 的推进和清零挪到早退之前：析构函数断言批次已排空
（`DEBUG_ASSERT(nr_pages_ == 0)`），传播失败的调用方仍然要能正常析构这个对象。

### 修完看到了什么

映射失败本身还在（那是下一个问题），但它现在走对了路。栈回溯从：

```
init_local_apic → Result<Arc<VmMapping>>::~Result → RefCounted::destroy → #UD
```

变成：

```
init_local_apic → VmArea::map_at → map_with_vmo → ~Rc<VmMapping> → RefCounted::destroy → #UD
```

也就是说失败不再一路伪装到 `init_local_apic` 才暴露，而是在 `map_with_vmo` 里被接住、进入
清理路径。清理路径本身踩了 `ud2`——销毁一个 `VmMapping` 会撞非法指令，那是下一节。

## 三十五、映射失败时没人拆除已经激活的 `VmMapping`（2026-09-02）

上一节末尾那个 `#UD`。销毁一个 `VmMapping` 会撞非法指令，栈停在 `~VmMapping` 里。

### 那条 `ud2` 是什么

反汇编 `~VmMapping` 的开头就看得出来：

```asm
movq 0xa0(%rdi), %rax      ; m_list_hook.m_next
testq %rax, %rax
je   ...                   ; 空指针 → 没挂在链上，正常
leaq 0xa0(%rbx), %rcx      ; &m_list_hook
cmpq %rcx, %rax
jne  0x37693               ; 既不是空、也不指向自己 → ud2
```

用 `-fdump-record-layouts` 确认偏移 0xa0 正是 `VmMapping::m_list_hook`。这是 ustl 侵入式钩子
的自检：析构一个仍然挂在链表上的节点，直接陷阱，而不是默默把链表写坏。陷阱是对的，说明确实
有节点被带着链子销毁了。

### 谁把它挂上去，谁忘了摘

`VmMapping::activate()` 把自己挂进 VMO 的 mapping 链表，它自己的注释就提醒过这件事：

```cpp
// Note when a mapping was added into a VMO's mapping list, the inside counter
// has not been increased implicitly. It is required to pay attention to manually
// install and uninstall a mapping, avoiding lifecycle problem.
m_vmo->add_mapping(*this);
```

而 `VmArea::map_with_vmo()` 在 `create_mapping()`（末尾就是 `activate()`）成功之后，
`commit_range` 或 `map` 一失败就直接 `return ustl::err(status)`。局部的 `Arc<VmMapping>`
析构、引用计数归零、`~VmMapping` 在一个仍然挂在 VMO 链表和父 VMA 子集里的节点上运行——正是
钩子要拦的情况。上一节把错误传播修好之后，这条清理路径第一次真的被走到，于是陷阱就露出来了。

### 两处都要改

**其一，`map_with_vmo` 的失败路径要拆除 mapping。** `VmMapping::destroy()` 就是 `activate()`
注释里要的那个对应操作：unmap 已装上的部分、从 VMO 链表和父节点上摘下来、清掉 Active。

**其二，`VmMapping::destroy()` 不能在 unmap 失败时提前返回。** 它原来是：

```cpp
auto status = ...unmap(...);
if (Status::Ok != status) {
    log::trace(...);
    return status;        // ← 后面的注销全跳过了
}
if (m_vmo) { m_vmo->remove_mapping(*this); }
```

补上第一处之后立刻撞到这里：unmap 返回 `InvalidArgument`（那一页本来就没映射上），于是
`remove_mapping` 被跳过，节点照样带着链子被销毁，`ud2` 依旧。unmap 失败值得报告，但一个被
销毁却仍留在两条活链表上的对象是链表损坏，后者严重得多。现在两件事都做，状态照常返回。

### 结果

`#UD` 消失，dbg_1 第一次报出真实错误：

```
Failed to map 1 pages at 0xFFFFFF8000000000
Failed to tear down the mapping at 0xFFFFFF8000000000 after a failed map: InvalidArgument
Assertion failed on result with message: Failed to allocate MMIO for BP's Local APIC
```

也就是 `init_local_apic()` 自己那句 `DEBUG_ASSERT(result, ...)`——错误一路传到了检查它的地方。

剩下两件事，都不在 mm 里：

1. **LAPIC 的 MMIO 被分到了 physmap 起点**（第三十二节记的那条）。`map_at` 的 `virt_base`
   传的是 `0`，让 VMM 自己挑地址，挑到了 `0xFFFFFF8000000000`。这是真正的下一个问题。
2. **`init_local_apic()` 用 `DEBUG_ASSERT` 检查 `Result` 之后无条件解引用。** dbg.0 把断言
   编译掉，于是 `(*result)->base()` 作用在一个错误 Result 上，陷阱位置在 `init_local_apic`
   自己（+0x6c541）。dbg_1 停在断言上，dbg.0 停在这里。`local_apic.cpp` 正被另一个会话改着，
   这一处留给它。

## 三十六、非固定映射从来没用上 `alloc_spot()` 找到的地址（2026-09-02）

第三十二节起就挂着的那条 `Failed to map 1 pages at 0xFFFFFF8000000000`。LAPIC 的 MMIO 被放
到了 physmap 起点，和已有映射冲突。

`init_local_apic()` 调的是：

```cpp
map_at(arch::APIC_PHYS_BASE, 0, PAGE_SIZE, ..., VmMapOption::Commit | Pinned, "Local-APIC");
```

第二个参数是 `virt_base`，传 `0` 表示"地址由 VMM 挑"。往下走到
`VmArea::create_subaom_preamble()`，没有 `Fixed` 选项的分支是：

```cpp
} else {
    // If no given **Fixed** options, the specific address would be overwritten.
    auto result = alloc_spot(size_aligned, PAGE_SIZE, m_base, m_base + m_size - 1);
    if (!result) {
        return ktl::err(Status::InvalidArguments);
    }
}

return ktl::ok(ustl::make_pair(base_aligned, size_aligned));
```

`alloc_spot()` 返回 `ktl::Result<VirtAddr>`，也就是找到的那个空位——**结果被算出来然后扔掉
了**。函数返回的仍是上面按 `offset` 算出来的 `base_aligned`。那句注释说地址"would be
overwritten"，说明本意就是要覆盖，只是这一行从来没写。

于是每一个不带 `Fixed` 的请求都落在 `m_base + offset` 上。调用方根本不给地址时 `offset` 是
0，落点就是这个 VMA 的开头；而内核 root VMA 的开头正是 physmap 起点。

### 修法

把找到的空位赋回去：`base_aligned = *result;`。顺手把失败时的 `Status::InvalidArguments`
换成 `alloc_spot()` 真正返回的错误——地址空间耗尽和参数非法不是一回事。

### 结果

映射失败彻底消失（新日志里 `Failed to map` 一次都没有），两个镜像一口气冲过了整个 APIC
初始化：Local APIC 起来、IO-APIC 24 条中断线全部配好、APIC 定时器完成校准。

```
[cpu0 trace] IO-APIC[0]: configuration(edge, high, fixed, physical, 0, 32)
...
[cpu0 info] APIC timer: 10068285 counts/tick at divisor 1, TSC 10068000 cycles/tick
```

新的停靠点已经在调度器里，离 mm 很远了：

- dbg_1：`scheduler.cpp:218` 的 `DEBUG_ASSERT(num_schedule > 0)`。
- dbg.0：断言被编译掉，随后 `rip=0x0`——调了一个空函数指针。

这两处属于 `kernel/task` 与 `kernel/time`，另一个会话正在那一片工作，留给它。

## 三十七、让 canary 真正工作：`magic<T>()` 恒为 0，以及一批从没播种的 canary（2026-09-03）

第三十三节里顺带发现、当时只记录没有修的那个问题。

### 一、`gktl::magic<T>()` 对每个类型都返回 0

`magic<T>()` 走 `TypeName<T>::value()` → `priv::strip_type_name()`，而那个函数整个函数体都在
`#if defined OURS_PRETTY_FUNCTION` 里，`#else` 返回空 `string_view`。这个宏全树没有任何地方
定义过。空串喂给 `magic(string_view)`，循环一次不转，结果恒为 0。

于是全树 117 处 `Canary::verify<T>()` 都在拿 0 比 0，永远通过。canary 机制看起来在工作，实际
一次损坏都发现不了。

原来的实现还有两处坏掉的地方：`strip_type_name()` 返回的是 `value.data()`，长度信息丢了，
切出来的名字会一路跑到字符串结尾；`type_name(int)` 的默认模板实参引用了一个根本不存在的
`stripped_type_name`（`strip_` 写成了 `stripped_`）。

**修法**：`OURS_PRETTY_FUNCTION` 定义为 `__PRETTY_FUNCTION__`，并且**不留回退分支**——不认识
的编译器直接 `#error`。原来那个"优雅降级"正是灾难本身：它把整个机制静默地关掉了，而没有任何
人会注意到。`strip_type_name()` 改成返回带长度的 `string_view`，从 `"Type = "` 之后切到第一个
`';'`（gcc）或最后一个 `']'`（clang）。两个没用的 `type_name()` 重载一并删掉。

宿主验证：

```
name<VmObjectPaged>     = 'ours::mm::VmObjectPaged'
magic<VmObjectPaged>    = 531456611
magic<VmObjectPhysical> = 3326816834
magic<PmNode>           = 4078567354
```

### 二、机制一打开，一批从没播种的 canary 就亮了

这正是"一个 bug 掩盖另一个 bug"的教科书例子。改完立刻在 `init_pmm()` 里停住：`PmNode` 的构造
函数明明白白写着 `m_canary()`——默认构造，magic 0——而 `PmNode::init()` 调 `verify<Self>()`。

同类问题一共九个类：`PmNode`、`VmAspace`、`Mutex`、`CpuStopper`、`Scheduler`、`RunQueue`、
`Thread`、`HpetChannel`、`HpetClockSource`。它们都调 `verify<Self>()`，却从没给 canary 播过种。

播种方式用声明处的默认成员初始化 `gktl::Canary m_canary{this};` 而不是改构造函数：这样默认
构造函数也一并覆盖，将来新增构造函数不会漏。只有本来就把 `m_canary()` 显式写进初始化列表的
三个（`PmNode`、`HpetChannel`、`HpetClockSource`）改的是初始化列表本身，因为显式初始化会盖掉
默认成员初始化。

`Canary` 的默认构造函数那里补了注释说明这条约定：零 canary 是给"根本不检查"的对象用的，一个
调 `verify<T>()` 的类必须播种。

### 结果

dbg_1 回到修改前的同一个前沿（`scheduler.cpp:218` 的 `num_schedule > 0`），没有回退，而 canary
从此是真的在检查。它在这一次改动里就抓到了两个真实缺陷（`PmNode` 和 `HpetChannel` 的未播种
canary），这是它上线之后立刻兑现的价值。

### 还留着一处：wait queue 一族

`WaitQueue` / `OwnedWaitQueue` 有和第三十三节 `VmObject` 一模一样的混用，而且更深一层：

```cpp
static constexpr auto MAGIC       = gktl::magic("WaitQueue");        // 字面量
static constexpr auto OWNED_MAGIC = gktl::magic("OwnedWaitQueue");   // 字面量
WaitQueue() = default;                                               // canary 是 0

// 而且 canary 被当成向下转型的类型标签用：
if (self->m_canary.magic() == OwnedWaitQueue::OWNED_MAGIC) { ... }
```

三个毛病叠在一起：默认构造的 `WaitQueue` canary 是 0 却会被 `verify<Self>()` 检查；播种用的是
字面量哈希而检查用的是类型名哈希；canary 同时兼任类型标签。

目前的启动流程还没走到这里（先停在调度器），所以没有暴露。正确的修法和 `VmObject` 那次一样：
`MAGIC`/`OWNED_MAGIC` 改成 `gktl::magic<Self>()`，`WaitQueue()` 播种，向下转型比同一个值。
`wait_queue.hpp`、`wait_queue.cpp` 正被另一个会话改着，留给它。
