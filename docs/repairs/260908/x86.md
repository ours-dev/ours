# x86 待修项（2026-09-08）

## 1. `x86_syscall` 调用处理函数时栈没有按 SysV 对齐

`x86_syscall` 从 `tss.sp0` 开始压 17 个 8 字节的槽位（`arch::SyscallFrame`），然后
`call *(%r11, %rax, 8)`。

内核栈是页对齐的（日志里 `Allcoated Kernel stack:[FFFFFF880401D000, ...)`），所以
`tss.sp0` 是 16 字节对齐的；17 × 8 = 136，而 136 mod 16 = 8。于是执行到 `call` 时
`%rsp ≡ 8 (mod 16)`。

x86-64 SysV 要求的是：**在 `call` 之前** `%rsp` 16 字节对齐，这样被调用函数入口处
（`call` 压了返回地址之后）`%rsp ≡ 8 (mod 16)`。现在正好差 8 —— 处理函数入口拿到的是
16 字节对齐的 `%rsp`，等于整体错了半拍。

现在不炸，是因为内核用 `-mno-sse` 编译，没有需要 16 字节对齐的溢出。任何一天有人给
某个处理函数用上对齐的局部量（或者编译器为 `memcpy` 之类挑了对齐指令），它就会炸，而
且现场看起来会和系统调用毫无关系。

`interrupt_common`（`exception.S`）值得一并核对：它的帧槽位数不同，对齐结论未必一样。

修法是在 `call` 前把 `%rsp` 补齐（压一个哑槽位，或者让帧本身凑成 16 的倍数——后者更
好，因为它同时让 `SyscallFrame` 的大小自我说明）。注意不能简单 `and $-16, %rsp`：
出口要按帧的确切大小往回弹。
