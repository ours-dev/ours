# x86 —— 待修项（2026-09-10）

## SSE 从来没被打开：`CR4.OSFXSR` 有定义、无人写

**状态：暂缓，不是遗漏**（2026-09-17 决定）。当前没有任何东西需要浮点或 SIMD——
内核不用，用户程序也还没有用得上的场景。本仓库按「用户空间的真实需求倒逼」来选活，
所以在出现第一个需要浮点的用户程序之前不做这一条。下面的分析和修法顺序保持原样，
等需求出现时照着做。

在此之前，`-msoft-float -mno-mmx -mno-sse -mno-sse2` 这组开关是**有效的约束**而不是
临时绕法：它保证编译器不会替谁擅自向量化。谁要去掉它们，必须先做完下面第 1、2 步。

**严重程度**：中。当下被绕开了（用户态和内核都用 `-mno-sse` 编译），代价是**整个内核和
所有用户程序都跑在软浮点上**，而且第一个不知情的人会撞上一个非常难读的错误。

**症状**
一个用户程序只要大到让编译器向量化，第一条 SSE 指令就 `#UD`：

```
[4127082000 cpu1 error] #UD Invalid opcode: vector=6, error_code=0x0
```

`//examples/shell` 就是这么撞上的——它比 userboot 只大一点，编译器把一次结构体
初始化向量化成了 `pxor` / `movdqu` / `movdqa`（8 条），全部非法。userboot 里 0 条，
所以这条路一直是通的。

**证据**
```
$ grep -rn 'OSFXSR\|OsFxsr' kernel/ --include='*.cpp' --include='*.hpp'
kernel/arch/x86/lib/arch/include/arch/x86/system.hpp:51:        OsFxsr = 9,
kernel/arch/x86/lib/arch/include/arch/x86/system.hpp:96: ... FieldAt<Cr4Bits::OsFxsr> ...
```
只有位的**定义**，没有任何一处**置位**。`x86_init_percpu` 写的是 `FsGsBase` 和 `Umip`。

**当前的绕法**
`system/BUILD.gn` 的 `user.standalone` 加上了 `-msoft-float -mno-mmx -mno-sse
-mno-sse2 -mno-3dnow -mno-avx -mno-avx2`，和内核侧一致。用户程序因此不会再生成 SSE。

**该怎么修**
顺序是固定的，跳步就会坏得更隐蔽：

1. **先有 FPU/SSE 状态**：每个线程一块 `FXSAVE`/`XSAVE` 区域，在上下文切换时保存恢复。
   没有这个就置位 `OSFXSR`，两个线程会共用同一组 XMM 寄存器——比 `#UD` 难查得多。
2. `x86_init_percpu` 里置 `CR4.OSFXSR` + `CR4.OSXMMEXCPT`，并处理 `#XF`（vector 19）。
3. 把 `-mno-sse` 之类从 `user.standalone` 去掉，内核侧保留（内核用 SSE 需要在中断路径
   上也保存状态，那是另一个决定）。
4. `//system/app/shell` 可以作为回归：去掉编译开关之后它必须仍然跑通。

对标 Linux `fpu__init_cpu()` / `arch/x86/kernel/fpu/init.c`；Zircon 是
`x86_init_percpu()` 里的 `x86_extended_register_init()`。

**影响到的东西**
- 所有用户程序：不能用浮点、不能用任何 SIMD，编译器也不会替它们向量化。
- 内核：同样，且 `memcpy` 之类拿不到 SIMD 的加速。
